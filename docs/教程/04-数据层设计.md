### 🧠 设计思路与原理

**① SQLite 是什么？为什么它适合这个项目？**

SQLite 是一个**嵌入式**数据库：没有数据库服务进程、没有安装步骤，整库就是磁盘上的**一个文件**。对比常见方案：

| 方案 | 形态 | 本项目选它的理由 / 弃它的理由 |
| --- | --- | --- |
| MySQL / PostgreSQL | 独立服务进程 | 要安装、要配置、要保活——个人工具不需要 |
| MongoDB 等文档库 | 独立服务进程 | 同上，且引入新查询语言 |
| **SQLite（本项目）** | 一个文件 | 零安装、零配置、删除文件即「恢复出厂」 |
| 直接读写 JSON 文件 | 一个文件 | 无事务、无索引、并发写入易损坏——数据量一上来就痛苦 |

选型结论在第 1 章写过，这里补一层工程视角：SQLite 用**文件级**的简单性，换来了**关系级**的能力（事物、约束、索引、聚合查询）。这正是一个单用户工作台需要的全部。

**② 为什么用 `node:sqlite` 而不是 better-sqlite3？**

| 方案 | 安装 | API 风格 | 结论 |
| --- | --- | --- | --- |
| `sqlite3` | 需编译原生模块（新手噩梦） | 回调式异步 | 弃 |
| `better-sqlite3` | 需编译原生模块 | 同步 | 好用，但仍是第三方依赖 |
| **`node:sqlite`（本项目）** | **零安装**（Node 24 内置） | 同步（`DatabaseSync`） | 选它：零依赖 + 固定版本底线（第 1 章） |

**③ 同步 API 会不会「卡死」服务器？**

`DatabaseSync` 的每个查询都是**同步阻塞**的——查完才继续。听起来危险，但对本项目是**正确的取舍**：单用户、本地文件、每次查询亚毫秒级，阻塞时间可以忽略；换来的是代码极其简单（没有 `await`、没有连接池、没有事务回调地狱）。第 5 章你会看到，一个函数就能串完「查总数 → 查当页 → 组装返回」。反向条件：如果将来要服务多用户或做重查询，就得换成异步方案。

**④ 16 张表的分工**（第 0 章的地图，本章把它变成代码）

| 组 | 表 | 本章? |
| --- | --- | --- |
| 组织与系统 | `modules` `settings` `audit` `migrations` | ✅ 创建 |
| 业务资产 | `cases` `knowledge` `regressions` `reports` `workflows` | ✅ 创建 |
| 任务与流转 | `tasks` `relations` | ✅ 创建 |
| 模型配置 | `providers` | ✅ 创建 |
| 工作流引擎 | `workbench_assets` `workflow_runs` `workflow_run_steps` `validation_cases` | 第 8 章 |

**⑤ 五条数据约定**（后面每章都会用到，先记住）

1. **命名**：数据库列用 `snake_case`（SQL 传统），API 输出用 `camelCase`（JS 传统），由 `mapRow()` 自动转换；
2. **主键**：业务表用 `TEXT` 主键 + 前缀 id（如 `task_ab12cd34`——可读、可调试、不暴露记录数量）；纯流水表（relations/audit）用 `INTEGER AUTOINCREMENT`；
3. **JSON 列**：结构多变、整体读写的字段（步骤、分析结果、报告统计）存成 JSON **字符串**——避免为易变内容频繁 `ALTER TABLE`；
4. **时间**：统一 `TEXT` 存 ISO 字符串（`new Date().toISOString()`），可排序、可读、无时区歧义；
5. **状态**：状态机语义放进 `TEXT` 状态字段，`DEFAULT` 兜底初值。

## 4.1 打开数据库：几行代码，两个 PRAGMA

**第一步**：改 import。把 `server.mjs` 顶部改成（注意新增的 `mkdir` 和 `node:sqlite`）：


**第二步**：在四个常量（`root` / `port` / `host` / `production`）之后、`function send` 之前，插入：

```js
const dataDir = join(root, 'data');
await mkdir(join(dataDir, 'backups'), { recursive: true });
const db = new DatabaseSync(join(dataDir, 'testpilot.sqlite'));
db.exec('PRAGMA journal_mode=WAL; PRAGMA foreign_keys=ON;');
```

逐行讲解：

1. `const dataDir = join(root, 'data')`——所有运行期数据的家：数据库、密钥、备份都放这里。用第 3 章算好的 `root` 拼绝对路径，**不依赖启动目录**；
2. `await mkdir(join(dataDir, 'backups'), { recursive: true })`——`recursive: true` 意味着「父目录不存在就一起建」：一次调用同时建出 `data/` 和 `data/backups/`。`backups/` 是为第 11 章的数据迁移备份预留的——**现在就建**，让第一次运行就有确定的目录结构，之后写入不用再判存在性；
3. `new DatabaseSync(join(dataDir, 'testpilot.sqlite'))`——打开数据库。SQLite 的特性：**文件不存在时自动创建**，不需要「先判断再初始化」；
4. `db.exec(...)` 一次执行两条 PRAGMA，这两条值得展开对比：

| PRAGMA | 作用 | 生效范围 |
| --- | --- | --- |
| `journal_mode=WAL` | 启用「预写日志」模式（见下） | **持久**——记录在数据库文件头里，设置一次永久生效 |
| `foreign_keys=ON` | 打开外键约束检查 | **每连接**——SQLite 默认关闭，**每个新连接都必须重设** |

一句话记忆：**一个是一次性的，一个是每次必须的**——这也是为什么它们被放在服务器启动代码里。

**WAL 是什么、为什么关心它？** 默认日志模式（DELETE）下，写事务会锁住整个数据库，其他读取只能排队。WAL（Write-Ahead Logging）把新数据先追加到 `-wal` 附属文件，主库的读者**不被打断**（读不阻塞写、写不阻塞读），崩溃恢复也更快。代价是多出两个附属文件：`testpilot.sqlite-wal`、`testpilot.sqlite-shm`——**正常关闭时自动合并（checkpoint）回主库**，所以它们不是垃圾文件，**不要手动删**。本项目长期开着服务器，你还可能随时用命令行做只读查询——WAL 让两头互不打架。

> 现在重启 `npm run dev`，你会看到 `data/` 目录出现。这就够了——表还没有，但「家的地基」已经打好。真正的验证放在 4.6。

### 设计决策的三个小讨论

**① 为什么主键有的用 TEXT、有的用 AUTOINCREMENT？** 业务表（tasks/cases/…）的 id 会被外键引用、会出现在 URL 和前端列表里——用带前缀的 TEXT（`task_ab12cd34`）便于调试和肉眼识别；relations/audit 是纯流水，只关心顺序——`INTEGER AUTOINCREMENT` 最省事。

**② 为什么 dump 这么多 `DEFAULT`？** 它们把「业务默认值」下沉到数据层兜底：新建任务默认 `草稿 / 未提交 / 未入库`、默认风险 `P1`——就算 API 层漏传字段，存进去的也是**合法状态**而不是 `NULL`。`NOT NULL + DEFAULT` 是本项目最常用的组合。

**③ 外键为什么只写了三张表？** `tasks` / `cases` / `knowledge` 上有 `FOREIGN KEY(module_id) REFERENCES modules(id)`；`regressions` 的 `module_id` 没写外键——这是真实项目的**历史遗留**（不是设计缺陷，只是演化中没补）。写出来是想让你知道：真实项目很少「处处完美」，重点是**明确知道哪里妥协了**。

## 4.3 四个小工具：now / makeId / json / parse

建表之后、数据之前，先备四个小工具（真实项目第 34–37 行，逐字一致）：

```js
const now = () => new Date().toISOString();
const makeId = prefix => `${prefix}_${crypto.randomUUID().slice(0, 8)}`;
const json = value => JSON.stringify(value ?? {});
const parse = (value, fallback = {}) => { try { return JSON.parse(value); } catch { return fallback; } };
```

1. `now()`——统一的时间来源。ISO 格式（`2026-10-02T08:00:00.000Z`）可读、可按字符串排序、无时区歧义。**全项目所有时间戳都从这来**，不要在别处 `new Date()`；
2. `makeId(prefix)`——`crypto` 是 Node 的全局对象（无需 import）；`randomUUID()` 生成标准 UUID，`slice(0, 8)` 取前 8 位十六进制（32 位随机）——对个人工具绰绰有余，且 id 带上 `task_` / `kb_` 前缀后，看日志一眼就知道是哪种实体；
3. `json(value)`——序列化。`?? {}` 保证 `undefined`/`null` 不会变成字符串 `"undefined"`，而是存成合法的 `{}`；
4. `parse(value, fallback)`——反序列化的**安全版**：`JSON.parse` 会为脏数据抛异常，这里 `try/catch` 兜住，失败返回 fallback（默认 `{}`）。**「读取永不崩溃」**是数据层铁律：数据库里可能存着历史脏数据，读的时候要优雅降级。

这段代码有四个值得学习的点：

**① 幂等守卫——第一行就是灵魂**：

```js
if (db.prepare('SELECT COUNT(*) AS n FROM modules').get().n) return;
```

`modules` 表里有任何一条数据就直接返回——**种子只在「第一次启动、库还全空」时执行**。效果：反复重启服务器，演示数据不会翻倍。注意这是「整段跳过」的粗粒度策略：它保证的是**不重复**，不保证「数据被部分删除后自动补齐」（简单策略，够用即可）。

**② prepare 一次、run 多次**——循环插入的标准姿势：

```js
const insertModule = db.prepare('INSERT INTO modules VALUES (?, ?, ?, ?, ?, ?, ?)');
[...].forEach((m, i) => insertModule.run(...m, '启用', i + 1, now()));
```

`prepare` 把 SQL 编译成语句对象（一次），`run` 执行并传参（多次）——比每次拼 SQL 字符串又快又安全。`?...?` 是**参数占位符**，参数与列**按位置一一对应**：`modules` 表 7 列，所以这里有 7 个 `?`。

**③ `...r.slice(0,8)` 的接法**——先把「数组模式」当作**值表**看：一条用例在代码里是个数组 `[id, code, title, module_id, priority, type, version, status, 内容对象]`；`cases` 表 13 列 = 前 8 个直接展开 + `null`（source_task_id）+ `json(r[8])`（content_json）+ `0`（archived）+ 两个时间戳。这种「数组 + 展开 + 少量手工参数」的写法让 seed 一眼能数出每行数据，代价是要**盯住列顺序**（见「要点与坑」第 5 条）。

**④ 业务场景是连贯的**——全部演示数据围绕「支付回调」这一个场景编织：知识库里是支付回调的历史 Bug、日志关键字、回归规则；任务是从这些材料分析出来的记录；回归清单引用用例与任务；报告引用回归与任务。打开界面后，每一个页面的数据都能互相跳转——这是**有意设计的**，教学、截图、演示都靠它。

## 4.5 关联数据与两个映射函数

### relations 的第一条数据（守卫式插入）

真实项目第 80–82 行，紧跟在 `seed()` 调用之后：

```js
if (!db.prepare("SELECT 1 FROM relations WHERE source_type='task' AND source_id='task_bug_001' AND target_type='knowledge' AND target_id='kb_004'").get()) {
  db.prepare('INSERT INTO relations(source_type,source_id,target_type,target_id,label) VALUES(?,?,?,?,?)').run('task','task_bug_001','knowledge','kb_004','Bug 分析引用回归规则');
}
```

为什么这一条**不在 seed() 里**？回到 4.4：seed 的守卫是「modules 非空就整体跳过」——而 `relations` 是项目**后期**才加入的表（真实演进史）：老库里早就有了 modules，seed 永远不会再执行，所以这条关联需要**自己的守卫**。用的惯用法是「先 `SELECT 1` 判断存在，不存在才插入」（insert-if-absent）——和第 4.4 的「整体跳过」相比，这是**行级**的幂等。

> 它也演示了一个真实工程状态：schema 与数据在持续演化，每个新加的种子数据都要自己解决「老库怎么补上」的问题。

### moduleLabel()：把模块 id 翻译成人话

```js
function moduleLabel(moduleId){if(!moduleId)return '';const m=db.prepare('SELECT * FROM modules WHERE id=?').get(moduleId);return m?`${m.project_name} / ${m.module_name} / ${m.submodule_name}`:'';}
```

数据库里任务/用例只存 `module_id`（如 `mod_pay_callback`），但界面要显示「电商平台 / 支付中心 / 支付回调」。这个函数把三级名字拼成显示串，随每条记录一起返回给前端——**前端拿来即显示，不用再查一次模块表**。

> 性能小讨论：列表 20 行数据，`mapRow` 会对每行调用一次 `moduleLabel` —— 20 次单行查询（典型的 N+1）。为什么能接受？SQLite 同步查询亚毫秒级、本地单用户、列表页最大 100 行。这是「先简单正确，再按需优化」的实例；要优化可以缓存模块表（只有几十行）。

### mapRow()：数据库语言 → API 语言的翻译官

```js
function mapRow(resource,row){if(!row)return null;const camel=Object.fromEntries(Object.entries(row).map(([k,v])=>[k.replace(/_([a-z])/g,(_,c)=>c.toUpperCase()),v]));for(const key of ['inputJson','resultJson','contentJson','dataJson','stepsJson','valueJson'])if(key in camel){camel[key.replace('Json','')]=parse(camel[key]);delete camel[key];}if(camel.moduleId)camel.moduleLabel=moduleLabel(camel.moduleId);if(resource==='providers')camel.keyConfigured=Boolean(camel.keyMask);return camel;}
```

一行压缩代码，拆开看是三层转换：

**第一层：改键名（snake_case → camelCase）**

```js
Object.entries(row).map(([k, v]) => [k.replace(/_([a-z])/g, (_, c) => c.toUpperCase()), v])
```

正则 `_([a-z])` 匹配「下划线 + 小写字母」，替换成该字母的大写：`review_status` → `reviewStatus`、`module_id` → `moduleId`、`created_at` → `createdAt`。`Object.fromEntries` 把处理后的键值对重新装配成对象。**为什么要有这一层？** 数据库按 SQL 惯例用 `snake_case`，前端 JS 按语言惯例用 `camelCase`；两边都不想改，就在中间架一座桥——这座桥只存在于 `mapRow` 一个函数里，API 层直接吐 camelCase，前端零适配。

**第二层：JSON 列反序列化（字符串 → 对象）**

```js
for (const key of ['inputJson','resultJson','contentJson','dataJson','stepsJson','valueJson'])
  if (key in camel) { camel[key.replace('Json','')] = parse(camel[key]); delete camel[key]; }
```

数据库列 `input_json` 改键名后是 `inputJson`，值还是一段**字符串**；这层把它 `parse` 成**真对象**后改名去尾：`inputJson` → `input`。于是 API 输出里：`input` 是对象、`contentJson` 这个名字**永远不会出现**。六个列名就是一纸清单——凡是有 `_json` 后缀的列，都会被自动处理。**新增此类列时，记得把它加进这个数组**（这是个容易漏的约定）。

**第三层：派生字段（注入计算出来的附加值）**

```js
if (camel.moduleId) camel.moduleLabel = moduleLabel(camel.moduleId);   // 模块全名
if (resource === 'providers') camel.keyConfigured = Boolean(camel.keyMask);  // 是否已配 Key
```

- `moduleLabel` 见上；
- `keyConfigured`：providers 列表里，前端只需显示「已配置 / 未配置」状态，用 `key_mask` 是否非空转换成一个布尔值——真实 Key 在磁盘加密文件中（第 9 章）。

最后注意函数开头的 `if (!row) return null`——查不到记录时安全返回 `null`，调用方（第 5 章）据此返回 404。

### ⚠️ 要点与坑

1. **`foreign_keys` 是「每连接」的**——SQLite 默认不开外键检查，每个新进程/连接都要重设；而 `journal_mode=WAL` 是持久的（存在数据库文件头里）。这就是同一行里两条 PRAGMA 本质不同的地方；
2. **别手动删 `-wal` / `-shm` 文件**——未合并的数据还在 `-wal` 里；正常 `Ctrl+C` 关闭会自动 checkpoint 合并。想用文件层面备份数据库，先停服务器；
3. **JSON 列忘 `stringify` 会静默坏数据**——直接塞对象进去会存成 `"[object Object]"`，`parse` 会安全地回退成 `{}`，**不报错但数据丢失**。写库一律走 `json()`，读库一律走 `parse()`；
4. **时间只用 `now()`**——真实项目全部时间戳都是 ISO 格式；混入 SQLite 的 `datetime('now')`（`YYYY-MM-DD HH:MM:SS`，无 T、无毫秒、无 Z）会造成字符串排序错乱；
5. **`INSERT ... VALUES(?,?,...)` 与列顺序强绑定**——`?` 按位置对应列；以后改表结构（插入新列），**所有**相关 insert 都要同步改（真实项目里这样的 insert 有十几处）。改表前先搜一遍 `INSERT INTO 表名`；
6. **seed 是「全空才跑」的粗粒度幂等**——半删数据不会自动补齐；要恢复演示数据就删 `data/` 目录重建（验证 F）。删目录前想清楚：**自建的正式数据也会一起没**；
7. **`DatabaseSync` 会阻塞事件循环**——本地单用户无感；但别在循环里对 10 万行做逐行查询。列表查询已经用「一次 COUNT + 一次 LIMIT 分页」规避了（第 5 章）。
