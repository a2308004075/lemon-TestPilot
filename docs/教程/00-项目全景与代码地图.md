## 0.1 成品是什么

TestPilot 是一个**只在你自己电脑上运行**的测试工作台：数据保存在本机 SQLite 文件里，默认只有 `127.0.0.1:3344` 能访问，AI 只用你自己配置的模型。

![工作台首页](../手册截图/01-工作台首页.png)

它的主线业务流程一句话概括：

> **粘贴一段材料（Bug 现象 / 需求 / 日志 / SQL / 变更说明）→ 系统识别该做什么 → 按固定顺序执行分析 → 生成结构化结果 → 人工复核 → 沉淀进知识库 → 汇总成测试报告**

左侧导航有 13 个功能页，按职责分为四组：

| 分组 | 页面 | 职责 |
| --- | --- | --- |
| 工作台入口 | 工作台首页、AI 测试助手、执行记录、工作台编排、案例验证 | 智能任务的主入口与全流程追溯 |
| 分析工具 | 用例库、Bug 分析、日志分析、SQL 分析 | 日常测试工作的核心操作台 |
| 质量资产 | 回归测试、测试报告、知识库 | 结果沉淀与质量结论 |
| 系统配置 | 配置中心 | 三级模块、大模型、格式模板、关联规则 |

打开[用户操作手册](../用户操作手册.md)可以逐页看到 13 个模块的最终形态（含 24 张真实截图）。这份教学文档要讲的，就是如何把这些东西从零做出来。

## 0.2 架构总览

### 整体架构

整个系统只有**一个进程**（`node server.mjs`），结构极其简单：

```
┌────────────────────────────── 你的电脑 ──────────────────────────────┐
│                                                                      │
│   ┌─────────────┐        HTTP (JSON)        ┌─────────────────────┐  │
│   │   浏览器     │  ◄──────────────────►    │  node server.mjs    │  │
│   │  React 前端  │   /api/* → 业务接口       │  （唯一后端进程）     │  │
│   └─────────────┘   /*     → 页面/静态资源   │                     │  │
│                                             │  ├ handleApi()      │  │
│                                             │  │   ├ 通用资源层    │  │
│                                             │  │   └ workbench-api│  │
│                                             │  └ 静态文件/ dist   │  │
│                                             └─────────┬───────────┘  │
│                                                       │              │
│                             ┌─────────────────────────┴───────────┐  │
│                             │ data/testpilot.sqlite （SQLite 文件） │  │
│                             │ data/keys/*.dpapi  （加密的 API Key） │  │
│                             └─────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────────────┘
```

三个关键事实，先记住，后面每章都会回来：

1. **前后端同进程、同端口**：浏览器只访问 `127.0.0.1:3344` 一个地址；`/api/*` 是数据世界，其余路径是界面世界；
2. **没有外部服务**：没有数据库服务器、没有后端云服务。数据库就是一个文件，删掉文件 = 恢复出厂设置；
3. **开发/生产模式**：开发时服务器内嵌 Vite 提供热更新；生产时只服务 `dist/` 里的静态文件（第 3 章详解）。

这是当前项目的完整目录（★ 标注的是教程核心要讲的 8 个文件）：

├── index.html                前端唯一的 HTML 容器
├── src/
│   ├── main.tsx            ★ 前端全部：App 骨架 + 15 个页面组件 + 详情抽屉
│   ├── workbench.tsx       ★ 工作台 4 页：助手 / 执行记录 / 编排 / 案例验证
│   ├── styles.css            全局样式（CSS 变量 + 语义类名）
│   └── vite-env.d.ts         Vite 环境类型声明（自动生成性质，不用改）

├── tsconfig.json             TypeScript 严格模式配置
├── start.bat / start.command / 启动 TestPilot.command
│                             双击启动脚本（Windows / macOS）

### 一次操作的生命周期

用一次真实操作把整条链路串起来，这是后面每章都要回到的“地图”：

| 步骤 | 发生位置 | 发生了什么 |
| --- | --- | --- |
| 1 | 浏览器 | 你在 AI 助手页粘贴材料，点「按流程执行」 |
| 2 | 浏览器 | 前端发出 `POST /api/workbench/runs`，body 为 `{ text, moduleId, selectedRoutes }` |
| 3 | `server.mjs` | `http.createServer` 回调收到请求，`new URL` 解析路径，发现以 `/api/` 开头 → 交给 `handleApi()` |
| 4 | `server.mjs` | `parts[1] === 'workbench'` → 转发给 `workbench-api.mjs` 的 `handle()` |
| 5 | 引擎 | `routeText()` 用触发词匹配出 4 条路由并按固定顺序排序 |
| 6 | 引擎 | `fieldPresent()` 检查材料缺不缺必填信息；风险正则判定 P0/P1/P2 |
| 7 | 引擎 | 把执行记录写入 `workflow_runs`，每个工作流步骤写入 `workflow_run_steps` |
| 8 | 引擎 → 浏览器 | 返回 201 + 完整执行快照（JSON），前端渲染成「执行结果卡片」 |
| 9 | 数据库 | 这条记录永久保存在 SQLite 里，打开「执行记录」页随时可查、可复核 |

## 0.3 代码地图（8 个核心文件）

现役核心代码只有 8 个文件、约 600 行——但因为压缩风格，信息量约等于常规写法的 3000+ 行。逐个了解它们，以及「打开后你会看到什么」：

| 文件 | 行数 | 打开后你会看到 | 阅读优先级 |
| --- | --- | --- | --- |
| `package.json` | 30 | 依赖清单 + 5 个脚本入口 | ★★★★★ 先看 |
| `server.mjs` | 127 | 顶部一大段建表 SQL → seed 演示数据 → 若干单行函数（mapRow / listResource）→ 一个巨大的 `handleApi` → 底部静态服务与监听 | ★★★★★ |
| `workbench-api.mjs` | 69 | 顶部 7 个入口的数据定义 → 路由/缺项/输出三个函数 → `createWorkbench(db)` 返回处理器 | ★★★★★ |
| `src/main.tsx` | 200 | 导入 + NAV 导航数组 + 工具组件区 + 15 个页面组件（每个压缩成 1–6 行）+ 20 来个工具函数 | ★★★★★ |
| `src/workbench.tsx` | 35 | 工作台 4 个页面组件，每个占据 1 行左右的“超宽行” | ★★★★ |
| `src/styles.css` | 14 | 第 1 行是字体导入，第 2 行是 CSS 变量（设计令牌），其余行按功能区分类名 | ★★★ |
| `scripts/deploy.mjs` | 62 | 顺序执行的六段部署逻辑，配一个 `run()` 子进程封装 | ★★★ |
| `scripts/provider-keys.mjs` | 53 | `dpapi()` 加密函数 + `providerKeys(dataDir)` 工厂（save/read） | ★★★ |

**遗留文件说明**：根目录的 `app.js`（498 行）和根级 `styles.css`（247 行）是**第一代纯 JS 原型**，现版本已不再引用，但保留它们是为了数据迁移功能（详见第 11 章）——这也是本项目一段真实的“演进史”。

## 0.4 数据地图（16 张表）

数据库是一个 SQLite 文件，共 16 张表，按职责分五组（设计细节分别在第 4 章和第 8 章）：

| 分组 | 表 | 一句话用途 |
| --- | --- | --- |
| 组织与系统 | `modules` | 项目→模块→子模块三级结构 |
| | `settings` | 键值配置（格式模板等） |
| | `audit` | 操作审计流水（只增不改） |
| | `migrations` | 迁移完成标记（幂等保护） |
| 业务资产 | `cases` | 测试用例（code 唯一、编辑升版） |
| | `knowledge` | 知识条目（独立审核状态机） |
| | `regressions` | 回归清单（进度服务端计算） |
| | `reports` | 测试报告（结论 + 统计快照） |
| | `workflows` | 全链路模板（步骤序列） |
| 任务与流转 | `tasks` | 六类分析任务（三维状态） |
| | `relations` | 多态实体关联（知识引用保护靠它） |
| 模型配置 | `providers` | 大模型厂商配置（API Key 仅存掩码，第 9 章） |
| 工作流引擎 | `workbench_assets` | 7 个入口的运行配置（支持版本递增） |
| | `workflow_runs` | 每次执行的完整快照 |
| | `workflow_run_steps` | 步骤级明细（逐步执行轨迹） |
| | `validation_cases` | 固定验证案例（回归路由规则） |

> 前 12 张表在 `server.mjs` 里创建，后 4 张由 `workbench-api.mjs` 自己创建——为什么这样切分，第 8 章会讲。

## 0.5 API 地图（约 30 条路由）

所有接口都在 `/api/` 下，按域分为四组（实现细节分别在 3–5、8、9 章）：

**① 通用资源 API（第 5 章）**——8 个资源的列表、详情、创建、更新：

```
GET    /api/bootstrap               首页一次拿全：统计 counts + modules + providers
GET    /api/{resource}              列表（分页/搜索/过滤），resource 见下方 8 个
GET    /api/{resource}/:id          详情
POST   /api/tasks | cases | knowledge | reports | workflows | modules   创建
PATCH  /api/tasks | cases | knowledge | regressions | modules | providers /:id   更新
GET    /api/audit?type=&id=         某实体的操作记录
GET/PATCH /api/settings/:key        键值配置读写
```

`{resource}` 取值：`tasks` `cases` `knowledge` `regressions` `reports` `workflows` `modules` `providers`。

**② 工作流引擎 API（第 8 章）**——前缀 `/api/workbench/`：

```
GET    /api/workbench/config              7 入口配置 + 路由策略 + 安全规则
POST   /api/workbench/preflight           执行前检查（路由识别 + 缺项）
POST   /api/workbench/runs                按流程执行（核心接口）
GET    /api/workbench/runs                执行记录列表（分页/搜索/状态过滤）
GET    /api/workbench/runs/:id            执行详情（含步骤明细）
PATCH  /api/workbench/runs/:id            人工复核（approve / reject）
GET    /api/workbench/assets              入口资产管理
PATCH  /api/workbench/assets/:id          编辑入口（版本递增发布）
GET    /api/workbench/validations         验证案例列表
POST   /api/workbench/validations/:id     运行验证案例
```

**③ 模型接入 API（第 9 章）**：

```
POST   /api/providers/:id/test     探活测试（GET /models）
POST   /api/ai/analyze             统一模型调用（OpenAI 兼容 chat/completions）
```

**④ 系统与迁移（第 11 章）**：

```
POST   /api/migrate                旧版 localStorage 数据迁移（幂等）
```

## 0.6 如何阅读压缩风格源码

真实文件采用压缩风格（一行承载多个语句，单行可长达数千字符）。读之前先接受三个事实：

1. **一行就是一段逻辑**。例如 `server.mjs` 第 100 行是一条完整的“创建任务”接口——读体、校验、INSERT、审计、返回，五个动作在一行里；
2. **结构就是段落标记**。`const fn=()=>{…}`、`if(…)return …`、`for(…)` 这类关键字就是天然的段落分隔，顺着它们断句即可；
3. **IDE 格式化只看不写回**。在编辑器里用 `Alt+Shift+F`（VS Code）或 `Ctrl+Alt+L`（JetBrains）临时格式化对照学习完全可以，但不要提交格式化结果——项目刻意保持压缩风格。

**实战演练**：把 `server.mjs` 第 100 行拆开看。先自己试着按分号断句，再看下面答案：

```js
// 真实源码第 100 行（压缩版）
if(req.method==='POST'&&parts[1]==='tasks'){const d=await readBody(req),taskId=makeId('task'),ts=now();db.prepare('INSERT INTO tasks VALUES(?,?,?,?,?,?,?,?,?,?,?,?,?,?)').run(taskId,d.type,d.title,d.moduleId||null,d.risk||'P1',d.status||'草稿','未提交','未入库',d.parentId||null,json(d.input),json(d.result),d.model||'本地规则',ts,ts);audit('task',taskId,'创建',d.type);return send(res,201,mapRow('tasks',db.prepare('SELECT * FROM tasks WHERE id=?').get(taskId)));}
```

```js
// 展开版（语义完全一致）
if (req.method === 'POST' && parts[1] === 'tasks') {
  const d = await readBody(req);          // ① 读请求体
  const taskId = makeId('task');          // ② 生成主键 task_xxxxxxxx
  const ts = now();                       // ③ 当前时间 ISO 字符串
  db.prepare('INSERT INTO tasks VALUES(?,?,?,?,?,?,?,?,?,?,?,?,?,?)').run(  // ④ 插入 14 个字段
    taskId, d.type, d.title, d.moduleId || null, d.risk || 'P1',
    d.status || '草稿', '未提交', '未入库', d.parentId || null,
    json(d.input), json(d.result), d.model || '本地规则', ts, ts
  );
  audit('task', taskId, '创建', d.type);  // ⑤ 写审计流水
  return send(res, 201, mapRow('tasks',     // ⑥ 回读该行 → 转命名 → 201 返回
    db.prepare('SELECT * FROM tasks WHERE id=?').get(taskId)));
}
```

**读压缩代码的推荐顺序**：先看 `if` 条件（这是路由签名）→ 再看 `const/let` 声明（这是局部变量）→ 跳过中间看 `return`（这是响应）→ 最后回来看中间的处理动作。本教程每一章都会用这种方法把关键代码“展开”给你看。

## 0.7 遗留文件说明

你可能会注意到根目录的 `app.js` 和根级 `styles.css` 没有出现在核心地图里——它们不是垃圾文件，而是这个项目的“第一代”。

- 第一代是一个纯 JS 原型（`app.js`，498 行），数据存在浏览器 `localStorage` 里；
- 第二代（也就是现在这套代码）改成了 SQLite，但在 `src/main.tsx` 里保留了检测旧数据、引导迁移的能力；
- 所以 `app.js` 值得在学第 11 章时读一读——它是理解“数据迁移”功能的历史背景。
