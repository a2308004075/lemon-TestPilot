### 🧠 设计思路与原理

#### ① 从「我的电脑能跑」到「谁的电脑都能跑」

开发模式下能跑，不代表交付得了。把项目压缩包发给别人，对方会依次撞上六堵墙：

| 墙 | 对方的症状 | 本章的对策 |
| --- | --- | --- |
| 依赖缺失 | `Cannot find package 'react'` | 自动 `npm ci`（第 2 段流水线） |
| 构建缺失 | 生产模式报「缺少构建文件」 | 自动 `tsc + vite build`（第 3、4 段） |
| 版本不符 | `node:sqlite` 加载失败 | 启动前强制检查 Node ≥ 24（第 1 段） |
| 端口被占 | `EADDRINUSE` 一片红 | 启动前探针 + 一句人话（第 1 段） |
| 不会敲命令 | 不知道 `npm run dev` 是什么意思 | 双击脚本（10.6） |
| 出错看不到 | 双击的窗口一闪而过 | 保窗口 + 落日志（10.5、10.6） |

「一键部署」的本质不是「省几条命令」，而是**把六堵墙尽可能提前拆掉，拆不掉的在撞上时给一句人话**。

#### ② 六段流水线总览

`deploy.mjs` 的全部工作就是这张表，顺序执行、任何一段失败即整体失败：

| 段 | 代码位置 | 做什么 | 失败时的表现 |
| --- | --- | --- | --- |
| 1 环境检查 | 第 24–32 行 | Node ≥ 24、PORT 合法、`node:sqlite` 可加载、端口空闲 | 中文报错 + 退出码 1 |
| 2 依赖安装 | 第 33–36 行 | `npm ci --include=dev` | 「部署失败：npm 退出码 N」 |
| 3 类型检查 | 第 38 行 | `tsc --noEmit` | 同上（附 TS 报错详情在日志里） |
| 4 构建 | 第 39 行 | `vite build` → `dist/` | 同上 |
| 5 启动 | 第 40–41 行 | `node server.mjs --production` | 服务异常退出会冒出来 |
| 6 开浏览器 | 第 42–52 行 | 探测启动成功 → 平台命令打开 | 只提示「请手动打开」，不算部署失败 |

为什么顺序不能变：没有 Node 装不了依赖（第 2 段依赖第 1 段）；类型不过就不构建（第 2 章 `scripts.build` 立下的纪律）；没有 `dist/` 生产服务起不来（第 3 章的缺文件保护）；前面全成功，才谈得上开浏览器。

#### ③ 为什么部署脚本用 Node 写，不用 .bat / .sh？

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| Windows 批处理 | 系统自带、双击即跑 | 语法古老（`setlocal`/`errorlevel`）、写不了复杂逻辑、只能管 Windows | 只做薄壳 |
| Shell 脚本（.sh/.command） | macOS 自带 | 同上、且每个平台要重写一份 | 只做薄壳 |
| **Node 脚本** | 一份代码跑三平台；逻辑能力满配；与项目同语言 | 需要机器上已有 Node（但那是本项目的先决条件） | **承载全部逻辑** |

于是本项目的分工是：**逻辑全在 `deploy.mjs` 里，`start.bat` / `start.command` 只做「找 Node → 调脚本 → 出错保窗口」三件事**——这就是两个脚本都只有 14 行的原因。这种模式叫**薄壳（thin wrapper）**：外壳只负责「把用户带进真正的程序」，一行业务逻辑都不放。

#### ④ `npm ci`：可重现构建的代价与收益

| | `npm install` | `npm ci` |
| --- | --- | --- |
| 读取谁 | `package.json` 为主，锁文件为辅 | **锁文件为准**（`package-lock.json`） |
| 锁文件与 json 不一致 | 自动更新锁文件，继续装 | **直接报错退出**（不是警告） |
| `node_modules` | 增量修补 | 整个删除后重装 |
| 适用场景 | 日常开发（加包、试版本） | 部署、CI、一切要「可重现」的场合 |

第 2 章说 `package-lock.json`「别删」——本章给出完整理由：锁文件记录了几百个包（含间接依赖）的精确版本，`npm ci` 按它重建出一棵和你开发机**同构**的依赖树。同一个锁文件在任何机器、任何时候装出的都是同一套版本——「昨天还好好的，今天装完依赖就崩了」类事故的最大克星。代价是严格：改了 `package.json` 的依赖却没跑 `npm install` 更新锁文件，`ci` 会直接拒绝服务（10.8 验证会看到）。

#### ⑤ 双层防御：端口探针 + 服务器兜底

deploy 的端口检查用 `net.createServer()` 试听一下再立刻关闭——「先借后还」。为什么不直接查「谁占用了端口」？因为跨平台没有统一可靠的查询方式，**试听（listen 成功即空闲）是最朴素也最通用的探测**。

但探针有一个理论上的弱点：检查完到真正启动之间有个毫秒级窗口，别的进程可能刚好抢走。所以第 3 章 `server.mjs` 的 `server.on('error')`（EADDRINUSE 中文提示）依然是必需的第二层。**任何「先检查后使用」都有竞态——职业习惯是：检查为了友好，兜底为了正确。**

#### ⑥ 双击脚本的三个隐藏问题

「双击」与「终端里敲命令」是两种运行环境，差在三个地方，两个脚本的各条规定都源于此：

| 差异 | 症状 | `start.bat` 的对策 | `start.command` 的对策 |
| --- | --- | --- | --- |
| 工作目录不确定 | 相对路径全错，找不到 `scripts/deploy.mjs` | `cd /d "%~dp0"` | `cd "${0:A:h}"` |
| 不加载 shell 配置 | Homebrew 装的 node「找不到」 | Windows 无此问题 | 手动 `export PATH="/opt/homebrew/bin:/usr/local/bin:$PATH"` |
| 出错窗口瞬间关闭 | 报错根本来不及看 | 失败分支 `pause` | 失败时 `read -k 1` |

顺带认识一个逃生口：环境变量 `TESTPILOT_NO_BROWSER=1` 可禁用「自动开浏览器」（10.4 代码里的判断，10.8 验证会用到它）。

## 10.1 新建 deploy.mjs（一）：骨架与两个工具（真实 1–23 行）

在 `scripts/` 目录里新建 `deploy.mjs`（和第 9 章的 `provider-keys.mjs` 做邻居）。第一部分先写 import 段、工作目录定位、日志设施与两个工具函数：

```js
import { spawn } from 'node:child_process';
import { createServer } from 'node:net';
import { mkdirSync, createWriteStream } from 'node:fs';
import { fileURLToPath } from 'node:url';
import { join } from 'node:path';

const root = fileURLToPath(new URL('../', import.meta.url));
process.chdir(root);
mkdirSync('logs', { recursive: true });
const log = createWriteStream('logs/deploy.log', { flags: 'a' });
const port = Number(process.env.PORT || 3344);
const host = process.env.HOST || '127.0.0.1';
function say(message) { console.log(message); log.write(`${new Date().toISOString()} ${message}\n`); }
function run(command, args, options = {}) {
  return new Promise((resolve, reject) => {
    const child = spawn(command, args, { cwd: root, env: process.env, ...options });
    for (const [stream, output] of [[child.stdout, process.stdout], [child.stderr, process.stderr]]) {
      stream?.on('data', data => { output.write(data); log.write(data); });
    }
    child.once('error', reject);
    child.once('exit', code => code === 0 ? resolve() : reject(new Error(`${command} 退出码 ${code}`)));
  });
}
```

上面这段与真实文件第 1–23 行**逐字一致**。逐段读。

**① import 五件（第 1–5 行）——每个都有明确去处**：

- `spawn` 来自 `node:child_process`：本脚本要亲手拉起 npm、tsc、vite、server 四个子进程，是「子进程总调度」；
- `createServer` 来自 **`node:net`**（不是 http！）：它在这里唯一的用途是**端口探针**——第 10 行开始会看到它「试听即关」；
- `mkdirSync` / `createWriteStream` 来自 `node:fs`：日志设施用**同步 + 流**的组合（下面拆）；
- `fileURLToPath` + `join`：定位项目根目录（注意 `../`）。

**② root 的定位技巧与一行 chdir（第 7–8 行）**：

```js
const root = fileURLToPath(new URL('../', import.meta.url));
process.chdir(root);
```

- 与 `server.mjs` 第 10 行的 `new URL('.', ...)` 只差一级：**`deploy.mjs` 住在 `scripts/` 子目录里，`../` 才是项目根**。写脚本时先想清楚「我相对谁」是定位目录的第一道题；
- `process.chdir(root)` 把**进程的当前工作目录**切到项目根——之后所有相对路径（`logs/`、`server.mjs`）都从项目根算起，不管脚本是从哪被调用的。这一行是 10.6「双击脚本可以写得那么薄」的幕后功臣：工作目录修正被藏进了脚本内部；
- `chdir` 是**全局副作用**（影响整个进程），所以它只配出现在「入口脚本」里——普通模块里绝不要写。

**③ 日志设施三行（第 9–10 行）——同步建目录、追加写文件**：

```js
mkdirSync('logs', { recursive: true });
const log = createWriteStream('logs/deploy.log', { flags: 'a' });
```

- `mkdirSync` 用的是**同步**版本：必须赶在 `createWriteStream` 打开文件之前把目录准备好（异步的 `await mkdir` 在这里行不通——顶层虽然支持 await，但保持这两行「无依赖顺序感」更直观）；
- `{ flags: 'a' }` 是**追加模式**：每次部署的记录接在旧日志后面，而不是覆盖——你要的是「历史」，不是「最近一次」；
- 为什么不直接 `console.log` 完事？因为**双击场景里终端会关**（或一闪而过），文件日志是事故的唯一现场。这里的每一个设计都在回答「出错了怎么查」。

**④ port 与 host（第 11–12 行）——与 server.mjs 同源约定**：

```js
const port = Number(process.env.PORT || 3344);
const host = process.env.HOST || '127.0.0.1';
```

与 `server.mjs` 第 11–12 行**逐字同款**（回去对照一下）。`Number(... || 3344)` 的细节：环境变量是字符串，先 `Number()` 转数字再交给后面的校验（10.2 的 `Number.isInteger` 等着它）；`|| 3344` 兜底「没设置或空串」。

**⑤ say()：告示双写（第 13 行）**：

```js
function say(message) { console.log(message); log.write(`${new Date().toISOString()} ${message}\n`); }
```

一行函数，两个动作：打到终端（给正在看的人）+ 写进日志（给事后查的人）。ISO 时间戳（`2026-08-19T06:30:00.000Z`）打在每条日志行首——**日志的第一诉求永远是「什么时候出的事」**。后续每个流水线节点都会 `say` 一句话，这四句话就是没有进度条时代的进度条。

**⑥ run()：把子进程封装成 Promise（第 14–23 行）——与第 9 章 dpapi 同款的姿势**：

第 9 章 9.1 封装 `dpapi` 时预告过「第 10 章的 deploy.mjs 也会用同款姿势」——就是这个函数：`new Promise` 包住 `spawn`，把「回调式事件」翻译成 `await` 可用的线性代码。但两者重点不同：

| | `dpapi`（第 9 章） | `run`（本章） |
| --- | --- | --- |
| 通信方式 | stdin/stdout **交换数据**（边喂边收） | 只**转发输出**，不喂数据 |
| stdout/stderr | 收集到变量 | **同时写终端和日志**（第 17–19 行） |
| 成功判据 | 退出码 0 → resolve 解密结果 | 退出码 0 → resolve 空 |
| 失败信息 | 「Windows 用户密钥加密失败…」 | `` `${command} 退出码 ${code}` `` |

第 17–19 行的循环值得细看：

```js
for (const [stream, output] of [[child.stdout, process.stdout], [child.stderr, process.stderr]]) {
  stream?.on('data', data => { output.write(data); log.write(data); });
}
```

- 把「stdout→stdout、stderr→stderr」两组映射装进数组一次遍历——**同样的接线不写两遍**。`stream?.` 的可选链是防御：某些情况下（比如 spawn 失败）流的对象还不存在；
- `data` 是 Buffer，`output.write(data)` 直接透传给终端不转字符串——**保留原始字节，颜色和进度动画都不会坏**（npm/vite 的输出带 ANSI 色码）；
- `log.write(data)` 同时进文件——所以日志里会混着 npm 的安装清单和 vite 的构建表，这是有意的：**出事的现场全都在**（坑 9 会提它的副作用）；
- `child.once('exit', ...)` 用 `once` 而非 `on`：退出事件只会来一次，`once` 让「这个监听用完即弃」的语义更准确。非 0 退出 → `reject`，错误信息带上**命令名和退出码**——catch 时会拼成「部署失败：npm 退出码 1」，看的人立刻知道卡在哪一段。

> 验证点：此刻文件还不能运行（主流程没写），可以先用 `node --check scripts/deploy.mjs` 做纯语法检查——Node 的 `--check` 参数只解析不执行，是写长脚本时的「编译护栏」。

## 10.2 新建 deploy.mjs（二）：四道前置检查（真实 24–32 行）

骨架就绪，进入六段流水线的第 1 段。在文件末尾继续写（从这里开始是顶层 `try` 块，它会一直包到文末）：

```js
try {
  if (Number(process.versions.node.split('.')[0]) < 24) throw new Error('请安装 Node.js 24 LTS 或更高版本，然后重新启动。');
  if (!Number.isInteger(port) || port < 1 || port > 65535) throw new Error('PORT 必须是 1–65535 的整数。');
  await import('node:sqlite');
  await new Promise((resolve, reject) => {
    const probe = createServer();
    probe.once('error', error => reject(new Error(`端口 ${port} 无法使用：${error.code}。请关闭已有服务或设置其他 PORT。`)));
    probe.listen(port, host, () => probe.close(resolve));
  });
```

上面这段与真实文件第 24–32 行**逐字一致**。**注意这一段的「风格开关」**：deploy 是唯一没有 `handleApi` 那种函数包装的顶层脚本，从第 24 行起所有代码都直接躺在模块顶层——**ESM 的顶层 await**（第 3 章的 server.mjs 用 `await mkdir(...)` 时你已经见过一次）让「顺序执行的长脚本」不需要包 async 壳。四道检查逐个拆：

**① 检查一：Node 版本（第 25 行）**

```js
if (Number(process.versions.node.split('.')[0]) < 24) throw new Error('请安装 Node.js 24 LTS 或更高版本，然后重新启动。');
```

- `process.versions.node` 是形如 `"24.5.0"` 的字符串；`split('.')[0]` 取主版本段 `"24"`，再 `Number()` 转数字——**先转数字再比较**这一步不能省：字符串比较是字典序，`'9' > '24'` 会成立（'9' 的码点大于 '2'），这是经典的版本判断翻车点；
- 对照 `package.json` 的 `engines.node: ">=24.0.0"`（第 2 章）：`engines` 是给 npm 看的**声明**（安装依赖时最多给个警告），这里的检查是给**运行**看的**强制**——双保险，声明负责提醒，代码负责拦住；
- 为什么卡在 24？第 1 章的「六个没用」里最重要的一个——`node:sqlite`。下一道检查会说透。

**② 检查二：PORT 合法性（第 26 行）**

```js
if (!Number.isInteger(port) || port < 1 || port > 65535) throw new Error('PORT 必须是 1–65535 的整数。');
```

三个条件各挡一类坏输入：`!Number.isInteger(port)` 挡掉 `Number('abc')` 产出的 `NaN` 和小数；`< 1` 挡 0 与负数；`> 65535` 挡越界（端口号是 16 位无符号整数，65535 是上限）。**把校验做在使用的入口处**——10.8 验证 E 会亲手触发这个报错。

**③ 检查三：能力探测（第 27 行）——本书最「聪明」的一行检查**

```js
await import('node:sqlite');
```

这行代码不建库、不用它的任何 API，只是**把它加载进来**——只要不抛异常，就证明「当前这个 Node 运行时认识 `node:sqlite`」。为什么这比版本号检查更精准？因为版本号只是能力的一种**代理指标**：万一用户装的是编译时裁掉了 SQLite 的特殊构建、或某个 24.x 的早期 alpha……直接**探测能力本身**永远比探测版本号可靠。这种「动态导入当探针」的用法值得记住，写环境检查代码时一切能力探测都可以套用。

**④ 检查四：端口探针（第 28–32 行）**

```js
await new Promise((resolve, reject) => {
  const probe = createServer();
  probe.once('error', error => reject(new Error(`端口 ${port} 无法使用：${error.code}。请关闭已有服务或设置其他 PORT。`)));
  probe.listen(port, host, () => probe.close(resolve));
});
```

- `createServer()` 造了一个**没有任何 handler 的 TCP 服务器**——它不处理请求，只做一件事：试着听；
- `probe.listen(port, host)` 成功 → 回调里 **`probe.close(resolve)`**：立刻释放端口，close 完成后再把 Promise 标成成功。**「借」的时间只有一次 listen/close 的功夫**，随即还回去；
- 失败 → `error` 事件，`error.code` 是系统的错误码（端口占用就是熟悉的 `EADDRINUSE`），错误信息翻译成**带解决方案的人话**：「请关闭已有服务或设置其他 PORT」——与 README 故障处理的措辞一致。错误处理的最高境界是把「啊错了」变成「啊，你应该做 X」；
- 为什么不问操作系统「谁占着 3344」？因为 Windows、macOS、Linux 各有各的查询工具和输出格式，解析它们既脆又绕——**试听成功即空闲**是最通用的判据。

> 验证点：这段写完后可以做个快速演练——先在项目根开一个终端跑 `npm run dev` 占住 3344，再给 `deploy.mjs` 临时插一行 `console.log('检查通过')` 放在第 32 行之后，运行 `node scripts/deploy.mjs`：应立即看到「端口 3344 无法使用：EADDRINUSE…」。演练完删掉临时行、停掉 dev——完整的报错验证在 10.8。

- **为什么 Windows 要绕 `cmd.exe` 一圈**：`npm` 在 Windows 上实际是 `npm.cmd`（批处理文件），而 Node 的 `spawn` **不经过 shell**——`spawn('npm')` 找不到它，直接报 `ENOENT`。解法就是请系统命令解释器出场：`process.env.ComSpec`（系统官方环境变量，一般等于 `C:\Windows\System32\cmd.exe`）加 `/d`（跳过 AutoRun 注册表项）、`/s`、`/c`（执行完即退出）包住整条命令。这不是「多余的兼容」，而是**所有『Node 调外部命令』代码的必修课**（第 9 章 dpapi 调 `powershell.exe` 没这问题——因为它是 `.exe` 真 executable）；
- **非 Windows 直接 `spawn('npm')`**：macOS/Linux 的 `npm` 就是可执行文件，没有 `.cmd` 问题——分支两边各自的写法都是最短路径；
- **`--include=dev` 的三重含义**：① 不装开发依赖就没法构建（`tsc`、`vite` 都在 `devDependencies` 里）——这是「生产部署不装 devDependencies」旧直觉的陷阱，构建型部署必须装；② 即使环境里 `NODE_ENV=production` 也照装不误；③ **「信任来源干净环境」**——npm ci 会先校验 `package-lock.json` 与 `package.json` 的一致性，不一致直接报错（坑 2 详讲）；
- **`--no-audit --no-fund`**：跳过安全审计与赞助提示，让输出干净、速度更快。两句都是纯粹的「赶路用」开关。

**③ 第 3、4 段：类型检查与构建（第 38–39 行）**

```js

await run(process.execPath, [join(root, 'node_modules/vite/bin/vite.js'), 'build']);
```

三条「为什么这样写」：

- **为什么不用 `npx tsc` 或 `spawn('tsc')`？** 两个理由：① 和 `npm` 同款——`tsc` 在 Windows `node_modules/.bin/` 下也是 `.cmd`，`spawn` 直接找不到；② `npx` 还要先解析包位置、可能触发下载——多一层不确定性。**直接指定包内的 JS 入口文件**（`node_modules/typescript/bin/tsc`）是最「裸」的调用：不经过任何 shell、不依赖 PATH、三平台行为一致；
- **为什么用 `process.execPath` 而不是 `'node'`？** `process.execPath` 是「当前正在运行本脚本的那个 node 可执行文件的完整路径」——用它启动子进程，**保证和当前用的是同一个 Node**，完全不经过 PATH 查找。部署脚本最忌讳「探的是一回事、跑的是另一回事」；
- **与 `npm run build` 的关系**：`package.json` 里写的是 `tsc --noEmit && vite build`（第 2 章）——deploy 把它拆成**两条独立的 run**。不是多此一举：① `&&` 是 shell 语法，Node 里不存在，想复用就得再包一层 shell（那又回到 Windows 的坑）；② 拆开后每条命令的失败、输出、退出码都是独立的——`tsc` 过了但 `vite` 挂了，日志里一眼分清。顺手一个细节：`tsc` 成功时**没有任何输出**（静默即成功），所以 `--noEmit` 通过的例子里终端只闪过一行 `say`。

> 到这里，产物落在 `dist/`——`vite.config.ts` 里 `build.outDir: 'dist'`（第 2 章）与第 3 章静态服务读 `dist` 的约定，在这一刻将接上头。

## 10.5 新建 deploy.mjs（五）：信号转发与失败收尾（真实 53–62 行）

主流程最后一段 + 整个脚本的收尾。写完这一块，`deploy.mjs` 的 62 行就齐了：

```js
  for (const signal of ['SIGINT', 'SIGTERM']) process.on(signal, () => server.kill(signal));
  await new Promise((resolve, reject) => {
    server.once('error', reject);
    server.once('exit', (code, signal) => code === 0 || signal ? resolve() : reject(new Error(`服务退出码 ${code}`)));
  });
} catch (error) {
  say(`部署失败：${error.message}\n详细日志：${join(root, 'logs/deploy.log')}`);
  process.exitCode = 1;
} finally { log.end(); }
```

上面这段与真实文件第 53–62 行**逐字一致**——**deploy.mjs 全文件 62 行至此走完**。三块内容。

**① 信号转发：让 Ctrl+C 「接力」给服务（第 53 行）**

```js
for (const signal of ['SIGINT', 'SIGTERM']) process.on(signal, () => server.kill(signal));
```

- 按下 Ctrl+C 时，信号先到达的是 **deploy 进程**（它在前台），不是 server 进程。不转发会怎样？deploy 自己退出了，而 server 活着变成**孤儿进程继续占着 3344**——第二天开机你发现端口「莫名其妙被占」，凶手就是它；
- `server.kill(signal)` 把信号原样接力给子进程——deploy 与 server 有同样的「结束生命周期」，这才是正确的父子进程关系；
- **Windows 的实情要说透**：Node 在 Windows 上不支持真正的 POSIX 信号——`kill('SIGINT')` 的实际语义是「强制终止进程」。但别担心会漏掉服务：Windows 控制台下的 Ctrl+C 会发给**整个控制台进程组**，deploy 与 server 在同一个控制台里，往往同时收到；而关窗口时两者一起没。所以这段代码在 macOS/Linux 上是**精确的优雅转发**，在 Windows 上是**兜底保险**——两条路径殊途同归：**你按 Ctrl+C，服务就会停**。

**② 等待谢幕：`code === 0 || signal` 的判定细节（第 54–58 行）**

```js
await new Promise((resolve, reject) => {
  server.once('error', reject);
  server.once('exit', (code, signal) => code === 0 || signal ? resolve() : reject(new Error(`服务退出码 ${code}`)));
});
```

- 这行是整份脚本的「长眠点」——前面四段流水线跑完，deploy 挂在这里**陪着你跑服务**，直到服务结束才继续往下走。一份部署脚本的生命周期和它的服务一样长，这是「一键启动」与「构建脚本」的本质区别；
- **退出判定读法**：`code === 0`（正常退出）**或** `signal` 非空（被信号杀死——Ctrl+C 时 `code` 是 `null`、`signal` 是 `'SIGINT'`）都算「正常谢幕」，`resolve` 安静收场；其余（真正的崩溃、非 0 退出码）才 `reject`——错误的报错会造成「明明是我按的 Ctrl+C，怎么还报部署失败」的滑稽场面；
- 注意 `server.once('error', reject)`：**服务因端口被抢等原因启动失败时会走这里**（例如探针检查后、启动前那一瞬间被占用——10.2 的竞态窗口场景）——此时错误从 `server.mjs` 内部冒出来，deploy 忠实地把它转发进 catch。

**③ catch 与 finally（第 59–62 行）**

```js
} catch (error) {
  say(`部署失败：${error.message}\n详细日志：${join(root, 'logs/deploy.log')}`);
  process.exitCode = 1;
} finally { log.end(); }
```

- **catch 给的是「两段式」报错**：第一段人话（失败在哪一步、什么原因——来自各层 `reject(new Error(...))` 精心构造的消息），第二段指路（完整现场在 `logs/deploy.log`）。前面每一段埋的中文错误信息，最终都在这里与用户见面；
- `process.exitCode = 1`——第 3 章的老朋友（`server.on('error')` 用过）：**让退出码传达「失败」，但不立即终止**，保证 finally 与日志冲刷执行完，也让 `start.bat` 的 `if errorlevel 1` 能感知失败（10.6 的 pause 靠它触发）；
- `finally { log.end() }`——关闭日志文件流。虽然进程退出通常也会冲刷数据，但显式关闭让日志完整落到磁盘，也避免 Windows 上文件句柄拖延释放；
- **整份脚本的骨架**：顶层 `try / catch / finally` + 顺序 `await`——与 `server.mjs` 的 `handleApi` 是同一叙事风格：**线性、直白、顺序即流程**。全文件到此处只用了五个 `say`、两个工具函数、六段流水线——62 行。

> 验证点：`node --check scripts/deploy.mjs` 应无输出（语法通过）；但先别急着完整运行（它要装依赖、要开服务）——10.6 先补上双击脚本，10.8 再做端到端验证。

### ① start.bat——Windows 双击入口（14 行）

在项目根目录新建 `start.bat`（编码用系统默认的 ANSI/GBK 或带 BOM 的 UTF-8 均可，内容全英文所以无乱码风险）：

上面与真实文件**逐字一致**。逐行拆：

| 行 | 代码 | 作用 |
| --- | --- | --- |
| 1 | `@echo off` | 不把每条命令本身打印到屏幕（只要结果，不要过程） |
| 2 | `setlocal` | 环境变量的修改只限本窗口，不外泄到系统 |
| 3 | `cd /d "%~dp0"` | 切到**脚本所在目录**（`%~dp0` = 批处理自身目录）；`/d` 表示连盘符一起切——双击时工作目录可能是 `C:\Windows\system32`，而项目在 `D:` 盘，少了 `/d` 会「切不过去」 |
| 4 | `where node >nul 2>nul` | 静默查 PATH 里有没有 node（`>nul 2>nul` 把正常输出与错误输出都丢掉——只关心**退出码**） |

两个「为什么」：

- **为什么 node 检查的提示用英文？** 因为这台机器可能连 Node 都没装、也读不到中文环境的预期——英文是最低风险的保险。而 10.5 之后 deploy 自己的报错全部是中文（那时 Node 一定在）——**「兜底层用最通用的语言」是真实的工程取舍**（这个双语的「不一致」记在坑 8）；
- **为什么成功路径没有 pause？** 因为 deploy 成功后它不会退出——服务一直占着，窗口就是「运行中的服务 + 日志窗 + 停止按钮」。如果 deploy 退了（出错），才需要 pause 把窗口按住。**pause 只属于失败分支，这个细节值得咀嚼**：它暗示了「正常情况下这个窗口本来就不该关」。

上面与真实文件**逐字一致**。逐段拆——几乎每一行都是「zsh 方言」：

- **`#!/bin/zsh`（第 1 行）**：shebang 不只是装饰——双击 `.command` 时系统就靠它决定用哪个解释器。macOS 从 2019 年起默认 shell 就是 zsh（Catalina 起），所以直接用 zsh；里面的 `${0:A:h}` 语法（下一行）是 zsh 专属，写 `#!/bin/bash` 反而跑不起来；
- **`cd "${0:A:h}"`（第 2 行）**：zsh 的**路径修饰符**——`$0` 是脚本自身路径，`:A` 转成绝对路径，`:h` 取目录部分（head）。一行等价于「cd 到脚本所在目录」，与 start.bat 的 `%~dp0` 同义。引号不能省：路径含中文/空格时裸写会翻车；
- **`export PATH=...`（第 3 行）**：🧠 ⑥ 里说的核心问题——**双击启动的进程不读用户的 shell 配置**（`.zshrc`）。Homebrew 装的 Node 在 `/opt/homebrew/bin`（Apple 芯片）或 `/usr/local/bin`（Intel）里，不在系统默认 PATH 中——所以手动把它两补上前；
- **`command -v node`（第 4 行）**：POSIX 标准的「这个命令存在吗」查询，比 `which` 更 portable；`>/dev/null 2>&1` 丢弃输出只看退出码（与 bat 的 `>nul` 同义）；
- **`read -k 1`（第 6、12 行）**：zsh 的「读 1 个键」——任意键继续。这就是 mac 版的 pause。`"?提示文本"` 是 read 的特殊写法（提示作为参数）；
- **`result=$?`（第 10 行）**：先抢存上一条命令的退出码——因为 `if` 里的任何命令都会覆盖 `$?`；最后 `exit $result` 把退出状态原样传出去；
- **`echo` 用中文**（对比 start.bat 的英文）：macOS 终端默认 UTF-8，中文零风险，所以就用了更亲切的提示——两边语言不一致的根源就在这里（坑 8）。

> 执行权限提醒：`.command` 需要 `chmod +x` 才能真正双击运行（文件打包/解压时可能丢失执行位）——README 的故障处理里有这条指引（坑 7）。

### ③ 启动 TestPilot.command——中文名双保险（2 行）

```zsh
#!/bin/zsh
exec "${0:A:h}/start.command"
```

真文件全这两行。`exec` 是「**用新进程替换当前进程**」——不是新开一个子进程再等它，而是把这个壳直接「变身」成 start.command，**不留中间进程**。README 说「`启动 TestPilot.command` 为同一入口」——中文名只是给 Finder 里好找的双保险，逻辑零重复。

### ④ server-runtime.mjs——2 行兼容垫片（第 3 章伏笔揭晓）

```js
// Compatibility entry: use the same server and dist directory.
import './server.mjs';
```

- 它的来历在第 5 章对照表里埋过一笔（「历史上部署命令曾指向它」），真相写在 `docs/deployment-review.md`：「保留 server-runtime.mjs 兼容入口，**移除重复实现及 runtime-dist 依赖**」。历史版本里它指向一套独立的 `server-runtime.mjs + runtime-dist/` 实现（看 `.gitignore` 第 4 行：`runtime-dist/` 还在守灵）；后来项目统一到 `server.mjs + dist`，但**旧命令还活在别人的快捷方式、文档、脚本里**——删掉它，那些旧路径就会报「找不到文件」；
- 所以留下的最小垫片就两行：一行注释 + 一行 `import './server.mjs'`。**ESM 的副作用导入**——模块加载即执行（server.mjs 的顶层代码全部跑起来），不需要、也不该从它那里接什么值；
- 为什么说它是未走完的结？——它什么也不做，只是把「旧入口」映射到「新入口」。**兼容不是为了兼容本身，而是为了让「按旧文档操作的人」不掉坑**。练习 5 会让你亲手走一遍完整的「真实交付」。

### ⚠️ 要点与坑

1. **「每次启动都重装重构建」是设计取舍，不是 bug**——deploy 的承诺是「任何一台干净机器都能跑」，代价是必须有网、每次启动要等安装与构建（deployment-review.md 把它明确列为「限制」）。日常开发机用 `npm start`（依赖与产物都在）；只有交付、换机、排障才走完整 deploy；
2. **npm ci 的严格性要提前知道**——它要求 `package-lock.json` 与 `package.json` 完全同步，不同步时**直接报错退出**（不是警告、不是自动修复）。典型触发场景：改了依赖没跑过 `npm install`、或手工编辑过 package.json 的依赖段。修复：本地跑一次 `npm install` 让锁文件跟上再部署——**这个严格性是「可重现构建」的保费**，不是缺陷；
3. **Windows 上 `spawn('npm')` 必挂**——`npm` 是 `.cmd`，而 spawn 不经过 shell，报 `ENOENT`。deploy 的解法是 `cmd.exe /d /s /c` 包裹（10.3）。识别特征：报错里「找不到命令」但你在终端明明敲得通——那就是「终端有 shell、spawn 没有」的差别。第 9 章 dpapi 调 `powershell.exe` 没踩这个坑，因为它是真正的 `.exe`；
4. **端口探针有竞态窗口，「检查」与「兜底」是两层**——探针在「关闭」与「server 真正 listen」之间留一个毫秒级窗口；防御它不是把探针做复杂，而是承认不可能做完美——`server.mjs` 的 EADDRINUSE 兜底（第 3 章）永远是最后防线。**检查为了友好，兜底为了正确**；
5. **「TestPilot 已启动」这个字符串是跨文件的隐藏契约**——deploy 靠监听这行日志决定「何时开浏览器」；改 server.mjs 的启动日志文案（第 3 章第 127 行）会**静默破坏**这个功能（不报错、只是浏览器不再自动弹出）。改动日志文案前先全局搜一遍它；测试时用 `TESTPILOT_NO_BROWSER=1` 绕过。更稳的替代方案（轮询健康检查）见练习 3；
6. **双击环境 ≠ 终端环境的三个具体症状**——① 工作目录可能是 `C:\Windows\system32`（start.bat 的 `cd /d "%~dp0"` 修正）；② macOS 双击不读 `.zshrc`，Homebrew 的 node「找不到」（start.command 的 PATH 补丁修正）；③ 出错时窗口一闪而过（pause / `read -k 1` 修正）。三条规定都不是冗余，每条都对应一种真实翻车；
7. **`.command` 的执行权限会丢**——从压缩包解压、网盘下载后执行位可能消失，双击变「无法执行」。修复：`chmod +x start.command`（README 故障处理第二条）。这是 macOS 分发脚本的「必修意外」；
8. **start.bat 用英文提示、start.command 用中文——双语不一致是真实的**——原因是「node 未安装」这一路径不能假设系统读得懂中文批处理编码（ANSI 编码的 bat 里写中文可能乱码），英文最保险；而 macOS 终端默认 UTF-8 可以放心中文。不影响功能，但作为一个「一致性欠账」记录在案——精简版修复见练习 4；
9. **日志只增不减，且混着第三方输出**——`flags: 'a'` 意味着 deploy.log 永远追加、没有轮转；npm/tsc/vite 的原始输出也全量进日志——**出事时这是优点**（完整现场），长期跑则是「越来越大的文件」。按需清理或按练习 2 加轮转；
10. **两个锁文件的来历要弄清再动手**——项目里 `package-lock.json`（npm）与 `pnpm-lock.yaml` + `pnpm-workspace.yaml`（pnpm 时代遗留，`allowBuilds: core-js: false` 是 pnpm 的构建许可配置）并存。部署流水线只认前者（npm ci）。**删锁文件或换包管理器之前，先确认 deploy.mjs 在用哪个**——「不确定依赖链路的哪一环在读哪个文件」是工程事故的常见起点。

### ✍️ 练习

1. **给 deploy 加一条「快路径」**（跳过重复劳动）：新增环境变量开关——当 `TESTPILOT_FAST=1` 且 `node_modules` 与 `dist` 都已存在时，跳过第 2–4 段（安装与构建），直接启动。提示：在 `say('正在安装锁定依赖…')` 之前插一个判断；用 `existsSync(join(root,'node_modules'))` 与 `existsSync(join(root,'dist'))`（记得从 `node:fs` 补 import）。验收：第一次完整跑，第二次设 `$env:TESTPILOT_FAST='1'` 再跑——观察第二次快了多少。想一层：为什么不把快路径设为**默认**？（提示：stale dist——改了源码忘了构建，跑出的界面是旧的；「显式开关」把选择权与责任都交还使用者）；
2. **给日志加一个轻量轮转**：启动时检查 `logs/deploy.log` 大小（`statSync(...).size`），超过 1MB 就改名为 `logs/deploy-<时间戳>.log` 归档，然后重新开始写。验收：临时把阈值改成 1KB、追加几行内容后重启两次，观察到归档文件出现。思考：为什么轮转应该在「打开新日志流之前」做（回顾 10.1 的 `mkdirSync` 与 `createWriteStream` 的顺序感）；
3. **把「浏览器自动打开」从字符串耦合改成健康检查轮询**（本章最有价值的重构）：删掉「监听 stdout 找文案」的逻辑，改为一个循环：每 300ms 用 `fetch('http://127.0.0.1:${port}/')` 探一次，拿到 2xx 就打开浏览器并停止轮询（总上限 30 秒）。验收：功能不变（部署完成后浏览器自动弹出）；再把 server.mjs 第 127 行的日志文案随意改掉，确认新逻辑**不受影响**（旧逻辑此刻会失效——这就是「契约显式化」的收益）。提示：Node 24 自带全局 `fetch`；轮询放一个 `async` 函数里用 `setTimeout` 包 Promise；`TESTPILOT_NO_BROWSER` 的判断保留；注意 fetch 失败的异常要吞掉继续重试；
4. **对齐两个双击脚本**：① 把 start.bat 的英文提示改成中文（并用编辑器把文件保存为带 BOM 的 UTF-8 或 GBK，观察乱码问题——体会坑 8 里「为什么当初选英文」）；② 给两个脚本各加一句引导：检测到已存在 `node_modules` 与 `dist` 时，提示「如需跳过重复安装构建，可设置 TESTPILOT_FAST=1」（衔接练习 1）。验收：Windows 双击运行 start.bat（或命令行 `.\start.bat`）看到中文提示与引导；
5. **模拟一次「真实交付」（纯操作题）**：把项目目录打包成 zip——**排除 `node_modules`、`dist`、`logs`、`data` 四类目录**（第 2 章 .gitignore 的知识在这里派上用场），解压到一个全新目录（例如 `D:\deliver-test\`）。按 README 的流程完整走一遍：`npm run deploy`（或双击脚本）→ 从解压到浏览器出界面。记录两件事：全程耗时、中途遇到的意外（网络慢？杀毒软件开文件扫描？）。然后回到原项目目录 `npm start` 对比「热路径」的启动速度——把两组数字写进你的学习笔记，第 12 章的里程碑复盘会用到。**这一步没有代码改动，但你第一次完整站在了「使用者」的视角——本章的全部设计，从此有了体感。**
