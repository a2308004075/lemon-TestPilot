### 🎯 本章目标

一个真实项目的第一课永远是「我该用什么」。本章不讲代码，讲**决策**：

1. 学会「约束先行」的选型方法——先明确前提，再从前提推导技术；
2. 读懂 `package.json` 里的每一个依赖（运行时就 5 个）；
3. 理解六个「不使用」背后的思考，以及**什么时候应该反过来选它们**；
4. 知道版本底线（Node ≥ 24）的由来。

### 🚧 前置条件

- 读完第 0 章，对整体架构有印象；
- 不需要安装任何环境。

## 1.1 约束先行：先谈前提，再谈技术

新手最容易犯的选型错误是「看别人用什么就用什么」。正确的顺序是：**先列出这个项目的约束，再让约束替你淘汰选项**。

TestPilot 有四条不可协商的前提：

1. **个人本地工具**——单用户、单机、不需要多租户和权限体系；
2. **数据必须留在本机**——测试日志、SQL、知识库都可能涉密，不能上任何云；
3. **使用者就是开发者**——不需要考虑“给不懂技术的用户做后台配置”，但需要一键启动；
4. **十几年后还要能跑**——依赖越少，腐烂得越慢。

从这四条约束出发，直接推导出整套技术决策：

| 约束 | 推导出的决策 |
| --- | --- |
| 数据留在本机 | 不能有外部数据库服务 → 嵌入式 SQLite 单文件 |
| 个人工具、单用户 | 不需要登录/鉴权中间件 → 没有 auth 代码 |
| 单机单进程 | 前后端合并为一个进程 → 不需要反向代理、不需要 CORS 配置 |
| API 形态高度统一（REST + JSON） | 框架的中间件收益有限 → 原生 `node:http` 足够 |
| 用户要双击即用 | 部署必须脚本化、自动化 → `deploy.mjs` 六段流水线 |
| 长期可维护 | 依赖最小化 → 运行时就 5 个包 |

后面所有的“为什么不用 XXX”，答案都能回溯到这张表。

## 1.2 完整依赖清单

先看 `package.json` 全文（30 行，真实项目原样）：

```json
{
  "name": "testpilot-personal-workbench",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "scripts": {
    "dev": "node server.mjs",
    "build": "tsc --noEmit && vite build",
    "start": "node server.mjs --production",
    "check": "tsc --noEmit",
    "deploy": "node scripts/deploy.mjs"
  },
  "dependencies": {
    "jspdf": "^4.2.1",
    "lucide-react": "^1.32.0",
    "react": "^19.2.8",
    "react-dom": "^19.2.8",
    "xlsx": "^0.18.5"
  },
  "devDependencies": {
    "@types/react": "^19.2.18",
    "@types/react-dom": "^19.2.4",
    "@vitejs/plugin-react": "^6.0.5",
    "typescript": "^7.0.2",
    "vite": "^8.2.1"
  },
  "engines": {
    "node": ">=24.0.0"
  }
}
```

### 运行时依赖（5 个，全部讲清用途）

| 包 | 版本 | 解决什么问题 | 在代码里哪里用到 |
| --- | --- | --- | --- |
| `react` | ^19.2.8 | 组件化 UI 框架 | `src/main.tsx`、`src/workbench.tsx` 全部页面 |
| `react-dom` | ^19.2.8 | 把 React 渲染到浏览器 DOM | `main.tsx` 的 `createRoot(...).render(...)` |
| `lucide-react` | ^1.32.0 | 图标库（约 40 个图标） | 侧栏导航、按钮、状态图标 |
| `xlsx` | ^0.18.5 | 用例/回归导出 Excel 与 CSV | `downloadRows()`（第 7 章） |
| `jspdf` | ^4.2.1 | 测试报告导出 PDF | `downloadPdf()`（第 7 章） |

**为什么图标用库而不是手写 SVG？** 手写 40 个图标是几百行难维护的 SVG 路径；`lucide-react` 是 tree-shakable 的（打包时只包含用到的图标），代价可接受。注意它放在 `dependencies` 而不是 `devDependencies`——因为**构建产物运行在浏览器时需要它**。

### 开发依赖（5 个，只在开发/构建时用）

| 包 | 版本 | 作用 |
| --- | --- | --- |
| `typescript` | ^7.0.2 | 类型检查（`tsc --noEmit`），不产出文件 |
| `vite` | ^8.2.1 | 开发热更新 + 生产构建打包 |
| `@vitejs/plugin-react` | ^6.0.5 | 让 Vite 支持 JSX/TSX 与 React 热更新 |
| `@types/react` | ^19.2.18 | React 的类型声明（TS 需要） |
| `@types/react-dom` | ^19.2.4 | react-dom 的类型声明 |

**`dependencies` 与 `devDependencies` 的界线**：前者是“运行/打包产物需要”的；后者是“开发过程需要、运行不需要”的。判断标准一句话：**最终用户机器上还能不能用到它**。类型包（`@types/*`）永远在 dev——它们只是给编译器看的，不进入产物。

### scripts 里的 5 个入口

| 脚本 | 命令 | 用途 |
| --- | --- | --- |
| `npm run dev` | `node server.mjs` | 开发模式（内嵌 Vite 热更新） |
| `npm run check` | `tsc --noEmit` | 只做类型检查 |
| `npm run build` | `tsc --noEmit && vite build` | 类型检查 + 产出 `dist/` |
| `npm start` | `node server.mjs --production` | 生产模式启动（需先构建） |
| `npm run deploy` | `node scripts/deploy.mjs` | 一键部署（新手入口，第 10 章） |

一个反直觉的点：`dev` 不是 `vite` 命令，而是 `node server.mjs`——因为服务器**自己会以内嵌方式拉起 Vite**（第 3 章详解）。这样"一个命令、一个端口"就能同时跑前后端。

## 1.3 六个「不使用」的决策记录

每个决策记录四件事：候选方案 → 它能带来什么 → 为什么放弃 → **什么时候应该反过来选它**（最后一条最重要，选型没有绝对对错，只有适不适合）。

### 决策一：不用 Express / Koa，用原生 `node:http`

- 候选收益：Express 提供现成的路由分组、中间件、body 解析；
- 放弃原因：本项目 API 形态高度统一（REST + JSON + 通用资源层），框架的收益有限；且**学习价值高**——你会亲手实现路由分发、请求体读取、异常兜底，这些概念在任何框架里通用；
- 代价（要有数）：需要自己处理读请求体、404 兜底、异常捕获（第 3 章完整实现）；
- 何时反过来选：接口形态开始多样化（文件上传、WebSocket、复杂中间件链）时，框架的收益会反超成本。

### 决策二：不用 ORM，用 `node:sqlite` + 手写 SQL

- 候选方案：Prisma / Drizzle / Sequelize 等；
- 放弃原因：ORM 的价值在“多数据库适配 + 团队统一查询风格”，本项目只有一个数据库、一个人维护；且 `node:sqlite` 是 Node 24 **内置模块**，零安装（`sqlite3` 这类原生模块的编译问题常是新手噩梦）；
- 代价：SQL 要自己写、字段分布要自己维护（项目用“JSON 列 + 命名转换层”缓解，第 4 章）；
- 何时反过来选：数据模型复杂到需要频繁 join、迁移管理复杂、多人协作时。

### 决策三：不用前端路由库，用一个 `useState`

- 候选方案：react-router / wouter 等；
- 放弃原因：桌面式工具的页面切换不需要 URL 可分享、可刷新保持；一个 `useState<PageKey>` 就完成了全部“路由”功能；
- 代价：浏览器刷新会回到首页；无法用 URL 直达某个页面；
- 何时反过来选：当你想分享“执行记录详情链接”、或者页面层级变深时（第 12 章的扩展方向里就列了这条）。

### 决策四：不用状态管理库，用 `bootstrap` + props

- 候选方案：Redux / Zustand / Jotai；
- 放弃原因：全局需要共享的状态其实只有一份 `bootstrap`（模块列表、统计、模型配置），用 props 逐层传递完全可控；
- 代价：`props` 在组件树里要显式传递（本项目统一用 `const props = {...}` 展开传递，第 6 章）；
- 何时反过来选：出现跨层级、跨页面的高频共享状态（如实时协作）时。

### 决策五：不用 UI 组件库，自写基础样式

- 候选方案：Ant Design / MUI / shadcn 等；
- 放弃原因：组件库带来主题定制成本与体积负担；本项目的界面重复模式很强（列表/面板/抽屉），自写 14 行压缩样式的类名体系（panel/badge/table/drawer）反而完全可控；
- 代价：需要自己处理细节状态（按钮 loading、禁用态、响应式断点）；
- 何时反过来选：团队协作需要统一视觉规范、或表单场景复杂到需要现成校验组件时。

### 决策六：不用 CSS 框架，用「设计令牌 + 语义类名」

- 候选方案：Tailwind / UnoCSS；
- 放弃原因：项目样式是“全局语义化”（`.panel` `.drawer` `.badge.red`），CSS 变量集中管理颜色/圆角；压缩风格下也没有类名爆炸问题；
- 何时反过来选：组件数量继续增长、出现样式覆盖冲突时。

> 六条决策的共同逻辑：**这个项目里，“少一个依赖”的长期收益 > “少写一点代码”的短期便利**。但这不是教条——每条都写明了反向条件。

## 1.4 版本底线的由来

### Node ≥ 24

`engines` 字段声明了底线，部署脚本也会**真的检查**（`scripts/deploy.mjs` 第 25 行）：

```js
if (Number(process.versions.node.split('.')[0]) < 24)
  throw new Error('请安装 Node.js 24 LTS 或更高版本，然后重新启动。');
```

为什么是 24？因为本项目的数据库层用了 `node:sqlite`——这是 Node 较新内置的 SQLite 模块，**不需要 `npm install` 任何东西**就能 `import { DatabaseSync } from 'node:sqlite'`。用旧版本 Node 会在启动瞬间失败，所以选型时就把底线定在 24，并在部署脚本里做“能力探测”：

```js
await import('node:sqlite');   // 老版本 Node 会直接在这里抛错
```

这种「用一次 import 探测运行环境能力」的写法值得记住——它让“环境不满足”在部署第一步就被拦下，而不是运行到一半才崩。

### 其余版本

React 19、TypeScript 7、Vite 8 都是当前主版本线。个人项目的升级成本低，可以直接跟进新版本；`^` 前缀（如 `^19.2.8`）表示接受同主版本内的升级（19.x.x），真正的精确版本锁定由 `package-lock.json` 负责（`npm ci` 严格按它安装，第 10 章）。

## 1.5 部署形态决策：为什么没有 Docker 和 CI/CD

| 候选 | 放弃原因 | 本项目的方案 |
| --- | --- | --- |
| Docker | 目标用户是个人，装 Docker 本身就是门槛 | 双击 `start.bat` / `start.command` |
| CI/CD（GitHub Actions 等） | 单人开发、无发布流程 | `npm run deploy` 本地流水线 |
| Nginx 反向代理 | 前后端同进程同端口，没有代理需求 | `server.mjs` 一个进程全包 |
| PM2 等进程守护 | 个人桌面工具，用户关窗口即停 | 前台运行 + `logs/deploy.log` |

产出形态：**`dist/`（前端构建产物）+ `server.mjs`（后端）由同一个进程同时服务**。这就是“单进程部署”的全部含义。

### 🔍 对照真实项目

- `package.json` 全文（30 行）——本章 1.2 节即全文；
- `scripts/deploy.mjs` 第 25–27 行——版本检查与能力探测（`node:sqlite`、`PORT` 合法性）；
- 提醒：真实项目的依赖版本号会随时间变化，**以你打开文件时看到的为准**，本章的解读逻辑不变。

### ⚠️ 要点与坑

- **“依赖最小化”不是“拒绝一切库”**：三条判断标准——① 能否用平台内置能力（`node:sqlite` vs `sqlite3`）；② 长期收益是否大于升级维护成本；③ 是否真的不可替代（PDF 导出这种复杂格式，用 `jspdf` 是明智的）；
- **不要删除 `package-lock.json`**：它锁定整棵依赖树的精确版本，是“换台机器装出来一模一样”的保证；
- **`private: true` 别漏**：防止误发布到 npm；
- **`"type": "module"` 一旦开启**，所有 `.js/.mjs` 都用 ES Module（`import/export`），老教程里的 `require` 写法不能用。

### ✍️ 练习

1. 假设产品经理提出新需求「测试报告要支持导出 Word」——请按本章的选型方法给出你的决策记录：候选方案（docx 库 / 手写 XML / 后端生成）、各自收益与代价、你会选哪个、反向条件是什么；
2. 打开 `package-lock.json`（不用通读），搜索 `"node_modules/react"`，找到 React 实际锁定的精确版本号，对比 `package.json` 里的 `^19.2.8`，理解“范围声明”与“精确锁定”的关系。
