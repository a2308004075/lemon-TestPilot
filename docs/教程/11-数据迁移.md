### 🧠 设计思路与原理

#### ① 一代与二代：为什么必须搬一次家

第一代 `app.js` 选择 localStorage 在当时是合理的：个人工具、单人使用、零后端——localStorage 是最省事的方案。但它撞上了五个天花板：

| 天花板 | 具体表现 |
| --- | --- |
| 容量 | localStorage 通常约 5MB，且**同步写入**——数据略大就卡顿，甚至写失败 |
| 绑定浏览器 | 数据属于「这台电脑的这个浏览器」；换浏览器、清缓存、换电脑 = 数据消失 |
| 没有查询 | 搜索是 JS 数组 `filter` 全量过滤（`app.js` 里就是这么干的）——没有索引、没有真分页 |
| 没有并发控制 | 整个 `state` 一次 `JSON.stringify` 覆盖保存（`save()`）——多标签页同时操作会互相覆盖 |
| 没有结构约束与审计 | 没有外键、没有状态机校验、没有操作记录；「能存进去」就算数 |

还有第六个、恰好也是最致命的一个：**服务端读不到**。第 8 章的 AI 工作流、第 9 章的知识检索都在服务端跑——放在浏览器里的数据，服务端一行也看不见。所以第二代把家搬进 SQLite，不是「更高级」，而是「引擎需要」。

这次搬家在数据工程里叫**数据迁移（data migration）**：把数据从旧结构翻译到新结构，且保证——不丢、不重、可追溯。

#### ② 三条铁律

本项目把迁移的要求浓缩成三条。逐条看「为什么」：

**铁律一：备份先行。** 迁移是**破坏性操作**——它读旧数据、写新表，一旦中途出错，没有备份就没有退路。所以代码里的顺序永远是：先把旧数据**原样**写盘（`data/backups/`），再动数据库。注意「原样」二字：备份是**证据快照**，不做任何清洗和转换——将来人工恢复时，你需要的是一份「事情发生前的世界」。

**铁律二：幂等。** 幂等（idempotent）指「同一操作执行一次和执行 N 次，效果相同」。迁移为什么必须幂等？三个现实场景：用户手滑连点两次按钮；请求发出后响应丢失、客户端重试；用户在多个浏览器里都有一份旧数据，先后触发迁移。`migrations` 表就是幂等的「凭据」：迁移成功后在表里留下一条记录，之后任何人再提交，都会被直接挡回。

**铁律三：逐条去重。** 只靠「凭据」还不够——如果凭据失效（手工清库、部分失败重试），批量导入本身还得自带防重。所以每条记录导入前先 `SELECT 1` 查主键：已存在就跳过。条目级幂等让「整批迁移」变成「一批可重放的幂等操作」。

#### ③ 两端分工与迁移协议

迁移是**双端协作**：浏览器负责「知道你手里有旧数据」，服务端负责「搬」。分工的理由：

| 环节 | 放在哪 | 为什么 |
| --- | --- | --- |
| 检测旧数据 | 前端 | localStorage 只存在于浏览器（服务端根本读不到） |
| 询问用户 | 前端 | 需要把「检测到 N 个任务和 M 条知识」摆给用户看，再让他决定 |
| 备份写盘 | 服务端 | 浏览器写不了 `data/backups/` |
| 导入与登记 | 服务端 | 数据必须经 API 进库；幂等与审计由服务端统一负责 |

于是协议就是一条路由——`POST /api/migrate`：

| 项 | 内容 |
| --- | --- |
| 请求体 | 旧版 localStorage 里的**整个 state**（原样 JSON，不做预加工） |
| 响应（首次成功） | `{"migrated":true,"imported":{"tasks":N,"knowledge":M},"backupPath":"…"}` |
| 响应（已迁移过） | `{"migrated":false,"reason":"already-migrated","backupPath":"上次的备份路径"}` |
| 失败 | 500 + `{error}`（前端 toast 提示「迁移失败：…」，旧数据保留） |

「已迁移过」用 **200** 返回、而不是 409 之类的错误码——这不是失败，是另一种正常结局：请求没错、数据没错，只是「早就做过了」。

#### ④ 没有事务的迁移：可恢复比原子更重要

你可能会想：批量导入用数据库事务一把梭（要么全成、要么全回滚）不是更稳吗？本项目**故意没用事务**，靠的是另一套设计：

| | 事务版 | 本项目版 |
| --- | --- | --- |
| 中间失败 | 全部回滚，下次从零重来 | 已导入的**留在库里**，下次逐条跳过 |
| 完成标记 | 事务外单独记 | `migrations` 登记放在**最后一行**——没登记就是没完成 |
| 重试代价 | 全部重做 | 只补差集——**每重试一次就更接近完成** |
| 结果 | 原子的 | **收敛的** |

「收敛」是这个设计的灵魂：无论中途在哪一步崩溃，重新执行同一批数据，最终都会到达同一个终点。崩溃只会让进度**停滞**，不会让数据**损坏**（每条 INSERT 独立提交，主键 + 逐条去重保证不重不漏）。对「一次性、小规模、可重跑」的迁移来说，可恢复性比原子性更实用——第 7 章预告里说的「导入事务」，最终演化的形态就是它。

#### ⑤ 四层防御

「不重」这件事，本项目叠了四层防线，从外到内：

| 层 | 位置 | 防的场景 |
| --- | --- | --- |
| 1 前端清空 | 迁移成功后 `removeItem` | 正常人：点过一次，弹窗永不再出 |
| 2 整批幂等 | `migrations` 表检查 | 重复提交：第二个请求直接挡回 |
| 3 条目去重 | 每条导入前 `SELECT 1` | 凭据失效（手工清表、部分失败重试）：增量跳过 |
| 4 主键约束 | 数据库 `PRIMARY KEY` | 万分之一：前三层全漏，撞主键报错也不产生脏数据 |

前三层是「体验」，最后一层是「正确性」——**检查为了友好，约束为了正确**（第 10 章端口探针的同款哲学）。

#### ⑥ 取舍哲学：不迁比迁错好

迁移的诱惑是「把一切都搬过来」，但新旧两代的数据结构并不是一一对应。本项目对「对不齐」的字段采取同一个态度：**宁可留空（或留在备份里），不伪造映射**：

| 旧数据 | 处理 | 理由 |
| --- | --- | --- |
| 任务的 `module`（自由文本如「支付 / MQ」） | 丢弃（`module_id` 置 `null`） | 新版是三级模块表的外键，文本与 id 无对应关系——猜一个等于制造脏数据 |
| 任务的 `risk`（旧版根本没存这个字段） | 统一 `'P1'` | 给中间值 + 备份里可查原貌，比瞎猜 P0/P2 诚实 |
| 旧版 `schemas` / `bindings` / `reports` / `workflows` | 不迁移 | 结构差异大（如报告从纯文本变结构化 JSON）或价值低（模板重建便宜）；**旧数据连同这些字段完整躺在备份 JSON 里**，哪天要用可人工取 |
| `workflows`（链路模板，结构其实接近） | 未迁（但值得做） | 本章练习 2 的题目 |

对比「全都迁」的诱惑：给 module 硬塞一个默认模块、给报告编一套数据结构——迁完库里全是半真半假的记录，比少迁几条糟糕得多。**迁移的目标是「可用且可信」，不是「数量对得上」。**

## 11.1 后端：migrate 路由全量展开（真实 114 行）

第 5 章说 `handleApi` 是「一行一路由」的平铺结构——但第 114 行这一条，是整个文件里最长的一行：它一段顶别人五条。密集却不乱，因为它是一段**顺序脚本**：从上往下读一遍，就是迁移的全部逻辑。先看格式化后的全貌（与真实文件第 114 行**逐字一致**；为便于阅读做了换行缩进，并添加了 `// —— 第 N 段 ——` 的分段注释，去掉注释即为原文的压缩形态）：

```js
if (req.method === 'POST' && parts[1] === 'migrate') {
  // —— 第 ① 段：读请求体 + 幂等检查 ——
  const d = await readBody(req),
        old = db.prepare('SELECT * FROM migrations WHERE key=?').get('localstorage-v1');
  if (old) return send(res, 200, { migrated: false, reason: 'already-migrated', backupPath: old.backup_path });
  // —— 第 ② 段：备份先行 ——
  const backupPath = join(dataDir, 'backups', `localstorage-${Date.now()}.json`);
  await writeFile(backupPath, JSON.stringify(d, null, 2), { flag: 'wx' });
  // —— 第 ③ 段：导入任务 ——
  const imported = { tasks: 0, knowledge: 0 };
  for (const item of d.tasks || []) {
    const tid = item.id || makeId('legacy_task');
    if (db.prepare('SELECT 1 FROM tasks WHERE id=?').get(tid)) continue;
    db.prepare('INSERT INTO tasks VALUES(?,?,?,?,?,?,?,?,?,?,?,?,?,?)').run(
      tid, item.type || 'bug', item.title || '旧版任务', null, 'P1', item.status || '已完成',
      '未提交', '未入库', null, json(item.input || {}), json(item.result || {}),
      '旧版规则', item.createdAt || now(), now()
    );
    imported.tasks++;
  }
  // —— 第 ④ 段：导入知识 ——
  for (const item of d.knowledge || []) {
    const kid = item.id || makeId('legacy_kb');
    if (db.prepare('SELECT 1 FROM knowledge WHERE id=?').get(kid)) continue;
    db.prepare('INSERT INTO knowledge VALUES(?,?,?,?,?,?,?,?,?,?,?,?)').run(
      kid, item.title || '旧版知识', item.category || '业务规则库', null, item.risk || 'P1',
      item.status || '待审核', 1, item.content || '', null, '从旧版迁移',
      item.updatedAt || now(), now()
    );
    imported.knowledge++;
  }
  // —— 第 ⑤ 段：登记与审计 ——
  db.prepare('INSERT INTO migrations VALUES(?,?,?)').run('localstorage-v1', now(), backupPath);
  audit('migration', 'localstorage-v1', '完成', json(imported));
  // —— 第 ⑥ 段：响应 ——
  return send(res, 200, { migrated: true, imported, backupPath });
}
```

先建立两个全局印象，再逐段深挖。

**印象一：这一段没有新概念。** 数一数它用到的全部工具——`readBody`（第 5 章）、`send`、`now`、`makeId`、`json`（第 4 章）、`db.prepare` 的查/插（第 4、5 章）、`audit`（第 5 章）、`join` / `dataDir`（第 3、4 章）、`writeFile`（node:fs/promises，第 2 章就 import 了）、`migrations` 表与 `backups` 目录（第 4 章建好）。**没有一件是新东西**——迁移的难度不在 API，而在「用已有积木搭出正确的顺序」。

**印象二：它和第 5 章所有写路由的「气质」不同。** 对比这张表：

| | 普通写路由（第 5 章） | migrate 路由 |
| --- | --- | --- |
| 输入 | 单条记录 | **一整批**（旧版整个 state） |
| 校验 | 「先查、再并、后写」，缺啥 404 | **宽进**：字段缺失一律 `||` 兜底，不报错 |
| 幂等 | 无需考虑（每次创建都是新记录） | **核心主题**（四层防御都在这） |
| 副作用 | 写 1 张表 + 1 条审计 | 写 2 张表 + 1 个磁盘文件 + 1 条审计 |
| 完成标记 | 无 | `migrations` 登记（「做过」本身要留痕） |

为什么这么「宽」？因为迁移的对象是**历史数据**——它们长什么样不由你决定，而由两年前的代码决定。对历史数据严苛校验只会频繁卡壳；宽容 + 兜底 + 备份，才是对历史数据的正确姿势（唯一的例外是坏条目会抛异常，见「要点与坑」第 4 条）。

### 第 ① 段 · 幂等检查：最先执行、零副作用

```js
const d = await readBody(req),
      old = db.prepare('SELECT * FROM migrations WHERE key=?').get('localstorage-v1');
if (old) return send(res, 200, { migrated: false, reason: 'already-migrated', backupPath: old.backup_path });
```

- `readBody`（第 5 章的老朋友）把请求体读成 JSON 对象 `d`——注意 `d` 就是**旧版整个 state**（连不迁移的 `schemas`、`bindings` 都一起收下），路由对请求体不做任何预加工，原样接收；
- 一行 `const` 声明两个变量（逗号式），`d` 与 `old` 是「读体的两个产物」；
- `db.prepare('SELECT * FROM migrations WHERE key=?').get('localstorage-v1')`——查迁移登记表，`get` 的语义是「返回第一行，或 `undefined`」；
- 注意 `'localstorage-v1'` 是**直接写在代码里的字符串**——它是本路由的「迁移协议名」。为什么带 `-v1` 后缀？将来若第一代还有续作，可以并存登记 `'localstorage-v2'`……**主键即版本**：第 4 章那句「主键就是迁移名」的完整含义在这里落地——登记表天生支持多版本迁移，不需要改表结构；
- `if (old)` 命中即返回：**200 + `migrated:false` + `reason` + `backupPath`**，三个字段各有用处：`migrated:false` 给前端判断（决定 toast 文案）、`reason` 给机器与日志（`'already-migrated'` 是稳定枚举）、`backupPath: old.backup_path` **把上次的备份路径捎回去**——「你的数据备份在哪」永远有答案（本机工具的人情味细节）；
- 最关键的一个设计：**幂等检查放在第一行**。任何「已迁移」的重复请求都是**零副作用**的——不写备份、不碰数据库、不打审计。检查越早，重复请求的代价越小。

### 第 ② 段 · 备份先行：写盘的两行心事

```js
const backupPath = join(dataDir, 'backups', `localstorage-${Date.now()}.json`);
await writeFile(backupPath, JSON.stringify(d, null, 2), { flag: 'wx' });
```

- `dataDir` 是第 4 章的常量（`<root>/data`）；`backups` 子目录在启动时由 `await mkdir(join(dataDir, 'backups'), { recursive: true })` 备好——**第 4 章那行 mkdir 的存在意义，在这里兑现**：写备份时不用再判断目录是否存在；
- 文件名 `localstorage-<毫秒时间戳>.json`：时间戳让每次迁移的备份**天然不重名**，也是日后翻档案的排序依据；
- `JSON.stringify(d, null, 2)` 的第三个参数 **2 是缩进空格数**。对比数据库里的 `json()`（紧凑无空格）：**备份是给人读的，库里的 JSON 是给机器读的**——稍后 11.5 打开备份文件你会看到漂亮的多行结构，「手工恢复」时它才是救命稻草；
- 本段最重的细节是第三个参数 `{ flag: 'wx' }`，值得一张表：

| flag | 含义 | 用在备份上的后果 |
| --- | --- | --- |
| `'w'`（默认） | 打开写入，**文件已存在则清空覆盖** | 危险：一旦同名，上一份备份被静默抹掉 |
| `'wx'` | **排他**创建：文件已存在则报错 | 「绝不覆盖任何已有备份」——备份文件的铁律 |

  `'wx'` 是「备份只增不改」这条规矩在函数参数级别的表达。代价是极小概率撞名时报 EEXIST → 500 → 重试一次就好；而即便撞名真的发生，损失也只是「这一次失败」，绝不会是「历史备份被覆盖」——**代价的方向选对了**；
- `await` 的位置也是内容：这一行必须**完成**，才轮到下一段。如果写盘失败（磁盘满、权限错），整个请求 500、数据库一个字都没写、退路完好——「备份先行」是字面上的先后顺序。

### 第 ③ 段 · 导入任务：十四列逐个对齐

```js
const imported = { tasks: 0, knowledge: 0 };
for (const item of d.tasks || []) {
  const tid = item.id || makeId('legacy_task');
  if (db.prepare('SELECT 1 FROM tasks WHERE id=?').get(tid)) continue;
  db.prepare('INSERT INTO tasks VALUES(?,?,?,?,?,?,?,?,?,?,?,?,?,?)').run(
    tid, item.type || 'bug', item.title || '旧版任务', null, 'P1', item.status || '已完成',
    '未提交', '未入库', null, json(item.input || {}), json(item.result || {}),
    '旧版规则', item.createdAt || now(), now()
  );
  imported.tasks++;
}
```

逐点拆：

- `d.tasks || []`——「宽进」第一处：没有 `tasks` 字段 = 空数组 = 无事可做，而不是报错；
- `const tid = item.id || makeId('legacy_task')`——**保留旧 id** 是整段的设计核心：id 是逐条去重的钥匙（下一行查的就是它）。旧版任务都有 `crypto.randomUUID()` 生成的 id（`app.js` 的 `runCurrentTask`），所以 `makeId` 这一支极少走到——只有数据被手工编辑、丢了 id 时才兜底生成，`legacy_` 前缀让「迁移兜底生成」一眼可识别；
- `if (db.prepare('SELECT 1 FROM tasks WHERE id=?').get(tid)) continue;`——条目级去重。`SELECT 1` 是**最小化查询**（不取任何列，只问「在不在」）；`continue` 而不是报错——已存在 = 已经搬过 = 跳过。**「跳过垃圾，而不是撞上垃圾」**是批量导入的正确姿势；
- 14 个值逐列对齐第 4 章的 `tasks` 表（14 列），完整对照如下——这张表也是 11.4 的「预告版」：

| 列 | 值 | 说明 |
| --- | --- | --- |
| `id` | `tid` | 旧 id 或 `legacy_` 兜底 id |
| `type` | `item.type \|\| 'bug'` | 六类任务的词表两代一致 |
| `title` | `item.title \|\| '旧版任务'` | 兜底文案 |
| `module_id` | **`null`** | 旧版 module 是自由文本，不伪造映射（⑥ 的哲学） |
| `risk` | **`'P1'`** | 旧版没存这个字段，给中间值 |
| `status` | `item.status \|\| '已完成'` | 旧词表原样带入（如「待复核」） |
| `review_status` | `'未提交'` | 状态机初值，与第 5 章 POST /tasks 一致 |
| `knowledge_status` | `'未入库'` | 同上 |
| `parent_id` | `null` | 旧版没有父子任务结构 |
| `input_json` | `json(item.input \|\| {})` | `\|\| {}` 兜住无 input 的旧任务（11.3 细说） |
| `result_json` | `json(item.result \|\| {})` | 同上 |
| `model` | **`'旧版规则'`** | 来源标记：第一代没有大模型，分析全靠本地规则 |
| `created_at` | `item.createdAt \|\| now()` | 旧时间尽量保留 |
| `updated_at` | `now()` | 刚被迁移 = 刚被改动 |

- `imported.tasks++` 放在 `INSERT` 之后、循环体内——只统计**真正插入**的条数（`continue` 跳过的不算）。响应里报出的数字因此是诚实的「本次搬了多少」。

### 第 ④ 段 · 导入知识：同构循环的三处差异

```js
for (const item of d.knowledge || []) {
  const kid = item.id || makeId('legacy_kb');
  if (db.prepare('SELECT 1 FROM knowledge WHERE id=?').get(kid)) continue;
  db.prepare('INSERT INTO knowledge VALUES(?,?,?,?,?,?,?,?,?,?,?,?)').run(
    kid, item.title || '旧版知识', item.category || '业务规则库', null, item.risk || 'P1',
    item.status || '待审核', 1, item.content || '', null, '从旧版迁移',
    item.updatedAt || now(), now()
  );
  imported.knowledge++;
}
```

与第 ③ 段同构（去重、计数、兜底的结构一模一样），只讲三处差异：

- `version` 固定填 **`1`**——旧版没有版本概念，所有迁移知识从 v1 起步；之后每次编辑由第 5 章的 `version=version+1` 自动升版，「从旧版迁移 v1、后来又改过两版」的演化史就完整了；
- `review_note` 填 **`'从旧版迁移'`**——知识表的「审核/来源说明」字段。第 7 章的详情抽屉「审核信息」区会原样显示它——日后审查一条老知识时，一眼知道它的来历；
- 时间字段的**错位映射**：`created_at = item.updatedAt || now()`——旧知识只有「更新时间」这一个时间维度，它最能代表「这条知识的年代」，于是让它顶到新版的 `created_at`；而 `updated_at` 用 `now()`。这一手「时间双轨」的完整讨论放在 11.4；
- 另外两个空位：`module_id` 置 `null`（同任务），`source_task_id` 置 `null`（旧版知识没有「来源任务」关联）。

### 第 ⑤ 段 · 登记与审计：最后一步的双重留痕

```js
db.prepare('INSERT INTO migrations VALUES(?,?,?)').run('localstorage-v1', now(), backupPath);
audit('migration', 'localstorage-v1', '完成', json(imported));
```

- **登记在最后**：这是 ④ 节「收敛设计」的落点——前面任何一步抛错，这两行都不会执行，`migrations` 里就不会留下「已完成」——下次重跑仍然放行整批，已插入的条目被逐条跳过，直到真正走完全程；
- 登记三列全部对上第 4 章的表结构：`key`（协议名）、`completed_at`（完成时间）、`backup_path`（证据位置）——第 4 章那句「记录完成时间与备份路径」，现在每个字都有了实指；
- `audit('migration', 'localstorage-v1', '完成', json(imported))`——**复用第 5 章的审计系统**（`audit()` 函数）：`entity_type='migration'`、`entity_id='localstorage-v1'`、`action='完成'`、`detail=imported` 的 JSON——审计详情自带「战报」（搬了多少条）。一条 `GET /api/audit?type=migration&id=localstorage-v1` 就能查到这次历史瞬间（11.5 验证 G 亲手查）；
- 顺带回答一个问题：为什么不给每条迁移记录各写一条审计？——**审计的粒度是「操作」，不是「行」**：一次迁移是一次操作，一条审计足够，控制流水表体量的同时信息也完整。

### 第 ⑥ 段 · 响应：接口给全信息，界面挑着用

```js
return send(res, 200, { migrated: true, imported, backupPath });
```

- 三个字段：`migrated:true`（前端据此选择成功文案）、`imported`（明细）、`backupPath`（位置）；
- 有意思的是前端**实际只消费了 `imported`**（拼总数做 toast）——`backupPath` 界面上没展示。这是有意留的：「接口给全信息，界面挑着用」。未来加一个「查看备份位置」的界面、或 curl / 脚本直接调用，都不用改后端。这与第 5 章「回读再返回」是同款思路——**返回完整事实，而不是刚好够用的最小集**；
- 200 而不是 201：迁移不是「创建了一份资源」，而是「执行了一次操作」——状态码选 200 比 201 更贴切。

### 六段合读：三条并行的线

回读一遍这六段，你会发现同一段顺序同时讲了三件事：

1. **数据流**：请求 → 备份 → 任务 → 知识 → 登记 → 响应——一次搬家的物理路径；
2. **防御流**：整批幂等 → 备份 → 条目去重 → 主键兜底——四层防线按「从便宜到昂贵」依次展开（先查表最便宜，写盘次之，插入最贵）；
3. **失败流**：任何一步抛错 → 被第 5 章 `handleApi` 的统一 `try/catch` 接住 → 500 → 前端 toast「迁移失败：…」→ 旧数据仍在浏览器、可随时重试。

三线平行不交叉，就是这段「最长一行」真正好读的原因——**平铺的顺序脚本，是复杂批处理最好的结构**。

> 验证点：此刻对 `server.mjs` 跑一次 `node --check server.mjs`，应无输出（语法通过）。完整的端到端验证放在 11.5——那需要先准备一份「旧数据」。

## 11.2 前端闭环：清空永远在确认之后

第 6 章逐字讲过 `migrate` state（第 49 行）与检测 `useEffect`（第 51 行），第 7 章 7.14.2 逐字讲过 `MigrationModal` 的界面（第 159 行）。那些是「零件」，本节把零件拼成一条完整时序——**闭环**。先看一次真实迁移的全流程：

| 步骤 | 谁 | 做什么 | 代码位置 |
| --- | --- | --- | --- |
| 1 检测 | `App` 挂载时的 effect | 读 `localStorage.getItem(...)`，有数据就 `setMigrate(JSON.parse(raw))` | 第 51 行 |
| 2 弹窗 | 条件渲染 | `migrate` 非空 → `<MigrationModal>` 出现 | 第 72 行 |
| 3 提交 | 用户点「备份并迁移到 SQLite」 | `migrate()` 内 `API.post('migrate', data)` | 第 159 行 |
| 4 确认 | 服务端 | 六段流水线（11.1）→ 200 响应 | 第 114 行 |
| 5 清空 | `done()` 回调 | 删 localStorage、关弹窗、刷统计 | 第 72 行 |

第 3 步送出的 `data` 就是第 1 步 `JSON.parse` 的结果——**整个旧 state 原样上送**：前端不加工，服务端不追问，备份落盘的就是这份原貌。

### done 回调：三件事，一个顺序

```js
// 第 72 行（节选）
done={()=>{localStorage.removeItem('testpilot-personal-workbench-v1');setMigrate(null);refresh();}}
```

三件事各司其职，顺序也是设计的一部分：

- **`removeItem` 第一**：数据已进库（服务端已确认），旧副本使命结束。这是「四层防御」的第 1 层——正常人点过一次，弹窗永不再出；
- **`setMigrate(null)` 第二**：关闭弹窗；
- **`refresh()` 最后**：重拉 `/api/bootstrap`，让侧栏计数与「数据资产」卡片立刻反映新数据——**迁移的结果必须看得见**。否则界面停在旧统计上，用户会怀疑「到底搬没搬」。

### migrate() 的三个分支

```js
// 第 159 行（节选，为阅读换行；`tasks+` 后的空格为原文如此，无功能影响）
async function migrate() {
  try {
    const r = await API.post('migrate', data);
    notify(r.migrated ? `已迁移 ${r.imported.tasks+ r.imported.knowledge} 条旧数据` : '旧数据已经迁移过');
    done();
  } catch (e) { notify(`迁移失败：${e.message}`); }
}
```

| 分支 | 条件 | 界面 | 数据 |
| --- | --- | --- | --- |
| 成功 | `r.migrated === true` | toast「已迁移 N 条旧数据」（两类相加） | `done()`：清空 + 关窗 + 刷新 |
| 已迁移过 | `r.migrated === false` | toast「旧数据已经迁移过」 | 也走 `done()`（见下） |
| 失败 | 请求抛错（网络 / 500） | toast「迁移失败：…」 | **什么都不做**——旧数据原样保留 |

三个要点：

1. **失败分支「什么都不做」是本章最重要的前端设计**：不清空、不关窗、旧数据一个字节不动——`done()` 只出现在 `try` 的成功路径上。「清空永远在服务端确认之后」：宁可让用户重试，不可让数据消失；
2. **「已迁移过」也走 `done()`**，这里有一个真实的边角风险：服务端在幂等命中时**直接返回、不写备份**（第 ① 段在备份之前），前端却照样 `removeItem` 清空浏览器副本。好在「已经迁移过」意味着 `migrations` 凭据存在，也就意味着**上一次迁移一定写过备份**——数据仍有据可查；但若有人手工清过 `migrations` 表再遇到这条路径，副本就真的没了。完整的权衡写在 ⚠️ 坑 3；
3. **按钮没有 loading 防抖**：迁移进行中还能再点——服务端幂等检查就是为这种手滑准备的第二道门。**前端防抖为了体验，服务端幂等为了正确**（第 10 章同款分工哲学）。

### 「暂不迁移」与一处文档漂移

`close={()=>setMigrate(null)}`——「暂不迁移」只做一件事：关弹窗。localStorage 一个字节没动，下次刷新，检测 effect 会再次读到旧数据、再次弹窗。

这是**有意为之**：点「暂不」是「这次不」，不是「永远不」——迁移是用户的权利，不该被一次点击判为永久放弃。但对照 `docs/用户操作手册.md` 第 519 行：

> 点击 **暂不迁移**：关闭弹窗，下次进入不再重复提示（可用旧数据文件手动恢复）。

「下次进入不再重复提示」与代码行为**不符**——代码里没有任何「不再提示」的持久化标记。这类「文档说的和代码做的不一样」叫**文档漂移**（documentation drift），在真实工程里几乎是常态：文档写完，代码又进化了。处理原则与工程一致——**以代码为准，把漂移记下来**：本章 ✍️ 练习 3 就是把手册的这句承诺做成真。

> 验证点：本节不修改代码——「暂不迁移」的行为观察（刷新后弹窗是否再现）在 11.5 的验证 H 统一进行。

## 11.3 旧数据说明书：读懂 app.js 的 state

迁移的另一半功课是「旧数据长什么样」。`app.js` 是 498 行的第一代原型，本章**只读不改**。想读懂请求体里装的是什么，看这几处就够：

| app.js 位置 | 内容 | 与迁移的关系 |
| --- | --- | --- |
| 第 91 行 | `STORE_KEY` 定义 | 键名三方契约的「写」方 |
| 第 97–106 行 | `initialKnowledge` 八条 | 知识数据的开机状态 |
| 第 108–110 行 | `knowledge()` 工厂 | 知识对象形态 |
| 第 112–123 行 | `initialState` 六字段 | 迁移请求体的整体形状 |
| 第 125–127 行 | `sampleTask()` | 任务形态 A：**无 `input`** |

### 键名就是协议

```js
// app.js 第 91 行
const STORE_KEY = 'testpilot-personal-workbench-v1';
```

这个字符串在项目里出现**三处**，一处都不能错：

| 出现处 | 角色 | 代码 |
| --- | --- | --- |
| `app.js` 第 91 行 | **写**——第一代保存（第 147 行 `save()` 调用） | `localStorage.setItem(STORE_KEY, …)` |
| `main.tsx` 第 51 行 | **读**——新版检测 | `localStorage.getItem('testpilot-personal-workbench-v1')` |
| `main.tsx` 第 72 行 | **删**——迁移成功后清空 | `localStorage.removeItem('testpilot-personal-workbench-v1')` |

三处任何一处改名，链路即断：写改读不改 → 弹窗永不出现；删错名 → 每次都重复弹窗。再加上服务端 `migrations` 的主键 `'localstorage-v1'`（这次搬迁协议的「登记名」）——**跨代际的字符串约定，就是迁移协议本身**。留意一个细节：协议名与 localStorage 键名刻意不同名（一个描述「哪批数据」、一个描述「哪次协议」），硬绑同名反而会把「同一批数据换协议再迁一次」的路堵死。

### 六字段与去留

`initialState`（第 112–123 行）就是「浏览器里那坨数据」的全貌——它**原样**成为迁移请求体的根对象：

| 字段 | 内容 | 本轮迁移 | 理由 |
| --- | --- | --- | --- |
| `tasks` | 任务数组 | ✅ 导入 `tasks` 表 | 核心资产 |
| `knowledge` | 知识数组 | ✅ 导入 `knowledge` 表 | 核心资产 |
| `workflows` | 链路模板 | ❌ 未迁 | 结构接近、价值高——✍️ 练习 2 的题目 |
| `reports` | 报告 | ❌ 不迁 | 新版结构化 JSON vs 旧版文本，差异过大 |
| `schemas` | 表单字段定义 | ❌ 不迁 | 新版由「配置中心 → 格式模板」+ `settings` 表接管 |
| `bindings` | 任务-知识关联 | ❌ 不迁 | 新版用 `relations` 表建模 |

六进二出——服务端的两个 `for` 只翻 `d.tasks` 与 `d.knowledge` 两个抽屉，其余四个**原样躺在备份里**（第 ② 段写盘的是整个 `d`）。所以「没迁 ≠ 丢了」：第 ⑥ 节的取舍，在数据层面就是这一句。

### 任务对象的两种形态

同一个 `tasks` 数组里混着两种形状。**运行中新建的**（`runCurrentTask`，第 422 行）——带 `input`：

```js
const task = { id:crypto.randomUUID(), type:ui.taskType, title:draft.title || def.title, status:'待复核', createdAt:formatNow(), input:{...draft}, result };
```

**种子演示数据**（`sampleTask`，第 125–127 行）——**没有 `input`**：

```js
function sampleTask(type, title, status) {
  return { id:crypto.randomUUID(), type, title, status, createdAt: '2026-08-19 10:30', result: makeResult(type, { title, environment: 'staging', version: 'v2.8.3' }) };
}
```

现在回看服务端的 `json(item.input || {})`：`|| {}` 不是「防御性编程的礼貌」，而是**真实存在的空值现场**——种子任务从没被编辑过，`input` 就是 `undefined`。迁移代码里每一个兜底，背后都对应旧数据里一个真实可能的空洞。

还有第三种「不太标准」的形态——**组合任务**（`runCombination`，第 471 行）：

```js
state.tasks.unshift({ id:crypto.randomUUID(), type:ui.comboSelected[0], title, status:'待复核', createdAt:formatNow(), combination:[...ui.comboSelected], result:{…} });
```

- `type` 取勾选的**第一个**任务类型（组合语义被压平进单类型字段）；
- `combination` 是旧版特有字段（记录组合了哪几项）——新版没有对应列，服务端**只取它认识的字段**（`type / title / status / createdAt / input / result`），不认识的原样留在备份里。

任务的 `status` 还有一处「诚实的对不齐」：旧词是 `'待复核' / '已复核' / '已完成'`（前两个来自 `runCurrentTask` 与种子），而新版的词表是「草稿 / 待审核 / 已完成 / 待补充」。服务端的选择是 `item.status || '已完成'`——**旧词原样入库，不强行翻译**。于是一条 `'待复核'` 任务迁进新版后，徽章会因词表不识别而显示**灰色**（`badgeClass` 的默认分支）——不漂亮，但它是真的；伪造一个 `'待审核'` 才是更坏的选择（旧版没有审核流，翻译等于编造）。这条准则在 11.4 与 ⚠️ 坑 7 继续展开。

### 知识对象的形态与时间的三种格式

```js
// app.js 第 108–110 行
function knowledge(title, category, module, risk, content) {
  return { id: crypto.randomUUID(), title, category, module, risk, content, status: '已发布', updatedAt: '2026-08-19' };
}
```

- `module` 是**自由文本**（`'支付 / MQ'`、`'订单 / 优惠券'`）——不是 id，与新版三级模块表无法对应 → 导入置 `null`（11.4 详述）；
- `status:'已发布'`——旧版知识没有审核流，出厂即发布；好在旧词表（`已发布 / 待审核`）与新版知识状态机恰好兼容，服务端 `item.status || '待审核'` 可以原样收下——**兼容是运气，不兼容才是常态**（任务状态就不兼容）；
- 时间只有一个维度 `updatedAt`——第 ④ 段「错位映射」的根源。

最后是时间格式的**三副面孔**，它们混在同一个 state 里：

| 产地 | 样例 | `new Date()` 解析（实测） |
| --- | --- | --- |
| `sampleTask` 种子 | `'2026-08-19 10:30'` | 正确：2026-08-19 10:30 |
| `knowledge()` 工厂 | `'2026-08-19'` | 按 UTC 解析：本地时间 08:00 |
| `formatNow()` 运行中 | `'08-19 10:30'` | **错误：2001-08-19 10:30**——没有年份，引擎把年份猜成 2001 |

第三行是真实的陷阱：`formatNow()`（第 149 行）只格式化「月/日/时/分」，产出**没有年份**；这类任务迁进库后，将来界面用 `date(v)`（`new Date(v).toLocaleDateString(...)`）渲染，显示的就是 **2001 年**。

那迁移为什么不「顺手清洗」？——因为清洗意味着**猜**：猜年份、猜补零。猜错比留着更糟（第 ⑥ 节「不迁比迁错好」的又一次适用）。服务端的选择仍是 `item.createdAt || now()` **原样保留**：迁移负责搬运事实，不负责制造事实；原始 JSON 在备份里，想订正时人工订正。

> 验证点：第三行可在浏览器 Console 亲手复现——`new Date('08-19 10:30').toString()`（node 里同样成立）。11.5 备份文件的 `createdAt` 字段里，也能见到这种「没有年份」的时间。

## 11.4 字段映射全表：14 列与 12 列逐个对账

11.1 第 ③ 段的预告版表回答了「每一列填了什么值」，本节回答两个更深的问题：**这些填法属于哪几类决策？** 以及 **哪几列值得单独讨论？** 先把两张表全部格子的赋值归纳成四类：

| 决策类型 | 含义 | 任务列（14） | 知识列（12） |
| --- | --- | --- | --- |
| 直接搬运 | 旧数据有真值，原样带走 | `id`、`type`、`title`、`status`、`input_json`、`result_json`、`created_at` | `id`、`title`、`category`、`risk`、`status`、`content`、`created_at` |
| 空白留白 | 真正对不上，宁可 `null` 不编造 | `module_id`、`parent_id` | `module_id`、`source_task_id` |
| 常量填充 | 新版结构需要、旧版没有的 | `risk`、`review_status`、`knowledge_status`、`model`、`updated_at` | `version`、`review_note`、`updated_at` |
| 兜底默认 | 值缺失时才启用 | `type \|\| 'bug'`、`title \|\| '旧版任务'`、`status \|\| '已完成'`、`input/result \|\| {}` | `title \|\| '旧版知识'`、`category \|\| '业务规则库'`、`risk \|\| 'P1'`、`status \|\| '待审核'`、`content \|\| ''` |

四类的行为准则一句话：**有值就搬、对不上就空、新版要就填、缺了才兜底**。下面把最值得深挖的几列逐个展开。

### 任务侧：五个值得深挖的格子

**1. `risk = 'P1'`——中间值是最安全的猜测。** 旧版任务对象从头到尾没有 `risk` 字段（`sampleTask` 和 `runCurrentTask` 都没造它）。服务端给了 `'P1'`——为什么不是 P0/P2？P0 在新版规则里意味着资金、数据、安全级别的风险（`main.tsx` 第 181 行的 `high` 正则判定），旧任务没经过这套判定、**没有资格自称 P0**；P2 是「低危」，又会把潜在的高危悄悄降级。P1 = 「需要关注」——错判的方向最安全：宁可多让一个人看一眼，不可让高危隐身。原始信息也并没丢——备份里每条任务的 `result` 原样在，人工复核时可随时升/降级。

**2. `module_id = null`——不伪造外键。** 旧版 `module` 是自由文本（`'支付 / MQ'`），新版 `module_id` 是三级模块表的外键（如 `mod_pay_callback`）——两者之间没有确定的对应关系。给自由文本猜一个 id、或建一个叫「支付 / MQ」的伪模块，都会污染模块体系。宁可置空：前端的 `shortModule()` 会显示「未指定」——**诚实的空缺，好过虚假的完整**（🧠⑥ 在具体格子上兑现）。

**3. `model = '旧版规则'`——把来源写进数据。** 普通创建任务时 `model` 是 `'本地规则'` 或 `'厂商 / 模型名'`（第 8、9 章）——迁移来的任务都不是。填 `'旧版规则'` 让每一条迁移任务自带出生证明：将来在列表里看到这一列，立刻知道「这条不是新系统算的」。**来源信息要写进数据本身，不能只写在迁移文档里**——文档会漂移（11.2 刚见过一次），数据不会。

**4. `parent_id = null`——旧版没有父子结构。** 旧版组合任务用 `combination: [...]` 数组平铺记录（11.3 讲过），没有「父任务 + 子任务」的实体关系；新版（第 8 章）用 `parent_id` 外键建父子树。结构不同，组合信息留在备份里，`parent_id` 置空。

**5. 两个时间列的「双轨制」——最值得单独一节。**

### 时间双轨：created_at 与 updated_at 为什么待遇不同

三个格子的填法摆在一起看：

| 列 | 填法 | 语义 | 依据 |
| --- | --- | --- | --- |
| 任务 `created_at` | `item.createdAt \|\| now()` | 「数据诞生的时刻」 | 旧时间就是史实——**改掉等于伪造历史** |
| 任务 `updated_at` | `now()` | 「最后一次被改动的时刻」 | 迁移本身就是一次改动——诚实记录 |
| 知识 `created_at` | `item.updatedAt \|\| now()` | 同上 | 旧知识只有 `updatedAt` 一个时间维度——**它最有资格代表「这条知识的年代」** |

注意第三个格子里的**错位映射**：旧知识的字段叫 `updatedAt`，却填进了新表的 `created_at`。为什么不「名对名」填进 `updated_at`？——两个填法对比一下：

| 方案 | created_at | updated_at | 结果 |
| --- | --- | --- | --- |
| 名对名 | `now()` | 旧 `updatedAt` | 怪异：声称它在 2026 年 8 月「被修改」、却在 10 月才「被创建」——修改早于创建 |
| 错位映射（采用） | 旧 `updatedAt` | `now()` | 自洽：这条知识「从 2026-08-19 起就存在」，迁移这次操作「刚刚碰过它」 |

时间戳的第一纪律是**先后自洽**：`updated_at` 永远不早于 `created_at`。命名服从语义，而不是反过来。

还有一个「排序副作用」值得知道：任务与知识列表默认按 `updated_at` 倒序（`server.mjs` 第 86 行 `resources` 配置里的 `order:'updated_at'`）。迁移完成那一刻，所有旧数据修齐刷 `now()`，齐齐「浮到列表顶部」——这是给用户的第一份「签到表」：打开列表，最前面就是刚搬进来的老伙计；随着日后的新操作，它们会被慢慢冲淡回各自的时间位置。**「短暂置顶」是设计的效果，不是 bug。**

### 知识侧：三个值得深挖的格子

**1. `category`——两代词表一字不差（运气）。** 新版的七大分类（`main.tsx` 第 34 行 `KB_CATEGORIES`）与第一代（`app.js` 第 90 行）**逐字一致**：历史 Bug 库、业务规则库、接口异常库、日志规律库、SQL 经验库、压测经验库、回归规则库。所以 `item.category || '业务规则库'` 可以直接收下——**升级时「分类体系不变」是真实项目里常见的兼容策略**（业务概念稳定，技术实现变迁）。对照任务 `status` 的旧词不兼容（11.3）——兼容是运气，不兼容是常态。

**2. `risk`——唯一「真搬」的可选字段。** 对照任务列的 `risk = 'P1'` 写死：知识侧却是 `item.risk || 'P1'`——因为旧版 `knowledge()` 工厂有 `risk` 参数（P0/P1 的真值），而任务对象没有。同一次迁移里，「有则搬、无则兜底」两种待遇并存——**决策的单位是字段级的，不是整表级的**。

**3. `version = 1` 与 `review_note = '从旧版迁移'`——给「以前没有的维度」标上起点。** 旧知识没有版本概念、没有审核备注——新版有。填 1 和「从旧版迁移」，相当于给这些知识补上「出生档案」：日后它每被编辑一次，`version+1`（第 5 章），版本演进从 1 开始、「从旧版迁移」永远留在审核备注里。第 7 章详情抽屉的「审核信息」区显示的就是它。

### 三个横向取舍

1. **保留旧 id vs 生成新 id**——保留旧 id 是条目级幂等的钥匙（11.1 第 ③ 段）；代价是库里出现两种 id 风格（旧版 `crypto.randomUUID()` 36 位；新版 `task_xxxxxxxx` 短前缀）。**幂等 > 美观**：id 是给机器用的，不是给人看的；
2. **能带就带 vs 统一兜底**——知识 `risk` 真搬、任务 `risk` 兜底，同一个字段名两种处理。**逐字段评估「旧值可信吗」，而不是逐表统一**；
3. **来源写进数据 vs 只写文档**——`model='旧版规则'`、`review_note='从旧版迁移'` 都是「数据内的来源标记」。文档会漂移，数据库里的标记不会。

2. **没有新数据**——`migrated:false` 在备份与导入**之前**就返回了（第 ① 段）；
3. **没有新审计**——G 步查审计只会看到一条（只要你不重复 C）。

还有两个细节值得品：请求体送的是**空对象**也照样被挡回——幂等检查在第一行，跟请求体根本无关；而 `backupPath` 给出的是**上次**的备份路径——「already-migrated」不是死胡同，它把出口一并指给你（第 ① 段讲的「人情味细节」）。

### 验证 G · 查审计：这次操作留了痕

```
curl.exe -s "http://127.0.0.1:3344/api/audit?type=migration&id=localstorage-v1"
```

（URL 里有 `&`，所以整个 URL 要用引号包住——否则 PowerShell 会把 `&` 当成命令分隔符。）

预期输出（`items` 数组里一条）：

```
{"items":[{"id":9,"entityType":"migration","entityId":"localstorage-v1","action":"完成","detail":"{\"tasks\":2,\"knowledge\":2}","createdAt":"2026-10-02T…Z"}]}
```

三个观察点：`action='完成'`；`detail` 自带「战报」`{"tasks":2,"knowledge":2}`；`createdAt` 就是迁移那一刻（`id` 是自增值，具体数字不重要）。若你刚做过 F 步，再查一次——`items` 仍只有一条：**幂等命中连审计都不打**。这就是第 ⑤ 段说的「审计的粒度是操作，不是行」——一次迁移一条记录，一次重复请求零条记录。

### 验证 H · 「暂不迁移」行为观察（本章最后一课）

再往 Console 里放一份最简单的旧数据（故意用一条全新的 id）：

```js
localStorage.setItem('testpilot-personal-workbench-v1', JSON.stringify({
  tasks: [ { id: 'legacy_demo_003', type: 'bug', title: '再次检测的旧任务', status: '待复核', createdAt: '2026-08-21 09:00' } ],
  knowledge: []
}));
```

**H-1 观察「暂不」的效果：** 刷新 → 弹窗再现（检测 effect 又读到了键）→ 点「暂不迁移」→ 键还在（Application 里看一眼）→ **再刷新一次——弹窗再次出现**。这与 `docs/用户操作手册.md` 第 519 行的承诺（「下次进入不再重复提示」）不符——不是 bug，而是前端**没有做「不再提示」标记**（11.2 的文档漂移现场）。想要「不再提示」，去做 ✍️ 练习 3。

**H-2 观察边角风险：** 这次点「备份并迁移到 SQLite」。预期：

1. toast：「旧数据已经迁移过」（`migrated:false` 分支）；
2. 弹窗关闭，localStorage 里的键**被清空**（`done()` 在成功路径上无条件执行）；
3. `dir data\backups`——**文件数不变**：幂等命中没有写任何新备份。

这正是 11.2 讲的**边角风险现场**：前端把这份「刚放进去的副本」清掉了，而服务端这次没写备份——`legacy_demo_003` 既没进库、也没进任何备份，真的没了。如果这是从别处恢复回来的真数据，第一次迁移的备份救不了它（备份里只有 001/002 那批）。演示数据无所谓，但它把「坑 3」从文字变成了眼见：**服务端「零副作用」与前端「无条件清空」相遇时，谁都没有错，风险却存在**。防范思路见 ✍️ 练习 4（「安全清空」）。

把 H 作为本章的最后一课很合适：**系统的行为由代码决定，文档只是对它的一种描述**——两者不一致时，相信代码、修正文档（或按练习 3 把行为补上）。

### ⚠️ 要点与坑

1. **键名是三方契约。** `testpilot-personal-workbench-v1` 在 `app.js` 第 91 行（写）、`main.tsx` 第 51 行（读）、第 72 行（删）三处出现——任何一处改名，链路即断：写改读不改 → 弹窗永不出现；删错名 → 每次刷新重复弹窗。改名要三处同步改（外加服务端协议名 `localstorage-v1` 的呼应关系）；
2. **「暂不迁移」是「这次不」，每次刷新都会再现。** 代码里没有「不再提示」的持久化标记；手册第 519 行的「不再重复提示」是文档漂移。以代码为准；想要真「不再提示」，做练习 3；
3. **「已迁移过」分支不写备份，而前端仍会清空浏览器副本**（H-2 亲手演示）。凭据存在意味着第一次迁移写过备份，多数情况下有教；但「恢复回来的新副本」不在旧备份里，会被真清。防范：练习 4；
4. **坏条目零容忍：「宽进」只宽容字段缺失，不宽容结构损坏。** 一条 `null`、或 `d.tasks` 不是数组，`for…of` 会直接抛错 → 整批 500。好在逐条插入、已完成的不回滚——修好数据重跑即可（收敛设计）。对来历不明的数据，先小范围试迁；
5. **备份 `{flag:'wx'}` 是排他写。** 同毫秒撞名报错也不覆盖——失败一次重试就好，历史备份永远安全。「备份只增不改」；
6. **完成标记必须在最后一行。** 若把 `INSERT INTO migrations` 提前，一旦中途崩溃就会「半成品 + 已登记」——重跑被挡，数据永远缺一块。收敛设计的生命线是「没登记 = 没完成」；
7. **旧词表原样入库，徽章会显示灰色。** 任务的「待复核 / 已复核」不在新版词表里，界面显示为中性灰——「看起来不对」不等于「做错了」，宁真勿美；
8. **不伪造映射。** 自由文本 module 不猜外键（置 `null`），缺失的 risk 给中间值 P1——未映射的原貌全在备份里，人工未来可补；
9. **`imported` 计数只报「本次新增」。** 重复跑时数字会变小甚至为 0（全被跳过）——toast 的 N 不是「你共有多少旧数据」；
10. **空 / 残缺请求体也会登记。** `POST` 一个 `{}` 也会写空备份、登记 `localstorage-v1`——「宽进」的代价，几乎成为一次性的迁移机会就此消耗。宽容的接口需要谨慎的调用者：正式迁移前，先看清楚要送什么（这正是练习 5「预检面板」的价值）。

### ✍️ 练习

1. **让迁移报告带上「跳过数」。** 目前 `imported` 只统计新增；后端加一个 `skipped:{tasks,knowledge}`（在 `continue` 前计数），前端 toast 改成「新增 X 条、跳过 Y 条」。改动点集中在 `server.mjs` 第 114 行与 `main.tsx` 第 159 行，两处各一两行；
2. **把 `workflows` 也迁过来。** 它是四类未迁数据中结构最接近的（`{id,name,steps}` → `workflows` 表的 `id/name/steps_json/status/created_at/updated_at`）。在 migrate 路由里加第三个循环：`INSERT INTO workflows VALUES(?,?,?,?,?,?)`，`status` 给 `'模板'`；别忘去重、计数与备份兼容（参数形状参照第 5 章 `POST /workflows`）；
3. **做「不再提示」按钮。** 把手册的承诺做成真：`MigrationModal` 的「暂不迁移」改为「写一个标记（如 `localStorage['testpilot-migrate-dismissed']='1'`）再关闭」，检测 effect 看到标记就跳过弹窗。思考题：标记存 localStorage 还是服务端 `settings` 表？各自的问题是什么（换浏览器？提前迁移？）；
4. **「安全清空」：幂等命中时也先写备份再返回。** 补上「前端清空 = 一定有备份」的闭环。注意：重复请求会多出备份文件——好在都是小文件，「只增不改」也允许；可以再进一步：新旧内容一致时跳过写入；
5. **迁移预检面板。** 在弹窗里先给旧数据「体检」：按 `type` 分组统计任务数、逐条标出「将丢弃的字段」（`module`、`combination`）与「将兜底的值」（risk→P1、model→旧版规则）。数据全在 `data` 对象里，不用改后端——这也是把坑 4（坏条目）提前暴露给用户的机会。
