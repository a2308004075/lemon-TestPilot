### 🧠 设计思路与原理

#### ① OpenAI 兼容协议：一个 fetch 打通四家

大模型厂商各家的原生 API 协议并不相同，但自 ChatGPT 之后，**「OpenAI Chat Completions 协议」成了事实标准**——几乎所有主流厂商都额外提供一套「兼容模式」端点：

| 厂商 | 兼容端点（base_url） | 说明 |
| --- | --- | --- |
| OpenAI | `https://api.openai.com/v1` | 协议本家 |
| 通义千问 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | 注意中间的 `compatible-mode`——阿里云为兼容协议单独开的入口，与原生 dashscope API 是两套 |
| DeepSeek | `https://api.deepseek.com/v1` | 原生即兼容 |
| 任意（自定义） | 你自己填 | 中转站（One-API 等）、本地 Ollama（`/v1`）、自部署 vLLM——只要讲 OpenAI 协议就能接 |

兼容协议的核心只有两条约定，一条负责请求、一条负责响应：

```text
请求：POST {base_url}/chat/completions
      Header: Authorization: Bearer <API Key>
      Body:   { model, messages:[{role,content},...], temperature, max_tokens }

响应：{ choices: [ { message: { content: "..." } } ] }
```

本项目这一层代码的取舍：

- **收益**：一份 `fetch` 代码服务所有厂商——`base_url` 和 `model` 存在数据库里（providers 表），换厂商是改一行数据，不是改代码；
- **代价**：用不了各家独有参数（如千问的联网搜索开关注入到原生协议才行）——对本项目的四个分析任务来说无感；
- **边界**：兼容协议只保证「大形状」一致，细节参数名各家仍有出入（坑 9 会讲 `max_tokens` 的例子）——这是「最大公约数」路线的固有成本。

#### ② 密钥为什么不进数据库

很多人第一反应是「在 providers 表里加一个 `api_key` 列不就行了」。本项目偏偏不这么做，原因是一条**真实威胁模型**：

- SQLite 是一个**本地明文文件**（`data/testpilot.sqlite`，外加 WAL 副本）。密钥一旦进库，任何拿到这个文件的人——拷贝、上传网盘、传给别人排障、误提交进 Git——都等于拿到了你的全部 API Key；
- 更糟的是**备份与同步**：第 4 章说过数据库会做备份（`data/backups`），很多人还会把整个项目目录丢进云盘。密钥进库 = 密钥进入所有这些副本。

于是本项目的存储分层是：

| 数据 | 存在哪 | 谁能看到 |
| --- | --- | --- |
| 真 API Key | **系统密钥保险箱**（macOS 钥匙串 / Windows DPAPI 密文文件 `data/keys/<id>.dpapi`） | 只有当前操作系统用户 |
| 掩码 `key_mask`（如 `sk-••••890`） | providers 表 | 界面上给用户看「配过没有、配的是哪个」 |
| 派生布尔 `keyConfigured` | 不落库，请求时由掩码推导 | 前端判断「该厂商能不能用」 |

**任何 API 响应里都不存在真 Key 字段**——包括 `GET /api/providers`、bootstrap、更新接口的回读。这就是第 7 章那句欠账的完整答案：`keyConfigured` 是「从掩码反推的存在性」，不是真 Key 的任何变形。

#### ③ 系统保险箱一号：macOS 钥匙串

macOS 把「系统托管密钥」做成了现成的命令行：`/usr/bin/security`。

```text
存：security add-generic-password -U -a <id> -s TestPilot-LLM -w <secret>
取：security find-generic-password -a <id> -s TestPilot-LLM -w
```

- `-a <id>` 是条目账号（本项目用厂商 id）、`-s TestPilot-LLM` 是服务命名空间——两者合起来唯一定位一条密码；
- `-U` 表示「已存在则更新」——同一个厂商换 Key 就是覆盖写；
- 钥匙串里的数据由系统加密管理，解锁状态、访问权限都由 macOS 管——**「解密所需的秘密」不在你的项目里，而在操作系统用户体系里**。

#### ④ 系统保险箱二号：Windows DPAPI

Windows 的对应物叫 **DPAPI**（Data Protection API）：`CryptProtectData` 加密、`CryptUnprotectData` 解密。

它的工作方式值得展开，因为这是全项目最「黑魔法」的一段：

1. **加密密钥不落在任何文件里**——系统从**当前登录用户的凭证**派生；
2. 本项目用的作用域是 `CurrentUser`：密文与「当前用户 + 当前机器」绑定。**换一个 Windows 用户、换一台电脑，`Unprotect` 必然失败**——这是特性不是 bug（坑 5 展开）；
3. macOS 钥匙串本质相同：解密能力属于「谁在用一个操作系统账户」，不属于项目代码。

Node 没有内置 DPAPI 绑定，有三种调用姿势：

| 方案 | 代价 | 结论 |
| --- | --- | --- |
| 原生扩展（node-gyp 编译） | 破坏「零依赖 + 免编译」，跨平台分发成本高 | 不用 |
| 第三方 npm 包 | 供应链多一个依赖 | 不用 |
| **调 PowerShell 的 .NET 类** | 每次加解密启动一个进程（约 0.1–0.3 秒） | **采用** |

PowerShell 的 `System.Security.Cryptography.ProtectedData` 就是 .NET 封装的 DPAPI。加解密只在「保存配置 / 探活 / 分析」三个低频时刻发生，进程启动开销完全可接受——**用可接受的性能代价换零依赖**，和第 1 章的哲学一脉相承。

#### ⑤ 三条路由的分工：写钥、探活、分析

本章点亮的三条路由各管一段，职责不重叠：

| 路由 | 管什么 | 失败时告诉你什么 |
| --- | --- | --- |
| `PATCH /providers/:id` | 配置与密钥**入库** | 密钥写不进（Linux / 权限问题） |
| `POST /providers/:id/test` | **连通性探活**（不烧 token） | 网络通不通、Key 认不认、地址对不对 |
| `POST /ai/analyze` | **业务调用**（真实聊天补全） | 出结果或失败原因 |

为什么探活要独立成一个接口？因为「配置对不对」和「分析好不好」是两类问题：探活用 `GET /models` 做一次几乎零成本的握手（9.5 详讲），让用户在**不花一分钱**的前提下确认配置可用；分析接口则只在真正要产出时调用。

配上前端第 7 章就写好的降级闭环，整体行为是：

```text
本地规则（永远先算一版）
   │
   ├─ 有「启用 + 已配 Key」的厂商？ ── 没有 ──▶ 直接用本地结果
   │        │有
   │        ▼
   │   调 /ai/analyze ── 成功 ──▶ 模型字段覆盖本地（厂商 / 模型名记入 model）
   │        │失败（超时 / 401 / 网络）
   │        ▼
   │   toast 提示「模型暂不可用，已使用本地规则」──▶ 本地结果照常落库
   ▼
任务永远有完整结果，模型只是「增强」，不是「依赖」
```

## 9.1 新建 provider-keys.mjs（一）：DPAPI 封装（真实 1–19 行）

在项目里新建 `scripts/` 目录（第 10 章的 deploy 脚本也会放这里），写入 `provider-keys.mjs` 的第一部分——import 段与 DPAPI 加解密函数：

```js
import { execFile, spawn } from 'node:child_process';
import { promisify } from 'node:util';
import { mkdir, readFile, writeFile, rename } from 'node:fs/promises';
import { join } from 'node:path';
import { randomUUID } from 'node:crypto';
const exec = promisify(execFile);
function dpapi(mode, value) {
  const script = `Add-Type -AssemblyName System.Security; $s=[Console]::In.ReadToEnd(); $bytes=[Convert]::FromBase64String($s); $out=[Security.Cryptography.ProtectedData]::${mode}($bytes,$null,[Security.Cryptography.DataProtectionScope]::CurrentUser); [Console]::Out.Write([Convert]::ToBase64String($out))`;
  return new Promise((resolve, reject) => {
    const child = spawn('powershell.exe', ['-NoProfile', '-NonInteractive', '-EncodedCommand', Buffer.from(script, 'utf16le').toString('base64')], { windowsHide: true });
    let output = '';
    child.on('error', reject);
    child.stdout.on('data', d => output += d);
    child.stderr.resume();
    child.stdin.on('error', reject);
    child.on('close', code => code === 0 ? resolve(Buffer.from(output.trim(), 'base64')) : reject(new Error('Windows 用户密钥加密失败，请检查 PowerShell 和当前用户权限。')));
    child.stdin.end(value.toString('base64'));
  });
}
```

上面这段与真实文件第 1–19 行**逐字一致**。逐段读。

**① import 段（第 1–6 行）——两种子进程调用姿势各取所需**：

- `execFile` 与 `spawn` 同出 `node:child_process`：`execFile` 适合「跑完收集输出」的场景（macOS 的 `security` 命令），`spawn` 适合「需要边喂边收」的场景（DPAPI 要走 stdin/stdout 交换数据）；
- `promisify(execFile)` 把回调风格的 `execFile` 变成 `await` 风格——第 10 章的 `deploy.mjs` 也会用同款姿势；
- `node:fs/promises` 引入四件套：`mkdir`（延迟建目录）、`readFile` / `writeFile`（读写密文）、`rename`（原子替换，9.2 详讲）；
- `randomUUID` 只服务于「临时文件名」，防止并发写撞名。

**② dpapi 函数的第一印象：它写了一段 PowerShell**（第 7–8 行）。

`script` 模板里 `${mode}` 是可变的：调 `dpapi('Protect', ...)` 时它是 `Protect`（加密），调 `dpapi('Unprotect', ...)` 时它是 `Unprotect`（解密）——**一个函数同时封装了双向操作**。把这一行按分号拆开（真实文件里是一整行），就是一段完整的 PowerShell 脚本：

```powershell
Add-Type -AssemblyName System.Security                                    # 加载 .NET 安全程序集
$s = [Console]::In.ReadToEnd()                                            # 从标准输入读入 base64 文本
$bytes = [Convert]::FromBase64String($s)                                  # 解码回字节数组
$out = [Security.Cryptography.ProtectedData]::Protect($bytes, $null,
       [Security.Cryptography.DataProtectionScope]::CurrentUser)          # 调 DPAPI（Protect 或 Unprotect）
[Console]::Out.Write([Convert]::ToBase64String($out))                     # 结果编码成 base64 写出
```

四个设计点：

- **为什么数据结构是 base64**：stdin/stdout 是「文本通道」，直接传二进制会遇到编码、换行截断、控制字符等各种问题；base64 把任意字节变成纯 ASCII 文本，两端各做一次编码转换——**二进制安全**；
- **`$null` 是第二个参数（可选熵）**：本项目不加额外口令，传空。作用域用 `CurrentUser`——这就是前面说的「与当前用户绑定」在代码里的落点；
- **`[Console]::In.ReadToEnd()` 而不是 `ReadLine()`**：读取直到流关闭，天然处理任意长度；
- **macOS 读者注意**：这个函数只在 `win32` 分支被调用，macOS 上它是「死代码」但无害。

**③ spawn 的四个参数（第 10 行）——每个都有讲究**：

```js
spawn('powershell.exe', ['-NoProfile', '-NonInteractive', '-EncodedCommand', Buffer.from(script, 'utf16le').toString('base64')], { windowsHide: true })
```

| 参数 | 作用 | 不加会怎样 |
| --- | --- | --- |
| `-NoProfile` | 不加载用户的 PowerShell 配置文件 | 别人的 profile 脚本可能拖慢启动、注入输出 |
| `-NonInteractive` | 禁止任何交互提示 | 万一弹出确认框，进程永挂 |
| `-EncodedCommand` | 用 base64 传脚本 | 脚本里的 `$`、`[`、引号在 Windows 命令行转义是地狱——编码传递彻底绕开 |
| `windowsHide: true` | 不弹出黑窗 | 每次保存密钥 / 探活，桌面闪一下黑框，观感极差 |

`-EncodedCommand` 有个硬性规定：**内容必须是 UTF-16LE 编码再转 base64**——所以是 `Buffer.from(script, 'utf16le').toString('base64')`，顺序反过来会得到乱码脚本。这是 PowerShell 编码命令的经典坑。

**④ Promise 的七行接线（第 9–18 行）——把子进程当协程用**：

- `new Promise((resolve, reject) => {...})`：把「回调式」的子进程事件封装成 `await` 可用的 Promise；
- `child.on('error', reject)`：进程都起不来（如 powershell.exe 找不到）→ 直接失败；
- `child.stdout.on('data', d => output += d)`：数据是**分块到达**的，逐块累积到 `output` 字符串（和 `readBody` 收集请求体是一个套路）；
- `child.stderr.resume()`：把 stderr 的数据「放水流走」。为什么不是监听而是 `resume()`？如果 stderr 管道写满而无人读取，操作系统会阻塞子进程——`resume()` 是最省事的「排水」方式（不收集、不阻塞）；
- `child.stdin.on('error', reject)`：喂数据的通道也可能出错（如进程已退出），同样要接线；
- `child.on('close', code => ...)`：进程结束。`code === 0` 表示成功——把 stdout 的 base64 文本解码回 Buffer 后 `resolve`；非 0 则 `reject`，错误信息是**给用户看的中文**；
- `child.stdin.end(value.toString('base64'))`：把要处理的数据（明文或密文 Buffer）编码成 base64 喂给 stdin，然后关闭输入流——`ReadToEnd()` 就是靠这个「关闭」知道读完了。

**⑤ 一个已知的文案瑕疵**：第 16 行的错误信息说「密钥**加密**失败」，但这条消息在 `Unprotect`（解密）失败时同样会抛出——9.8 的验证会亲眼看到这个问题（坑 5 细讲）。

> 验证点：此刻文件还不能独立运行（缺 export），但语法已完好——下一节写完 `save` / `read` 后立即用一条命令实测加解密往返。

## 9.2 新建 provider-keys.mjs（二）：工厂、save 与 read（真实 20–53 行）

第一部分只是 DPAPI 的封装；这一部分才是「密钥管家」对外的全部接口。继续写：

```js
export function providerKeys(dataDir) {
  function path(id) {
    if (!/^[a-zA-Z0-9_-]+$/.test(id)) throw new Error('无效的模型配置编号');
    return join(dataDir, 'keys', `${id}.dpapi`);
  }
  return {
    async save(id, secret) {
      if (!secret) return;
      if (process.platform === 'darwin') {
        try { await exec('/usr/bin/security', ['add-generic-password', '-U', '-a', id, '-s', 'TestPilot-LLM', '-w', secret]); }
        catch { throw new Error('macOS 钥匙串保存失败，请检查钥匙串是否解锁及访问权限。'); }
      } else if (process.platform === 'win32') {
        const destination = path(id);
        const encrypted = await dpapi('Protect', Buffer.from(secret));
        await mkdir(join(dataDir, 'keys'), { recursive: true });
        const temporary = `${destination}.${randomUUID()}.tmp`;
        await writeFile(temporary, encrypted, { mode: 0o600 });
        await rename(temporary, destination);
      } else throw new Error('当前密钥存储仅支持 macOS 和 Windows。');
    },
    async read(id) {
      if (process.platform === 'darwin') {
        try { return (await exec('/usr/bin/security', ['find-generic-password', '-a', id, '-s', 'TestPilot-LLM', '-w'])).stdout.trim(); }
        catch { return ''; }
      }
      if (process.platform === 'win32') {
        let encrypted;
        try { encrypted = await readFile(path(id)); } catch (error) { if (error.code === 'ENOENT') return ''; throw error; }
        return (await dpapi('Unprotect', encrypted)).toString('utf8');
      }
      return '';
    }
  };
}
```

上面这段与真实文件第 20–53 行**逐字一致**。四段逐一拆。

**① 工厂函数与闭包（第 20 行）**：

```js
export function providerKeys(dataDir) { ... return { save, read }; }
```

和 `createWorkbench(db)` 一样的「**依赖注入工厂**」模式：函数接收 `dataDir`，返回一对操作函数，内部通过闭包记住数据目录——**模块不 import 任何全局路径，宿主给什么目录就用什么目录**。三个好处：宿主（server.mjs）掌控数据位置；测试时可以指向临时目录；将来把驱动换成别的存储实现，只改这一个文件。

**② path：一个白名单正则挡住路径穿越（第 21–24 行）**：

```js
function path(id) {
  if (!/^[a-zA-Z0-9_-]+$/.test(id)) throw new Error('无效的模型配置编号');
  return join(dataDir, 'keys', `${id}.dpapi`);
}
```

这是全文件**安全密度最高**的三行。关键在 `id` 的来源：`PATCH /api/providers/:id` 里的 `:id` 是 URL 里的一部分，属**用户可控输入**。如果不做校验，`id = '../../server.mjs'` 会拼出 `data/keys/../../server.mjs.dpapi`——写入操作就会逃出 `keys/` 目录。虽然「能写到哪」还受操作系统权限限制，但**永远不要给路径拼接留下穿越的可能**。

正则 `^[a-zA-Z0-9_-]+$`（字母、数字、下划线、连字符）的思路是**白名单**：只放行「看起来像配置编号」的字符，其余一律 `throw`。四个种子 id（`openai` / `qwen` / `deepseek` / `custom`）全部合规——正常用户永远碰不到这个校验。这和项目里其他安全点的思路一致：不给攻击面留「黑名单漏网」的机会（黑名单总会被绕过，白名单不会）。

**③ save 的三平台分支（第 26–39 行）**：

```js
async save(id, secret) {
  if (!secret) return;                       // 1. 空密钥直接返回
  if (process.platform === 'darwin') { ... } // 2. macOS：钥匙串
  else if (process.platform === 'win32') { ... } // 3. Windows：DPAPI 文件
  else throw new Error('当前密钥存储仅支持 macOS 和 Windows。'); // 4. 其他平台：拒绝
}
```

- **`if (!secret) return`（第 27 行）**：空串 / undefined 直接静默返回。这是「没传就不动」的语义——与 PATCH 路由的 `if (d.apiKey)` 配合，构成「不填 Key 则保持原状」；但副作用是**没有清除入口**（坑 4 详讲）；
- **macOS 分支（第 28–30 行）**：`exec` 调用系统命令，`-U` 是「更新已有条目」——同一厂商换 Key 即覆盖。任何失败（钥匙串锁定、权限拒绝）都被 `catch` 翻译成中文错误抛出；
- **Windows 分支（第 31–37 行）**——五步「原子写」值得单列一张表：

| 步骤 | 代码 | 为什么这么做 |
| --- | --- | --- |
| 1 | `destination = path(id)` | 先过白名单校验，拿到目标路径 |
| 2 | `dpapi('Protect', Buffer.from(secret))` | 明文（UTF-8 Buffer）→ DPAPI 密文（Buffer） |
| 3 | `mkdir(keys, { recursive: true })` | **延迟创建**：`data/keys/` 目录在第一次保存密钥时才出现 |
| 4 | `writeFile(`${destination}.${randomUUID()}.tmp`, encrypted, { mode: 0o600 })` | 先写**临时文件**：唯一后缀防并发撞名；`0o600` 是「仅所有者可读写」权限 |
| 5 | `rename(temporary, destination)` | **原子替换**：同一磁盘内的 rename 是原子操作 |

第 4、5 步合起来就是文件操作里的经典模式「**先写临时文件，再原子改名**」：如果写完临时文件后程序崩溃 / 断电，坏掉的是 `.tmp`（who cares），**已存在的正式密文毫发无损**；读者永远只会看到「完整的旧文件」或「完整的新文件」，不存在中间态。对比「直接覆写正式文件」——写一半断电就是既丢了旧的也没拿到新的。

`0o600`（八进制 600 = 所有者读写、组和其他人不可访问）在 Windows 上会被忽略（Windows 用 ACL 而不是 POSIX 权限位），但语义正确、macOS/Linux 上必须这样写——**一个不能因为「反正 Windows 忽略了」就省掉的习惯**。实际上本文件的保护主要靠 DPAPI 本身 + 用户目录的默认 ACL。

- **其他平台（第 38 行）**：Linux 等直接抛「仅支持 macOS 和 Windows」。为什么不支持 Linux？因为 Linux 的「系统密钥库」是**碎片化**的：GNOME Keyring / KWallet / 或者根本没有桌面环境（纯服务器常见），要接就得引入额外依赖（libsecret 等）——违背零依赖原则。**宁缺毋滥**：不装作支持然后给用户一堆玄学错误，而是明确报错。（Linux 上读取分支返回空串——应用的其他功能照常可用，只是用不了模型。）

**④ read 的分支与容错设计（第 40–51 行）**——注意它和 save 有一个**刻意的不对称**：

```js
try { encrypted = await readFile(path(id)); }
catch (error) { if (error.code === 'ENOENT') return ''; throw error; }
```

- **「不存在」返回空串，「坏了」抛错**：`ENOENT`（文件不存在）说明「还没配过 Key」——这是**预期状态**，返回 `''` 让上层给出友好的 400「请先保存 API Key」；而权限错误、磁盘损坏、解密失败等**真实故障**则继续 `throw`，让错误冒到 500——不该被当作「没配」静默吞掉；
- macOS 分支同理：`find-generic-password` 找不到条目（退出码非 0）时 `catch` 返回 `''`——「没在钥匙串里」= 未配置；而其他错误……真实项目在这里**没有细区分**（统一返回空串），是一个可以改进的边界（练习灵感）；
- Windows 解密路径：`dpapi('Unprotect', encrypted)` → `.toString('utf8')` 还原明文——与 save 的 `Buffer.from(secret)` 严丝合缝；
- 最后一行 `return ''`：所有非 macOS/Windows 平台读不到密钥——与 save 的「抛错」形成对照（保存是主动操作，明确报错；读取是被动查询，安静地表示「没有」）。

## 9.4 点亮路由一：PATCH /providers/:id（真实 111 行）

现在回到 `handleApi`。第 5 章在这里留过一句注释：

把注释里「providers 的 PATCH / test 与 ai」这几个字兑现——**在 settings 路由之前**插入下面这条 PATCH（真实文件第 111 行，一整行，逐字）：


这是本章最长的一行，也是全项目**唯一一条「配置 + 密钥」双写路由**。按执行顺序拆成四步：

**① 先查（防 404）**：

```js
const c=db.prepare('SELECT * FROM providers WHERE id=?').get(parts[2]);
if(!c)return send(res,404,{error:'模型厂商不存在'});
```

第 5 章讲过的「先查、再并、后写」范式开头。`c` 是当前行——它的两个用途马上出现：`??` 并入的兜底值、旧掩码的保管处。

**② 写密钥（先钥后库）**：

```js
if(d.apiKey)await saveProviderKey(parts[2],d.apiKey);
```

- **`if(d.apiKey)` 是「本次传了 Key 才写」**：前端没碰 API Key 输入框时，`form.apiKey` 是 `undefined`——`JSON.stringify` 会直接丢掉这个键，请求体里根本没有 `apiKey` 字段；传了空串 `''` 也会被 falsy 过滤。两种「没传」殊途同归；
- **先写密钥库、后写数据库的顺序是刻意的**：如果密钥写失败（Linux 平台、磁盘权限、DPAPI 异常），`await` 直接抛出 → 被 `handleApi` 的 `catch` 接住 → 返回 500，**UPDATE 根本不会执行**。这样就不可能出现「掩码说配了、钥匙串里却没有」的假状态；反过来如果先写库再写钥，失败时库里就会留下一枚永远点不亮的假掩码。

**③ 算掩码**：

```js
const mask=d.apiKey?`${d.apiKey.slice(0,3)}••••${d.apiKey.slice(-3)}`:c.key_mask;
```

三态一目了然：传了新 Key → 重算掩码（前 3 位 + 四个圆点 + 后 3 位）；没传 → 沿用旧掩码；从未配过 → 旧掩码为空串，继续空着。掩码的**表现边界**（超短 Key 会泄露）是坑 3 的主题，先记住公式即可。

**④ 落库（七个 SET 列 + 一个 WHERE，共八个 `?`）**：

```js
db.prepare('UPDATE providers SET base_url=?,model=?,temperature=?,timeout=?,max_tokens=?,enabled=?,key_mask=? WHERE id=?')
  .run(d.baseUrl??c.base_url, d.model??c.model, d.temperature??c.temperature, d.timeout??c.timeout, d.maxTokens??c.max_tokens, d.enabled?1:0, mask, parts[2]);
```

- 前五项是第 5 章熟悉的 `??` 并入：**传了就更新、没传保持原值**；
- `enabled?1:0` 是**全路由唯一一个没有 `??` 的字段**——这正是坑 2 的源头：`d.enabled` 为 `undefined`（客户端没传）时，表达式结果是 `0`，厂商被意外停用。前端 `ModelSettings.save` 每次都会带上 `enabled:Boolean(form.enabled)`，所以正常界面操作不会触发；但任何「只改一个字段」的 PATCH（比如你 9.8 里的 curl）都会踩中；
- `key_mask` 写第三步算出的掩码——数据库里只有掩码，没有真 Key；
- 最后 `audit('provider',parts[2],'更新配置')` 留痕（注意：审计**只记动作不记内容**——密钥不会出现在审计详情里，这是第 5 章审计纪律的安全延伸），并回读返回。回读经过 `mapRow`，所以响应里的 `keyConfigured` 立即就是最新状态。

把三种典型请求的效果放在一起看：

| 请求体（PATCH /providers/openai） | 密钥库 | providers 表 | 响应的 keyConfigured |
| --- | --- | --- | --- |
| `{"apiKey":"sk-xxx...","enabled":true}` | 写入/覆盖 `openai.dpapi` | `key_mask` 重算，`enabled=1` | `true` |
| `{"model":"gpt-5-mini"}` | 不动 | 其余不动，**`enabled=0`（坑 2 现场）** | 保持 |
| `{"baseUrl":"http://...","apiKey":""}` | 不动（空串过滤） | 其余不动，掩码保持 | 保持 |

> 验证点：这条路由写完后重启，用 `curl.exe -s -X PATCH http://127.0.0.1:3344/api/providers/custom -H "Content-Type: application/json" -d '{"temperature":0.3}'` 试一发——响应 temperature 变为 0.3，而其他字段原样——但你会发现 `enabled` 从 0 变 0 看不出异常（种子本来就是 0）；9.8 验证 A 会用 enabled=1 的厂商把坑 2 完整复现一次。

## 9.5 点亮路由二：POST /providers/:id/test（真实 112 行）

紧接着插入探活路由（真实文件第 112 行）：

- `/models` 是 OpenAI 协议里「列可用模型」的端点，几乎所有兼容端点都实现了它——**它要求的鉴权和聊天接口完全一样（Bearer Token），却不产生任何 token 费用**；
- 一次探活实际上验证了五件事：DNS 解析、TCP/TLS 连通、网关路由、Bearer 鉴权合法性、URL 路径正确性（这是绕过「地址填错」最快的方式）；
- `replace(/\/$/,'')` 先去掉 base_url 尾部的斜杠再拼 `/models`——防止用户填成 `https://api.openai.com/v1/` 时拼出 `//models`（绝大多数服务容忍双斜杠，但总有少数网关不认）。这个「容忍用户多敲一个斜杠」的小习惯在 9.6 的聊天接口里同样出现。

**③ 超时信号**：

```js
signal: AbortSignal.timeout(p.timeout*1000)
```

- `AbortSignal.timeout(ms)` 是 Node 的原生「计时炸弹」：到点自动中断请求并让 `fetch` 抛 `TimeoutError`；
- 数据库里存的 `timeout` 单位是**秒**（60），`Date.now()` 和无数的超时 API 用的是**毫秒**——所以 `*1000` 不能忘（这是笔者在真实项目里反复见到的低级 bug）；
- 超时会抛出异常直接穿透到 `handleApi` 的 `catch`——**不会**走下面那个 502 分支。这是坑 10 要看的现象：错误码体系里有两类失败，一类有翻译（HTTP 状态码），一类没有（网络层异常）。

**④ 结果三态**：

| 情况 | 响应 | 前端 toast |
| --- | --- | --- |
| 探活成功 | `200 {ok:true, latency}` | 「连接成功，耗时 Nms」 |
| 服务可达但鉴权/路径错（401/404/…） | `502 {error:'连接失败：HTTP 401'}` | 原文展示 |
| 网络不通/超时/域名解析失败 | `500 {error:'fetch failed'}` 或英文 TimeoutError | 原文展示（坑 10） |

- `response.ok` 涵盖 2xx 全集——**只要状态码不是 2xx，就一律归为 502**（Bad Gateway，语义恰好是「我（网关）把请求发给上游失败了」）；具体是 401（Key 错）还是 404（地址错），看错误文案里的状态码即可分辨；
- `latency` 是失败前记录的 `started` 时间戳做差——**含 DNS+TLS+服务端处理的全链路墙钟时间**。探活耗时和聊天耗时不是一个量级（后者要生成 token），这个数字只用于「网络快不快」的判断；
- 顺便回答第 7 章的一个细节：`ModelSettings.test` 为什么绕过五方法封装、直接用 `API.request`——因为 `/providers/:id/test` 是「资源 + 子动作」形态，不在 `list/get/post/patch` 四件套的形状里，走底层 `request` 反而最直接。

> 验证点：重启后 `curl.exe -s -X POST http://127.0.0.1:3344/api/providers/openai/test` 预期 400 `{"error":"请先保存 API Key"}`（还没存过 Key）；custom 同理。真正的成功探活留给 9.8 验证 D 的离线 mock。

三条路由的最后一条、也是「降级闭环」的服务端主角。插入（真实文件第 113 行）：

把注释里最后一句「ai 接口在第 9 章」兑现后，记得把第 5 章的占位注释改成只剩 migrate 的版本（如 `// —— 配置与审计（migrate 在第 11 章）——`），免得下次自己混淆。按执行序拆五步：

**① 准入检查：一条 SQL 两道门槛**：


- 请求体只需两个业务参数：`providerId`（用哪家）与 `taskType` + `text`（分析什么）；
- `WHERE id=? AND enabled=1` 把「存在」与「已启用」两道检查合成一条 SQL——未启用的厂商查不出来，统一回 400；这是**服务端不信客户端**的一次体现：即使绕过界面直接调接口，未启用的厂商也调不通；
- 注意这里**没有再查 keyConfigured**——下一行直接尝试取密钥，靠真 Key 是否为空来判定（比布尔字段更可靠，因为它是事实本身）。

**② 取真实密钥**：

```js

if(!key)return send(res,400,{error:'模型 API Key 未配置'});
```

错误文案从「请先保存」变成「未配置」——因为此时厂商已启用，更可能是「配置到一半」的状态。两道 400 合起来就是前端 `enabled && keyConfigured` 双重筛选的服务端镜像。

**③ 请求体：与 OpenAI 协议对齐的六件套**：

```js

  method: 'POST',
  headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${key}` },

      { role: 'system', content: '你是测试分析助手。仅返回合法 JSON，包含 summary、risk、suggestions、missingFields。' },
      { role: 'user', content: `${d.taskType}\n${d.text}` }
    ]
  }),
  signal: AbortSignal.timeout(p.timeout*1000)

```

- **URL 与头**：与 9.5 完全同构（去尾斜杠、`Bearer` 鉴权）——这就是兼容协议「一份代码打四家」的直接体现；
- **system prompt 的四个字段名不是随便起的**：`summary`、`risk`、`suggestions`、`missingFields` 与第 7 章 `localAnalysis()` 返回的四个字段**同名**。这不是巧合，而是**数据契约**——9.7 会看到前端用 `result={...result,...ai.result}` 做浅合并，同名才能「模型结果覆盖本地结果」，不同名就白调了；
- **`content: `${d.taskType}\n${d.text}``**：把任务类型（bug / logs / sql / cases）放在第一行——同一个分析文本，以 Bug 视角和以日志视角看，模型的解读不同；taskType 就是给模型的「视角开关」；
- **`temperature` / `max_tokens` 直接取自 providers 表**——界面上「温度」「最大输出」两个输入框的值，第一次有了消费点（0.2 低温 = 稳定输出；4096 上限 = 防超长烧钱）；
- **`json(...)` 是第 4 章的工具**：`JSON.stringify(v??{})` 把请求体对象序列化——与第 5 章写库用的是同一个函数，这时它序列化的是要飞出局域网的 HTTP 请求体。

**④ 上游错误 → 502**：

```js
if(!response.ok)return send(res,502,{error:`模型调用失败：HTTP ${response.status}`});
```

与 9.5 同款处理：401（Key 无效）、429（限流）、400（参数被拒，坑 9）都从这里过——**上游的错，一律用 502 转述，并带上原始状态码**。

**⑤ 响应解析三连——本项目最「防碎」的十行**：

```js
const result=await response.json(), content=result.choices?.[0]?.message?.content||'{}';
return send(res,200,{provider:p.name,model:p.model,result:parse(content.replace(/^```json\s*|\s*```$/g,''),{summary:content})});
```

第一连「**安全取值**」：

```js
result.choices?.[0]?.message?.content || '{}'
```

`?.` 可选链逐层下降（响应结构不对也不会抛），`|| '{}'` 兜底空内容——取不到就当成空 JSON 对象，下游解析得到 `{}`；

第二连「**剥围栏**」：

```js
content.replace(/^```json\s*|\s*```$/g,'')
```

大模型即使被告知「仅返回合法 JSON」，也经常习惯性地包上 markdown 代码围栏：` ```json\n{...}\n``` `。这个正则剥掉头部 ` ```json ` 与尾部 ` ``` `——**注意它只处理「贴边」围栏**：模型如果先写一段解释再给 JSON，两个针定都不是行首/行尾，正则就无能为力了（坑 7）；

第三连「**宽容解析**」：

```js
parse(content.replace(...), {summary:content})
```

复用第 4 章的 `parse`（失败返回 fallback）——如果模型输出了无法解析的文本，兜底值是 `{summary:原文}`：**宁可把整段原文放进 summary 字段展示，也不丢信息、也不报错**。这是「宽容解析」的设计哲学：一个个人工具，模型偶尔不听话不应该让整个分析失败；

最后返回 `{provider:p.name, model:p.model, result}`——三个字段对应前端 `ai.provider` / `ai.model` / `ai.result`：

- `provider` 与 `model` 只是**名字**，用于把 `model` 列拼成「DeepSeek / deepseek-chat」；
- `result` 就是那包可覆盖本地结果的字段——如果模型听话，里面就是四个标准字段；如果模型不听话，里面就是 `{summary:原文}`（覆盖后本地 summary 被原文替换，但 risk 等字段保留——「部分成功」的优雅降级）。

## 9.7 前端衔接：两处旧代码的「真相时刻」（main.tsx 117、139 行）

后端三条路由全部点亮后，`src/main.tsx` 确实一行都不用改。第 7 章写 `ModelSettings` 和 `AnalysisPage.run` 时，它们就是按「后端将来会有这些接口」的契约写的——现在到了验证契约的时刻：把两处旧代码用本章的后端知识重读一遍，你会发现每一行都对应得上。

**① `ModelSettings` 的三个协议细节（第 139 行）**。第 7 章逐行讲过这个组件，这里只从「协议」视角看三个关键行：

```js

```

- **`save` 的请求体里有 `apiKey` 但永远没有「真 Key 回传」**：`{...form}` 里的 `form.apiKey` 只在用户本次输入过时存在（`undefined` 会被 `JSON.stringify` 丢掉）——与 9.4 的 `if(d.apiKey)` 严丝合缝；而响应回来的 provider 对象里只有 `keyMask` / `keyConfigured`，**下一次 `refresh()` 后输入框重建，真 Key 就只剩服务端知道**；
- **`enabled:Boolean(form.enabled)` 这一句是全链路的安全带**：表单里开关是布尔，SQLite 里是 0/1，路由里是 `d.enabled?1:0`——从界面到数据库的每一次转换都在这里被钉死。正因为每次保存都显式带上它，坑 2 的「局部更新停用」在正常界面操作下不会发生；
- **`test` 的 toast 文案直接消费 `r.latency`**：`{ok:true,latency}` → 「连接成功，耗时 42ms」——后端测的墙钟时间，前端原样展示，这是 9.5 设计的闭环；失败时 `e.message` 就是后端 400/502/500 里的 `error` 字段（第 6 章 API 封装的功劳）。

还有一个值得注意的小残留：保存成功后 `refresh()` 会更新 bootstrap，但 `providers` 表**没有 `updated_at` 列**，`useEffect(()=>setForm(p||{}),[selected,p?.updatedAt])` 的依赖数组前后都是 `undefined`——effect 不触发，输入框里会继续显示你刚刚敲入的明文 Key（切换厂商才会重建表单）。代码层面无害（Key 本就是你刚输入的），但作为「密钥生命周期管理不完整」的第三块拼图，记到坑 4 一起看。

**② `AnalysisPage.run` 的降级闭环完整时序（第 117 行）**。第 7 章拆过这段代码的 UI 含义；现在你有了后端的全部知识，重看一遍完整时序图：

```text
点击「开始分析」
  │
  ├─ ① localAnalysis(taskType,text)  →  result（本地规则打底），model='本地规则'
```

逐层读这张图：

- **① 本地规则永远先跑**：`localAnalysis` 是第 7 章写的确定性规则函数，无论后面发生什么，它一定产出一份完整的四字段结果——这是「永不空手而归」的底座；
- **② 的筛选条件与服务端镜像**：`p.enabled && p.keyConfigured` 对应的就是 9.6 里 `WHERE id=? AND enabled=1` 与「真 Key 非空」两道门槛——**前端筛掉不可能成功的调用，服务端兜住绕过前端的调用**，两边各自把关；
- **③ 的请求体就是 9.6 读到的那四个字段**：`providerId` 选哪家、`taskType` 给模型视角、`text` 是材料原文；
- **覆盖式合并的准确含义**：`result={...result,...ai.result}` 是**浅合并**——`ai.result` 里有的字段整体替换本地同名（如 `suggestions` 数组直接换成模型给的数组，不是拼接），`ai.result` 里没有的字段保留本地。所以 9.6 的 system prompt 里四个字段名必须与本地同名——**这是前后端之间没写在接口注释里、但被代码强约束的契约**；
- **内层 catch 是「模型失败 ≠ 任务失败」的保险丝**：模型超时、401、限流……任何失败都只损失「增强」部分，任务照常落库，只在 toast 里提一句。这就是第 8 章那句「确定性骨架 + 可插拔智能环」在前端的最终形态；
- **`model` 字段走完全程**：后端返回 `ai.provider` / `ai.model` 两个**名字**，前端拼成 `"DeepSeek / deepseek-chat"` 写进 `model`——这个字符串最后落在 `tasks.model` 列，在列表页「模型」列和详情抽屉「分析模型」行里展示。第 7 章说「`model` 字段是第 9 章要接力的钩子」——接力的终点在这里：**没调过模型的任务，`model` 永远是「本地规则」四个字；调过且成功的，永远是「厂商 / 模型」的格式——没有中间态，也没有冒名顶替**。

**③ 一个值得反复体会的设计对偶**：

| 层 | 本地规则 | 模型增强 |
| --- | --- | --- |
| 存在形式 | 确定性函数（永远可执行） | 外部 HTTP 依赖（可能失败） |
| 产出时机 | 先产出、无条件 | 后调用、成功才覆盖 |
| 失败影响 | 无（它就是兜底） | 只丢失增强字段 + 一句 toast |
| 落库字段 | `model='本地规则'` | `model='厂商 / 模型'` |

### ⚠️ 要点与坑

1. **界面文案还是 macOS 的**——`main.tsx` 第 139 行 `ModelSettings` 的 hint 写着「API Key 存入 macOS 钥匙串，不写入数据库」。第 7 章埋下的两笔欠账，答案现在齐了：Windows 下既不是钥匙串、也没进数据库，而是 DPAPI 密文文件（`data/keys/<id>.dpapi`）。`keyConfigured` 那笔已由 9.3 结清，唯独这句文案成了「没跟上」的文字——修法见练习 2；
2. **`d.enabled?1:0`——局部更新最容易被踩的坑**（9.4）：它是整条 PATCH 路由里唯一没带 `??` 的字段。客户端不传 `enabled` 时（`undefined` 为 falsy），表达式得 `0`——厂商被静默停用。前端每次保存都显式带 `enabled:Boolean(form.enabled)` 所以界面操作安全；但 curl、脚本、以及未来任何「只改一个字段」的新界面都会踩。验证 A 已亲历现场，正式修复见练习 5；
3. **掩码公式对超短 Key 会「露馅」**（9.4）：`slice(0,3)+'••••'+slice(-3)` 在 Key 长度 ≤ 6 时首尾两段重叠——6 字符的 `abc123` 掩码成 `abc••••123`，等于把整串都泄露了；即便长度正常，它也固定暴露首尾各 3 位。更稳的展示是「只露尾 4 位」（`'••••'+slice(-4)`）。现状是「个人工具、自己输入自己的 Key」场景下的合理简化，练习 5 顺手改掉；
4. **密钥没有删除通道——三重防线叠加的结果**（9.2 / 9.4 / 9.7）：想「清掉」一个已保存的 Key，前端传空串会依次撞上三道门：① 后端 `if(d.apiKey)` 对空串为假，跳过写钥；② 就算走到 `save()`，`if(!secret)return` 静默返回；③ 掩码 `d.apiKey?...:c.key_mask` 也沿用旧值。「不填 = 保持原状」的语义在三处叠加，结果就是**清不掉**——目前唯一途径是手动删 `data/keys/<id>.dpapi`（Windows）或钥匙串条目（macOS）。还有半块拼图：保存成功后输入框仍残留明文（`providers` 表没有 `updated_at`，`useEffect` 依赖不触发——9.7），切换厂商才会重建表单。两件事合起来说明：**密钥生命周期管理（新增 / 更新 / 清除）只做了一半**——补全见练习 1；
5. **DPAPI 绑定「当前用户 + 本机」，且错误文案会误导**（9.2）：换 Windows 用户或换机器后，`Unprotect` 必然失败——而这个失败被掩盖在「Windows 用户密钥加密失败」的文案下（该错误串在 Protect 与 Unprotect 失败时共用）。看到它先想两件事：是不是换了用户 / 机器？它其实说的是「解密」失败。这也是「拷贝项目目录跨机器恢复」的唯一陷阱：数据库、知识、配置全都能带走，唯独密钥必须重配；
6. **Linux 是「明确不支持」，不是 bug**（9.2）：`save` 抛「当前密钥存储仅支持 macOS 和 Windows。」（PATCH 返回 500）；`read` 返回空串（test / analyze 报 400）。部署到 Linux 服务器或 Docker 时，模型功能整体禁用、其余功能照常。设计理由：Linux 密钥库碎片化（GNOME Keyring / KWallet / 无桌面环境），接入即破坏零依赖原则——宁缺毋滥，不装作支持然后给用户一堆玄学报错；
7. **围栏剥离只认「贴边」围栏——不贴边就静默降级**（9.6）：正则 `^```json\s*|\s*```$` 只能剥「行首的 ` ```json `」与「行尾的 ` ``` `」。若模型先写一句「好的，以下是分析：」再给 JSON，头部剥不掉 → `JSON.parse` 失败 → 落入 `{summary:原文}` 兜底：**不报错、任务照常完成，但你期待的四字段变成整段原文塞进 summary**。当你发现「分析结果显示的是原始输出」时，多半是这里。强化解析见练习 3；
8. **探活依赖 `/models` 端点——不是所有兼容实现都有它**（9.5）：绝大多数厂商实现了，但少数自部署 / 中转站只实现 `/chat/completions`——探活 404 → 502「连接失败：HTTP 404」，而真实聊天其实可用。诊断口诀：**探活失败先看状态码**——401 / 403 是 Key 问题、404 是地址或端点缺失、网络层错误则是地址不通。另外 `custom` 没填 base_url 时拼出的是相对路径，请求直接失败——先把地址填全再点探活；
9. **`max_tokens` 的兼容边界**（9.6）：本项目按兼容协议的「最大公约数」只发 `max_tokens`；而部分较新的模型端点（如 OpenAI 推理系列）已改用 `max_completion_tokens`，收到旧参数名直接 400 → 我们转 502「模型调用失败：HTTP 400」。这是统一兼容层的固有成本——**遇到 400 且 Key / 地址都确认无误时，先怀疑参数名**（具体以厂商当时的文档为准）。出路无非两条：给 providers 表加参数映射，或换一个支持旧参数名的模型；
10. **网络层错误原样冒英文——错误翻译只做了一半**（9.5 / 9.6）：错误码体系里有两类失败——HTTP 状态码类（401 / 404…）有翻译「连接失败：HTTP xxx」；网络层异常（超时 `TimeoutError`、拒连 `fetch failed`）则直接冒 `error.message` 英文原文（500）。而且 `fetch failed` 的真正原因藏在 `error.cause.code`（ECONNREFUSED / ENOTFOUND…）里，catch 没读它，用户只能看到笼统一句。诊断口诀：**看到「fetch failed」= 请求根本没到达对端**——地址错、服务没起、DNS 失败、代理拦截，都可能是它。修复（进阶）：在 `handleApi` 的 catch 里拼上 `error.cause?.code`。
