### 🧠 设计思路与原理

#### ① 引擎解决的核心问题：从「用户选工具」到「系统选流程」

第 7 章的分析页有一个隐含前提：用户自己点进「Bug 分析」页，说明他知道自己要做什么。但真实场景里，用户手里往往只有**一段混杂的材料**（现象 + 日志 + 环境 + 版本），他并不清楚该从哪个任务做起。工作流引擎把选择权拿回系统：**你只管贴材料，路由由系统定**。

一次完整的执行（run）走这条链：

```
一段文本 ──▶ routeText 触发词路由 ──▶ [bug_analysis, log_triage, sql_analysis, regression_list]
                                        │  第 1 个 = 主任务，其余 = 辅助任务，顺序固定
                                        ▼
             fieldPresent 缺项预检 ──▶ missing: ['时间范围','SQL 文本']
                                        ▼
             buildOutput 逐路由产出结构化结果 + 风险判定（P0 / P1 / P2）
                                        ▼
             workflow_runs + workflow_run_steps 落库（输入快照 + 逐步轨迹）
                                        ▼
             人工复核：approve → 已完成 ／ reject → 待补充
```

#### ② 数据驱动的三层变现

第 5 章的 `resources` 表把「REST 层」做成了配置；这一章把「工作流」也做成配置——`ENTRY_DEFS` 一张表定义 7 个入口，三层消费全部自动：

| 层 | 消费的字段 | 效果 |
| --- | --- | --- |
| 路由 | `triggers` 触发词 | 不需要给每个入口写 if-else，新增入口只加一条数据 |
| 预检 | `required` 必填项 | 缺项清单、完整度百分比都由它算 |
| 流程 | `workflow` 步骤数组 | 执行时自动铺开成逐步轨迹，无需为每步单独写代码 |

更远一层：这些资产存在数据库里（`workbench_assets` 表），「工作台编排」页面可以**在线改触发词、改必填项、改步骤，保存即发布新版本（version+1）**——运营不用改代码。这就是编排页那句话的含义：「事实留在知识库；工作台只维护入口、触发词、表单、流程、引用映射与输出规则。」

#### ③ 「先流程，后智能」——v1 引擎为什么不调用大模型

本章的引擎**全程零模型调用**：路由靠正则、缺项靠规则、输出靠模板、风险靠关键词。这不是偷懒，而是刻意分层：

- 大模型是**不确定**的（同一输入两次输出可能不同），而「路由对不对、步骤全没全、复核有没有留痕」必须是**确定**的——否则「案例验证」无从谈起（用一个不确定系统验证另一个不确定输出？）；
- 模型接入点在第 5 章 `/api/ai/analyze` 已经预留（独立一环，失败降级本地规则），第 9 章会彻底接上；
- **确定性骨架 + 可插拔智能环** = 先用规则跑通全流程，再逐环替换成模型，每一环都能单独回归。

种子数据里的验证案例 `val_payment` 就是为这个哲学服务的：固定一份材料、固定期望路由，**每次改完引擎跑一遍**——期望的 4 个路由全部命中才算通过。这是「引擎自己的回归测试」。

#### ④ 两套任务体系并存（真实项目的演进痕迹）

读过第 7 章你会记得 `main.tsx` 里的 `TASK_META`（6 类任务）。本章 `ENTRY_DEFS` 又有 7 个入口，id 却不完全一样：

| 前端 TASK_META | 引擎 ENTRY_DEFS | 用途 |
| --- | --- | --- |
| `cases` | `testcase_gen` | 用例生成 |
| `bug` | `bug_analysis` | Bug 分析 |
| `logs` | `log_triage` | 日志排查 |
| `sql` | `sql_analysis` | SQL 分析 |
| `regression` | `regression_list` | 回归清单 |
| `report` | `test_report` | 测试报告 |
| —（无） | `prompt_test` | 引擎独有：Prompt 输出质量检查 |

它们是**两代演进**的沉淀：本地分析（第 7 章）先实现，工作流引擎（本章）后加，作者没有强行统一（统一要动两套 id 的所有消费点，收益却很低）。读真实项目时要能识别这种「近义体系」——它们各自闭环，通过「新页面用新体系」自然过渡。这正是 4 个工作台页面与 6 个本地分析页能并存的原因。

#### ⑤ 「认领制」挂载：两个模块如何优雅地拼在一起

`server.mjs` 的 `handleApi` 里加一行：

```js
if(parts[1]==='workbench')return await workbench.handle(req,res,url,parts);
```

`workbench-api.mjs` 只导出一个 `createWorkbench(db)` 工厂、返回 `{handle}`——主服务器把 `/api/workbench/*` 整条前缀**转交**给它，自己不关心内部路由。而 `handle` 内部第一行又检查 `parts[1]!=='workbench'` 就 `return false`——**双保险**：即使将来主路由改成分发制（挨个问各模块「是不是你的请求」），workbench 也能正确表态。一个函数接口 = 一条干净的模块边界。

- **覆盖一个测试人一天的完整工作**：生成用例 → 分析 Bug → 排查日志 → 分析 SQL → 出回归清单 → 写测试报告，外加一个元任务「Prompt 测试」（检验模型输出质量）——这 7 个入口就是需求文档的代码形态；

## 8.2 排序基准与五个小工具（真实 10–15 行）

紧接着是 6 行「地基」代码——一个派生常量 + 五个各司其职的小函数：

```js
const DEFAULT_ORDER=ENTRY_DEFS.map(x=>x.id);
const now=()=>new Date().toISOString();
const parse=(v,f={})=>{try{return JSON.parse(v)}catch{return f}};
const json=v=>JSON.stringify(v??{});
const makeId=p=>`${p}_${crypto.randomUUID().slice(0,8)}`;
const camel=row=>row?Object.fromEntries(Object.entries(row).map(([k,v])=>[k.replace(/_([a-z])/g,(_,c)=>c.toUpperCase()),v])):null;
```

上面这段与真实文件第 10–15 行**逐字一致**。逐行看：

**① `DEFAULT_ORDER`——从数据表推导的排序基准**（第 10 行）：

它不是手写的 `['testcase_gen','bug_analysis',...]`，而是 `ENTRY_DEFS.map(x=>x.id)`——**数组里自动就是这 7 个 id 的出场顺序**。这个常量是 `routeText`（8.5）排序的基准：无论用户怎么勾选、文本命中几个触发词，路由结果永远按这个顺序排列，**第 1 个就是主任务**。

为什么要这么重视顺序？因为「同一份输入永远得到同样的主任务」是可复现性的前提——案例验证（8.15）就是断言「这份材料应该命中这 4 个路由且顺序固定」。如果把 `DEFAULT_ORDER` 手写死，将来往 `ENTRY_DEFS` 加第 8 个入口时就会漏更新；用 `.map()` 推导则**永不脱节**。

**② `now`——统一时间戳**（第 11 行）：ISO 8601 格式（`2026-10-02T03:04:05.678Z`）。与 `server.mjs` 第 34 行完全同款——即使两个模块各写一份，项目内所有时间列的**格式约定**是一致的（第 4 章：列里存 ISO 字符串，前端 `dateTime` 再转本地显示）。

**③ `parse` / `json`——JSON 列的安全进出口**（第 12–13 行）：

```js
const parse=(v,f={})=>{try{return JSON.parse(v)}catch{return f}};   // 出：坏数据回退 f
const json=v=>JSON.stringify(v??{});                                 // 进：null/undefined 写成 {}
```

与 `server.mjs` 第 36–37 行同名同款。`json` 里的 `??{}` 杜绝了「存进 SQLite 的是字符串 `"null"`」这种事故——第 4 章讲过：JSON 列读的时候 `JSON.parse('null')` 会得到 `null` 而不是对象，让下游全炸。

**④ `makeId`——带前缀的短 id**（第 14 行）：

```js
const makeId=p=>`${p}_${crypto.randomUUID().slice(0,8)}`;
```

和 `server.mjs` 第 35 行一个思路：`crypto.randomUUID()` 生成 36 位 UUID，截取前 8 位拼接前缀（本文件里用 `run_`、`step_`）。注意 `crypto` 是 **Node 18+ 的全局 Web Crypto 对象**——不需要 import，直接可用（浏览器里这个对象是 `window.crypto`，Node 里是 `globalThis.crypto`，同源 API）。

**⑤ `camel`——下划线列名 → 驼峰属性名**（第 15 行）：

```js
row?Object.fromEntries(Object.entries(row).map(([k,v])=>[k.replace(/_([a-z])/g,(_,c)=>c.toUpperCase()),v])):null
```

这正是 `server.mjs` 第 85 行 `mapRow` 里用过的那段正则（第 4 章的「命名转换层」）——SQLite 的列名是 `main_route`、`updated_at`，前端要的是 `mainRoute`、`updatedAt`。`row? :null` 处理空值（查不到记录时返回 null 而不是崩掉）。

> 你可能会问：这三个函数（`parse`/`json`/`makeId`/`camel`）在 `server.mjs` 里已经有了，为什么不 `import` 过来？——**模块边界决策**：`workbench-api.mjs` 被设计成「拿一个 db 就能独立工作」的自洽模块，不反向依赖 `server.mjs`（`server.mjs` 才是它的宿主）。十几行工具代码的重复，换来零耦合——这个取舍在真实项目里很常见（第 1 章「不抽公共库」哲学的延续）。

## 8.3 两个归一化函数：行 → 对象（真实 16–18 行）

上一节的 `camel` 只做「列名换形」；真正把一行数据库数据变成「前端可直接消费的对象」的是这两个函数：

```js
function normalizeAsset(row){const x=camel(row);x.triggers=parse(x.triggersJson,[]);x.required=parse(x.requiredJson,[]);x.knowledge=parse(x.knowledgeJson,[]);x.workflow=parse(x.workflowJson,[]);delete x.triggersJson;delete x.requiredJson;delete x.knowledgeJson;delete x.workflowJson;return x}
function normalizeRun(row){const x=camel(row);for(const k of ['routesJson','inputJson','resultJson','missingJson','reviewJson','evidenceJson']){x[k.replace('Json','')]=parse(x[k],k==='routesJson'||k==='missingJson'||k==='evidenceJson'?[]:{});delete x[k]}return x}
```

上面这段与真实文件第 17–18 行**逐字一致**（第 16 行是空行，起视觉分隔作用）。注意签名里没有 `export`——它们是**文件内部函数**，外部拿不到（这符合第 1 章「最小暴露面」的习惯：只有 `createWorkbench` 对外）。

**① `normalizeAsset`——四个 JSON 列还原**：

`workbench_assets` 表里，`triggers`/`required`/`knowledge`/`workflow` 四列存的是 JSON 字符串（`triggers_json` 等，第 8.7 节建表时能看到后缀 `_json` 的命名约定）。转换三步走：

1. `camel(row)`——列名变形：`triggers_json` → `triggersJson`、`updated_at` → `updatedAt`；
2. 逐个 `parse(x.xxxJson, [])`——解析成真数组，默认空数组（坏数据不炸）；
3. `delete x.xxxJson`——删掉过渡键，最终对象是 `{id, name, icon, triggers:[...], required:[...], knowledge:[...], workflow:[...], version, status, updatedAt}` 的干净形态。

**② `normalizeRun`——六个 JSON 列 + 类型感知的默认值**：

写成循环而非手写六遍，节省了长度，但真正巧妙的是循环里的**三元默认值**：

```js
parse(x[k], k==='routesJson'||k==='missingJson'||k==='evidenceJson' ? [] : {})
```

- `routesJson`、`missingJson`、`evidenceJson` 三个列**语义上是数组**（路由 id 列表、缺项列表、证据来源列表）→ 解析失败回退 `[]`；
- `inputJson`、`resultJson`、`reviewJson` 三个列**语义上是对象** → 回退 `{}`。

为什么默认值必须区分数组和对象？因为前端会**直接调用数组方法**：`RunsPage` 里写着 `r.routes.length`、`r.missing.length`（8.20 见）——如果坏数据把 `routes` 还原成了 `{}`，`.length` 是 `undefined` 不会报错，但 `.map()` 会直接崩。**在数据边界处把类型修正好，下游就能「假设它一定对」**——这是归一化层的价值。

**③ 与 `mapRow` 的分工**：`server.mjs` 的 `mapRow` 是「8 个资源共用的大众化转换器」（还会附加 `moduleLabel`、`keyConfigured`）；这里的两个函数是「专属转换器」，只服务自己这两张表的读路径。**通用器保底线、专用器保精度**——两层并存，各管一段。

## 8.4 缺项判定引擎：字段规则表（真实 19–25 行）

接下来是引擎的第二个核心算法——判断「用户贴的这段文本里，到底有没有涵盖某个必填信息」：


上面这段与真实文件第 19–25 行**逐字一致**。这个函数的结构极简单——**一张「字段名 → 正则」查询表 + 一次测试**——但值得逐条拆开看：

**① 为什么是正则？**

因为引擎面对的输入是**一整段自由文本**，不是结构化表单。`required:['问题标题','复现步骤',...]` 里的这些「字段」在原文里**没有标记**，只能靠语言特征去猜：「出现『复现』『步骤』『操作』这类词，就认为用户贴了复现步骤」。这是**启发式预检**，不求精确、只求提醒——即使猜错，代价也只是多提示或少提示一条（执行永不因此被阻塞，见 `canRun` 的定义）。

**② 逐条点评关键正则**：

| 字段 | 正则 | 设计点 |
| --- | --- | --- |
| 问题标题 | `/.{5,}/` | 最宽松的一条：正文任意 5 个字符就算「有标题」。标题本来就无法从自由文本里严格判断，不如放行 |
| 环境 | `/环境\|staging\|test\|prod\|生产\|测试环境/` | 中文词 + 英文环境名全收——测试人写材料两种语言混着用 |
| 日志或 traceId | `/日志\|trace\s?id\|exception\|error\|timeout\|堆栈/i` | `trace\s?id` 允许「traceid」和「trace id」两种写法；`i` 让 exception/error/timeout 大小写不敏感 |
| 时间范围 | `/\d{1,2}:\d{2}\|\d{4}-\d{1,2}-\d{1,2}\|时间/` | 三种形态：`10:20`（时刻）、`2026-10-02`（日期）、或直接出现「时间」二字 |
| SQL 文本 | `/select \|update \|insert \|delete \|join \|explain /i` | **每个词都带尾随空格**——和 8.1 的 triggers 一个习惯：防止「selectivity」误命中。代价是「select(」这种无空格写法会漏判（真实瑕疵，见「要点与坑」） |
| 影响模块 | `/模块\|支付\|订单\|账户\|接口/` | 硬编码了业务名词——种子数据的模块就是支付/订单/账户，属于「测试环境特化」（换成你自己的项目要改这里） |

**③ `rules[field]?.test(text)||false` 的真实语义——保守判定**：

- 字段**在规则表里**：跑正则，命中 → `true`（不缺）、未命中 → `false`（缺）；
- 字段**不在规则表里**（比如你在编排页给某个入口新加了必填项，但忘了在规则表里登记）：`rules[field]` 是 `undefined`，`undefined?.test(...)` → `undefined` → `||false` → **判为「缺失」**。

所以这张表的缺省策略是**「没登记 = 当缺项处理」**——宁可多提示「请补充」，不能静默放行。这也是一种「不猜」：规则覆盖不到的地方，交给用户补信息，而不是假装检查过了。

> 与第 7 章 `Completeness` 组件（字数启发式）对比：那个是纯前端演示（`.length/1.2` 的假进度）；这个是真后端判定（19 条规则逐字段测试），预检接口返回的 `missing` 数组就是它能干活的证据。两者共享同一个设计取向——**先给反馈，再要精确**。

## 8.5 触发词路由：一个函数定宫（真实 26 行）

引擎的「大脑」全部藏在这一行里：

上面这段与真实文件第 26 行**逐字一致**。把它拆成五步读（顺序就是执行顺序）：

**第 1 步 · 全文小写**：`const lower=text.toLowerCase()`——触发词里 `'bug'`、`'lock wait'` 都是小写，所以正文也压成小写再比。中文过 `toLowerCase()` 无变化，无损；

**第 2 步 · 触发词命中**：

```js

```

遍入口（`filter`）→ 入口的触发词里**至少一个**（`some`）出现（`includes`）在正文中 → 保入口，最后只取 id。**子串匹配**：输入「debugger 崩溃了」会命中触发词 `'bug'`（debugger 里含 bug 子串）——宽松，但方向正确：宁可多命中（多跑一个辅助路由，用户可忽略），不可漏（漏了就丢了任务）；

**第 3 步 · 合并手动勾选**：

```js

```

前端「可选任务入口」（8.18）允许用户预勾选想同时跑的任务。去重追加（已在 `ids` 里的不重复加）——**勾选只能「补充」，不能「指定主任务」**，原因在下一步；

**第 4 步 · 兜底不拒答**：

```js
if(!ids.length)ids=['bug_analysis'];
```

一段跟什么都搭不上边的文本，也会路由到 `bug_analysis`（最通用的分析入口）——引擎的第一原则是「不拒答」：能分析什么先分析什么，缺项和风险等级会自己说话；

**第 5 步 · 固定排序（最重要的一步）**：

```js
ids.sort((a,b)=>DEFAULT_ORDER.indexOf(a)-DEFAULT_ORDER.indexOf(b));
```

所有路由按 `DEFAULT_ORDER`（8.2 的派生常量）重排。这一行决定了：**主任务 = `ENTRY_DEFS` 里出场顺序最靠前的命中项，而不是用户勾选顺序、也不是命中先后**。带来的性质：

- 同一份文本，路由结果**永远是同一顺序** → 可复现（案例验证就是靠这个断言）；
- 用户勾选只能在「已命中的集合」之外做加法（第 3 步）；即使他先勾了 `sql_analysis`，只要有 `bug_analysis` 命中，主任务就还是 `bug_analysis`；
- 「主任务只保留一个」（编排页原话）不是靠取第一个实现的，而是靠**排序后才能取第一个**。

> 验证一下你自己：拿 8.24 的示例文本跑一遍心算——命中 `bug_analysis`（有「复现」「实际结果」）、`log_triage`（有「日志」「traceid」「Lock wait」）、`sql_analysis`（有「SQL」）、`regression_list`（有「回归」）四个；按出场序排序后是 `[bug_analysis, log_triage, sql_analysis, regression_list]`。这个结果马上会被写进种子验证案例的 `expected_routes`（8.7），形成闭环。

## 8.21 OrchestrationPage：工作台编排页（workbench.tsx 31 行）

8.14 写的 `PATCH /assets/:id` 是个「能改触发词的接口」；这一页把它变成「敢让运营用的界面」——**不改代码，改数据，发布新版本**。先看逻辑段：

```tsx
export function OrchestrationPage({notify}:any){
  const [items,setItems]=useState<Row[]>([]),[current,setCurrent]=useState<Row|null>(null),[draft,setDraft]=useState<Row>({});
  const load=()=>api('/assets').then((r:any)=>{setItems(r.items);if(!current&&r.items[0]){setCurrent(r.items[0]);setDraft(r.items[0])}});
  useEffect(()=>{void load().catch(e=>notify(e.message))},[]);
  function choose(x:Row){setCurrent(x);setDraft({...x,triggers:[...x.triggers],required:[...x.required],knowledge:[...x.knowledge],workflow:[...x.workflow]})}
  async function save(){try{const r=await patch(`/assets/${current?.id}`,draft);setCurrent(r);setDraft(r);await load();notify(`已发布 ${r.id} v${r.version}`)}catch(e:any){notify(e.message)}}
  const editList=(key:string,value:string)=>setDraft({...draft,[key]:value.split('\n').map(x=>x.trim()).filter(Boolean)});
```

上面这段与真实文件第 31 行的**前三分之一**逐字一致（仅排版换行）。五点：

**① 三个状态 = 「列表 / 展示 / 草稿」三层**：

| 状态 | 装什么 | 谁在渲染 |
| --- | --- | --- |
| `items` | `GET /assets` 返回的 7 条资产 | 左栏「7 个标准入口」列表 |
| `current` | **展示中的**资产（本轮编辑的对象） | 右栏标题区、`WBadge` |
| `draft` | **编辑中的**草稿（textarea 绑定的就是它） | 右栏四个 textarea |

`current` 与 `draft` 分离是本页的核心结构：选中的资产（current）与正在改的内容（draft）是两个对象——**textarea 只改 draft，保存才合并**。命名用 `draft`（草稿）而不是 `edit`，正是这个「未发布状态」的暗示。

**② `load()` 的两件事与「刷新不抢选择」**：

```tsx
setItems(r.items);
if(!current&&r.items[0]){setCurrent(r.items[0]);setDraft(r.items[0])}
```

- 先刷新左栏列表（`setItems`）；
- 再判断：**当前没有任何选中（`!current`）且列表非空**时，自动选中第一条。

这里藏着一段 React 闭包的趣事：`useEffect(...,[])` 只跑一次，它捕获的是**首次渲染**的 `load`，那时 `current` 必为 `null` → 首屏自动选中第一条；而 `save()` 里调用的 `await load()` 用的是**当次渲染**的 `load`（闭包里的 `current` 已是选中资产）→ 不满足条件 → 只刷新列表，不覆盖用户的选择。**「首次选中、之后不抢」不是显式写死的，而是闭包捕获的自然结果**——读这段代码要意识到：`load` 每次渲染都会重建，不同的调用点拿到的是不同快照。

**③ `choose()`——切换入口时的拷贝边界**：

```tsx
setDraft({...x,triggers:[...x.triggers],required:[...x.required],knowledge:[...x.knowledge],workflow:[...x.workflow]})
```

对象本体展开 + **四个数组各复制一份**。为什么必须拷贝？因为 `x` 是 `items` 里的对象（正被左栏渲染），如果 `draft` 与它共享数组引用，将来任何 `draft.triggers.push(...)` 式的原地修改都会**污染列表源数据**（改草稿把列表也改了）。数组里装的是字符串（不可变），所以这一层浅拷贝已经足够隔离。

> 一个真实的不对称：首屏自动选中走的是 `setDraft(r.items[0])`——**没有拷贝**，此时 `items[0]`、`current`、`draft` 三者是同一个对象。之所以现在不出事，全靠 `editList` 坚持「整数组替换」（见下一点），从不原地改。防御只在一条路径上做了，另一条靠约定兜着——读项目代码时这种「不对称的防御」值得留意。

**④ `editList()`——textarea 文本 ↔ 数组的双向协议**：

```tsx
const editList=(key:string,value:string)=>setDraft({...draft,[key]:value.split('\n').map(x=>x.trim()).filter(Boolean)});
```

四个 textarea 的约定是「**每行一项**」，所以需要把「多行文本」还原成「字符串数组」。三步：`split('\n')` 按换行拆 → `map(x=>x.trim())` 每行去首尾空格 → `filter(Boolean)` 滤掉空行。显示的逆运算在 JSX 里：`(draft.triggers||[]).join('\n')`。

- `[key]:value` 的**计算属性名**写法——一个函数服务四个字段，避免写四遍相似代码；
- 即时规范化（trim + 滤空行）意味着**粘贴的带空行文本会被自动清理**——对「词表类」输入恰好是想要的便利；
- **「整数组替换」**：每次编辑都构建全新的 draft 对象与原数组副本，绝不 `push`——这正是 ③ 里「不污染列表」的约定来源。

**⑤ `save()`——发布新版本的四步闭环**：

```tsx
const r=await patch(`/assets/${current?.id}`,draft);   // 第 1 步：PATCH 送出整份 draft
setCurrent(r);setDraft(r);                             // 第 2 步：用服务器返回重置两个状态
await load();                                          // 第 3 步：刷新左栏（版本号变了）
notify(`已发布 ${r.id} v${r.version}`);                // 第 4 步：报出「新版本号」
```

- **前端「整发」、后端「挑用」**：draft 里带着 `id/name/icon/version/status/updatedAt` 全套字段一起送出，而后端（8.14）只挑 `triggers/required/knowledge/workflow/status` 五个用，其余忽略——前端不必裁剪载荷，后端守住白名单；
- 第 2 步用**响应值**重置 `current` 和 `draft`（而不是本地猜），响应来自 8.14 的「写后回读」——版本号 `version+1` 由 SQL 表达式在数据库端递增，前端传的旧 version 被无视——**并发安全**：两个标签页同时保存，不会因「旧值回写」丢失一次递增；
- 第 4 步的 toast（如「已发布 bug_analysis v2」）让运营立刻确认「这次改动生效了、现在是第几版」。

再来看 JSX（第 31 行的后三分之二）：

## 8.22 SandboxPage 与 WBadge：案例验证页（workbench.tsx 33、35 行）

引擎的「回归测试台」——把 8.7 种下的 `val_payment` 案例跑给用户看。先看逻辑段：

```tsx

```

上面这段与真实文件第 33 行的**前半部分**逐字一致（仅排版换行）。四点：

**① 两个状态，其中一个专为「按钮级 loading」**：

- `items`——`GET /validations` 的案例列表（当前只有 `val_payment` 一条）；
- `running`——**正在运行的案例 id**（字符串，默认为空）。它不存布尔值而存 id，因为每个案例卡片各有自己的运行按钮：`disabled={running===x.id}` 只禁用「正在跑的那一个」。

注意与上一节的差异：编排页把 `.catch` 挂在 `useEffect` 里（`void load().catch(...)`），这里把 `.catch` 写在 `load` 内部、`useEffect` 只写 `void load()`——两种写法功能等价，是同一作者的现场发挥（小不统一，无碍）。

**② `run()`——四步一气呵成**：

```tsx
setRunning(id);                                    // 第 1 步：锁定按钮
const r=await post(`/validations/${id}`,{});       // 第 2 步：POST 执行（空 body）
notify(r.passed?'验证通过：...':'验证失败：...');   // 第 3 步：按结果弹不同提示
await load();                                      // 第 4 步：重拉列表
finally{setRunning('')}                            // 收尾：无论成败都解锁
```

- **空 body**：`post(...,{})` 而非不传——因为 `body()` 助手（8.8）对无请求体的处理是返回 `{}`，这里前后端约定「执行不需要参数」（案例的材料与期望都在数据库里）；
- 响应 `r` 是 8.15 后端组装的 `result` 对象（`{actualRoutes,expectedRoutes,passed,checkedAt,rules}`）——前端只消费 `r.passed`；
- 第 4 步**没有本地乐观更新**：通过与否、`lastResult`、状态徽章全部以服务端为准，改完就重拉——数据量小，重拉是成本最低的正确做法；
- `finally` 保证失败也解锁——**加载态永远要能退出**（如果只有成功路径复位，一次网络错误会让按钮永久转圈）。

上面这段与真实文件第 35 行**逐字一致**。三个设计点：

**① 值驱动样式（而不是传 type prop）**：调用处只写 `<WBadge value={r.risk}/>`——组件内部拿**值本身**去两张词表里查：

| 词表 | 值 | 样式类 | 视觉效果 |
| --- | --- | --- | --- |
| `bad` | `P0`、`失败`、`已驳回` | `danger` | 红 |
| `ok` | `已完成`、`通过`、`已发布`、`已复核` | `success` | 绿 |
| 其余 | `P1`、`P2`、`待复核`、`待补充`、`待验证`…… | （空） | 默认黄（基础 `wb-status`） |

好处：调用方零判断、样式一致；代价：**颜色语义藏在组件词表里**——想给「P1」换成橙色，得回来改这个组件（且词表里 P1 与 P2 同色，风险三档实际只映射出两档颜色——真实小粗糙）。

**② 三元嵌套决定类名**：`bad?'danger':ok?'success':''`——第三档返回**空串**，因为基础类 `wb-status` 已经带了黄色样式；`bad` 优先于 `ok`（若某个值同时命中两张表，按危险处理——实际不会发生，但危机优先的排序更安全）。

**③ `value||'—'`**：空值显示破折号——防止界面上出现「空的胶囊」。

`WBadge` 全章共 **5 处使用**：

| 使用点 | 渲染的值 | 常见落档 |
| --- | --- | --- |
| 执行记录表·风险列 | `r.risk` | P0 红 / P1、P2 黄 |
| 执行记录表·状态列 | `r.status` | 待补充、待复核黄 / 已完成绿 |
| 执行记录抽屉·步骤轨迹 | `s.status` | 已完成绿（7 条路由的内容） |
| 编排页·资产标题区 | `current.status` | 已发布绿 |

### ⚠️ 要点与坑

1. **改 `ENTRY_DEFS` 不会更新已经建好的库**——种子用的是 `INSERT OR IGNORE`（8.7）：表里已有 7 条后，再改代码里的定义，数据库不会同步（编排页显示的还是旧数据）。想让代码改动生效：删掉 `data/` 下数据库文件重启，或进编排页手动改。记住这个分工：**代码是种子、库是事实**——线上永远以库为准；
2. **尾随空格与子串匹配的两种方向**——`'select '` 尾随空格防了「selectivity」误命中，代价是「select(」这种无空格写法漏判（8.4）；而触发词路由用的是 `includes` 子串匹配（8.5），方向相反地「宁滥毋缺」：输入「debugger 崩溃」会命中 `'bug'`、输入「latest」会命中环境规则里的 `'test'`。一个宁缺毋滥、一个宁滥毋缺——读完要能说出**为什么缺项与路由的取舍方向相反**（缺项多提示无害，任务漏跑有害）；
3. **`buildOutput` 的兜底是静默的**——将来加第 8 个入口忘写分支，它的输出会悄悄变成 prompt_test 的形状，不报错、不提示（8.6）。加入口时记得同时改 `buildOutput`；或者把兜底改成带显式标记的输出（如插一个 `unknown_entry: id` 字段）便于发现；
4. **验证案例只做「子集断言」**——`expected.every(x=>actual.includes(x))`（8.15）只验「期望路由都在」，不验「没有多出来的」。理论上就算 `routeText` 退化成「永远返回全部 7 个路由」，所有案例照样通过。**测试比实现更容易撒谎**——改验证逻辑时要先看断言的覆盖边界；
5. **`selectedEntries` 是个没用上的变量**——8.18 里用 `useMemo` 算了选中入口列表，但从未被消费（本意可能是想在预检面板展示选中项）。因为 tsconfig 没开 `noUnusedLocals`，`npm run check` 不报——**没有 linter 的项目里，「能编译」不等于「干净」**。删掉它，或接入 ESLint；
6. **第三次「筛选不重置页码」的样本**——RunsPage 的搜索框与状态下拉都漏了 `setPage(1)`（8.20）。加上第 7 章的 CasesPage 与 KnowledgePage，**全书累计 3 处同类样本**——这类「复制粘贴式缺陷」往往成组出现，发现一处就全局搜同类；
7. **执行记录抽屉少一个关闭途径**——对比第 7 章 `DetailDrawer` 的点遮罩关闭，`wb-run-drawer` 的 overlay 没有 `onMouseDown`（8.20）。抄一行就能补（练习 3）；
8. **「精修欠账」清单**——执行记录「主任务」列显示 `bug_analysis` 而非中文名；`RunResult` 头部徽章手写而非复用 `WBadge`（8.19）；`P1/P2` 同色不可区分（8.22）；`--wb-yellow` 定义了但从未被引用（8.23）。单看都小，合起来就是真实项目上线前的常态——教程如实保留而不是粉饰；
9. **`LIKE` 搜索会扫 `input_json` 大字段**——`/runs` 的搜索对 `input_json` 做 `LIKE '%q%'`（8.12），不走索引、数据量大了就是慢查询候选。v1 数据量下无感，属于「记录在案的取舍」；
10. **编排页的「输入即规范化」**——`editList` 每次 onChange 都 trim + 滤空行（8.21）：粘贴多行会被自动清理（好事），但**逐行编辑空格与空行也会被实时吃掉**——对「词表类」输入是便利，若将来要支持段落类编辑，这套 split/join 协议必须换掉（改用 JSON 草稿或「保存前才解析」）。

### ✍️ 练习

1. **邀请第 8 个入口进来**：给 `ENTRY_DEFS` 加一个「接口用例生成」（`id:'api_case_gen'`，触发词、required、workflow 自定）。因为种子是 `INSERT OR IGNORE`，你要么删库重启、要么手写一条 `INSERT`。验收：编排页出现第 8 张卡片；助手页输入含新触发词的文本能路由到它；预检能报它的缺项——**全程不写一行 if-else，纯数据驱动**（顺便体验要点 1 的坑）；
2. **给 `buildOutput` 补上第 8 个入口的分支**（练习 1 的续集）——不改它就会掉进 prompt_test 的兜底形状（要点 3）。对比「改前/改后」两种输出的差异，然后决定：兜底要不要加显式标记？
3. **抽屉补上点遮罩关闭**：对照第 7 章 `DetailDrawer`，给 `wb-run-drawer` 的 overlay 加 `onMouseDown={e=>e.target===e.currentTarget&&setSelected(null)}`。改完两个抽屉的关闭行为就一致了——**顺手把全书累计的三处筛选重置问题一起修了**（本章 RunsPage 的 q/status 加 `setPage(1)`，加上第 7 章的 CasesPage/KnowledgePage）；
4. **让验证更严格**：把 8.15 的 `expected.every(...)` 改成「集合相等」断言（长度相等 + 每项都在）——然后故意给 `test_report` 的触发词加一条「支付」并保存：实际路由会多出 `test_report`（样本里满是「支付」）。旧断言（子集）照样判「通过」，新断言（相等）会正确判「失败」——**这正是两种断言的差别所在**；
5. **给 P1 一个独立的橙色档**：在 `WBadge` 加第三组词表（如 `['P1','待复核','待补充']` → 新类 `wb-status.warn`），并在 `styles.css` 补一段橙色样式。回到执行记录页确认 P1 与 P2 可区分——**这题同时动了组件（8.22）与样式（8.23），体会「颜色语义集中在两处」的联动成本**。
