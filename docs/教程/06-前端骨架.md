### 🧠 设计思路与原理

**① 不用路由库，「路由」到底长什么样？**

第 1 章的决策三在这里见真章。一个路由库（react-router）做三件事：解析 URL → 映射到组件 → 提供跳转 API。本项目全都不需要 URL：「路由」就是 App 里的一个状态：

```tsx
const [page, setPage] = useState<PageKey>('dashboard');   // 当前页
<button onClick={() => setPage(item.id)}>                 // 跳转
{page === 'dashboard' && <Dashboard />}                   // 渲染
```

三件事各一行。代价：刷新回首页、链接不可分享——对桌面式工具完全可以接受。**验证方式**：本章做完后，浏览器地址栏始终是 `127.0.0.1:3344/`，而界面在 13 个页面间切换。

**② 为什么首屏要一个 `bootstrap` 全部拉取？**

模块列表（几十条）、8 个资源的统计（8 个数字）、模型配置（4 条）——全放一个请求里，前端只用**一个加载守卫**（`if (!bootstrap) return <加载中>`）就能保证「页面渲染时数据一定在」。对比「每个页面各自请求」的方案：会出现每个页面一套 loading 逻辑、数据不一致窗口期等问题。**本地工具，一次拉全最省心**（第 5 章 5.4① 已把这个接口写好了）。

**③ 样式为什么是「设计令牌 + 语义类名」？**

打开 `styles.css` 你会看到一种特别的组织方式：顶部 `:root` 定义一批 CSS 变量（`--yellow`、`--ink`、`--line`……），后面所有规则都引用变量而不写死色值。好处：

- **换肤/调整全局只在顶部改几行**（练习 4 会让你亲测：改一个 `--yellow`，全站主色跟着变）；
- 类名是**语义**的（`.panel`、`.badge.red`、`.drawer`），不是「外观描述」的（`.white-box-rounded`）——组件改样式只动 CSS，不动 JSX。

## 6.2 API 封装（35–41 行）：前端的「后端适配层」

接着写 `API` 对象——**全前端唯一负责和后端说话的地方**：

```tsx
const API={
  async request(path:string,options?:RequestInit){const res=await fetch(`/api${path}`,{headers:{'Content-Type':'application/json',...(options?.headers||{})},...options});const data=await res.json();if(!res.ok)throw Object.assign(new Error(data.error||'请求失败'),{data});return data;},
  list(resource:string,params:Record<string,string|number|undefined>={}){const q=new URLSearchParams(Object.entries(params).filter(([,v])=>v!==undefined&&v!=='').map(([k,v])=>[k,String(v)]));return this.request(`/${resource}?${q}`);},
  get(resource:string,id:string){return this.request(`/${resource}/${id}`);},
  post(resource:string,data:Row){return this.request(`/${resource}`,{method:'POST',body:JSON.stringify(data)});},
  patch(resource:string,id:string,data:Row){return this.request(`/${resource}/${id}`,{method:'PATCH',body:JSON.stringify(data)});}
};
```

`request` 是唯一的**底层出口**，其余四个是薄封装。逐点看 `request`：

1. `fetch(`/api${path}`)`——相对路径！因为前端和后端**同源同端口**（第 3 章的架构），不需要写 `http://127.0.0.1:3344`，也不会有跨域问题；
2. 请求头默认带 `Content-Type: application/json`，再合并调用方传入的头（`options?.headers` 在后、`...options` 最后展开——顺序决定了覆盖关系）；
3. `const data = await res.json()`——**无论成败都先尝试解析 JSON**（第 5 章的约定：错误响应也是 JSON）；
4. 关键的一行：`if (!res.ok) throw Object.assign(new Error(data.error||'请求失败'), { data })`——把后端返回的错误对象**挂在 error.data 上**再抛出。这样 UI 层 `catch (e)` 时既能拿 `e.message`（人话）又能拿 `e.data.dependencies` 等附加信息——第 5 章验证 F 的 409 引用清单，在第 7 章的详情抽屉里就靠这个字段展示（「被哪些任务引用了」）；
5. 成功时返回 `data`，类型上是 `any`——调用方直接当对象用。

四个薄封装的语义与后端一一对应（`GET 列表 / GET 详情 / POST 创建 / PATCH 更新`）：

- `list` 只做一件事：把参数对象变成查询串。`Object.entries(params).filter(([,v])=>v!==undefined&&v!=='')`——**值为空则不拼参数**（这就是「不填的筛选条件不会出现在 URL 里」的实现）；注意 `module_id` 这样的参数名是表列名风格，与后端一致（第 5 章验证 B 强调过）；
- `get/post/patch` 各自补上 `resource/id`、方法、JSON body；
- 方法内部用 `this.request(...)`——调用时必须保持 `API.get(...)` 这种形式。如果解构 `const { get } = API` 再调用，`this` 丢失会直接报错（见「要点与坑」第 5 条）。

这是全前端最浓缩的 30 行，按「状态 → 副作用 → 守卫 → 渲染」四段拆开：

### 状态（6 个 useState）

| 状态 | 类型 | 作用 |
| --- | --- | --- |
| `page` | `PageKey` | 当前的「路由」 |
| `bootstrap` | `Row \| null` | 全局数据底座（null = 还没加载） |
| `drawer` | `Drawer` | 右侧详情抽屉（非空即展开） |
| `toast` | `string` | 右下角提示（非空即显示） |
| `collapsed` | `boolean` | 侧栏是否收起 |
| `migrate` | `Row \| null` | 待迁移的旧版数据（第 11 章） |

六个状态就是整个应用的「全部灵魂」——没有 Redux、没有 Context，第 1 章的决策四兑现。

### 副作用（两个 useEffect）

**① 挂载时跑一次**（依赖数组为空 `[]`）：

```tsx
useEffect(()=>{
  refresh().catch(e=>setToast(e.message));                                  // 拉全局数据
  const raw=localStorage.getItem('testpilot-personal-workbench-v1');        // 检查旧版数据
  if(raw){try{setMigrate(JSON.parse(raw));}catch{/* ignore */}}
},[]);
```

- `refresh` 把 `/api/bootstrap` 拉回来塞进状态——**这是前端的第一个也是最重要的请求**；
- 第二段读取 localStorage 里第一代原型的数据键 `testpilot-personal-workbench-v1`——存在就弹迁移窗（第 11 章完整讲）；
- `catch{/* ignore */}` 是「解析失败无害」的显式表达（坏数据当不存在）。

**② toast 自动消失**：

```tsx
useEffect(()=>{
  if(!toast)return;
  const timer=setTimeout(()=>setToast(''),2800);
  return ()=>clearTimeout(timer);   // 清理函数
},[toast]);
```

每次 `toast` 变化跑一次：设一个 2.8 秒的定时器，到点清空。**返回的清理函数**是这里的关键——toast 在 2.8 秒内又变了一次（新提示顶掉旧的），React 会先执行上一次的清理（`clearTimeout`）再设新定时器，保证「旧提示不会提前把新提示关掉」。

### 守卫：没有数据就不渲染

```tsx
if(!bootstrap) return <div className="loading"><Loader2 className="spin"/><span>正在准备个人工作台…</span></div>;
```

**提前 return 模式**：bootstrap 为 null 时只渲染一个转圈加载页。它保证后面所有 JSX 里的 `bootstrap.counts` 一定安全——**用类型系统之外的方式消灭了「数据未就绪」的空值判断**（全项目只判这一次）。`loading` 与 `spin` 类来自 6.5 的样式。

> 注意 `useEffect` 必须写在提前 return **之前**——Hooks 的调用顺序在任何一次渲染中都必须一致，中途 return 会破坏顺序导致报错。

### 渲染：props 工具箱 + 三个区域

```tsx
const props={bootstrap,refresh,setPage,setDrawer,notify:setToast};
```

把 App 的「能力」打包成一个对象——每个页面组件都收到**同一份工具箱**：数据（bootstrap）、刷新（refresh）、跳页（setPage）、开抽屉（setDrawer）、弹提示（notify）。页面想跳转、想提示，都用工具箱里的方法，而不是自己造轮子。第 1 章说的「props 逐层传递完全可控」就指这个（它的代价见「要点与坑」第 3 条）。

渲染结构四区：

1. **`<aside className="sidebar">`**——品牌区（`brand-mark` 那个旋转的黄色 T）、收起按钮（`collapse`，`aria-label` 是无障碍属性——好习惯）、导航（`NAV.map`：`page===item.id` 加 `active` 类、序号 `String(index+1).padStart(2,'0')` 生成 `01`–`13`）、底部连接状态（「本机数据库已连接 / 127.0.0.1:3344」——静态文案，纯装饰）；

### ⚠️ 要点与坑

1. **StrictMode 会让 effect 跑两次（开发模式）**——你会看到 `/api/bootstrap` 被请求两次。这不是 bug：React 故意在开发模式重复执行 effect（并执行清理），暴露「缺清理函数」的副作用问题。GET 请求幂等所以无害；等第 8 章出现 POST 时，注意它写在**事件回调**里（不受此影响）；
2. **`&&` 左值的陷阱**——`{count && <X/>}` 在 `count` 为 `0` 时会把数字 `0` 渲染出来。本项目所有 `&&` 左值都是字符串比较（安全）；但你自己写新代码时记住这个坑；
3. **props 全量传递的代价**——`{...props}` 让每个页面都拿到所有能力，简单但**耦合宽**且类型是 `any`（改错了不会有类型报错）。规模变大时应定义 `Props` 接口收窄每个页面的入参——本项目选择「够用就好」；
4. **bootstrap 失败会永远停在加载页**——`refresh().catch` 只弹了 toast，没有错误兜底页/重试按钮（验证 E 能看到）。这是真实项目的已知粗糙点；要改进可以在守卫里加「重试」按钮（扩展方向）；
5. **`API` 方法里的 `this`**——务必以 `API.get(...)`、`API.list(...)` 形式调用；解构（`const { get } = API`）后调用会因 `this` 丢失而报错；
6. **`body{min-width:1180px}`**——这是**故意**的桌面假设：窗口更窄时出现横向滚动条，而不是把侧栏挤变形。布局在 1280px 以下有降级（第 11 行的媒体查询）；
7. **字体来自 Google Fonts（第 1 行 @import）**——离线时回退到 `system-ui`（`font-family` 的兜底顺序就是为此设计），只是字形不同、不会崩。
