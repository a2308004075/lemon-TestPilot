## 0. 项目全景与代码地图

### 0.1 成品是什么

TestPilot 是一个**只在你自己电脑上运行**的测试工作台：数据保存在本机 SQLite 文件里，默认只有 `127.0.0.1:3344` 能访问，AI 只用你自己配置的模型。

![工作台首页](./手册截图/01-工作台首页.png)

它的主线业务流程是：

> 粘贴一段材料（Bug 现象/需求/日志/SQL）→ 系统识别该做什么 → 按固定顺序执行分析 → 生成结构化结果 → 人工复核 → 沉淀进知识库 → 汇总成测试报告

打开[用户操作手册](./用户操作手册.md)可以逐页看到 13 个功能模块的最终形态。这份教学文档讲的，就是如何把这些东西一步步做出来。

### 0.2 架构总览

整个系统只有**一个进程**，结构极其简单：

```
┌────────────────────────────── 你的电脑 ──────────────────────────────┐
│                                                                      │
│   ┌─────────────┐        HTTP (JSON)        ┌─────────────────────┐  │
│   │   浏览器     │  ◄──────────────────►    │  node server.mjs    │  │
│   │  React 前端  │   /api/* → 业务接口       │  （唯一后端进程）      │  │
│   └─────────────┘   /*     → 页面/静态资源   │                     │  │
│                                             │  ├ handleApi()      │  │
│                                             │  │   ├ 通用资源层    │  │
│                                             │  │   └ workbench-api│  │
│                                             │  └ 静态文件/ dist   │  │
│                                             └─────────┬───────────┘  │
│                                                       │              │
│                             ┌─────────────────────────┴───────────┐  │
│                             │ data/testpilot.sqlite （SQLite 文件） │  │
│                             │ data/keys/*.dpapi  （加密的 API Key） │  │
│                             └─────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────────────┘
```

用一次真实操作把整条链路串起来（后面每章都会回到这张"地图"）：

1. 你在浏览器输入一段 Bug 描述，点击"按流程执行"；
2. 前端 `fetch('/api/workbench/runs', { method:'POST', body: … })`；
3. `server.mjs` 收到请求，发现路径以 `/api/workbench` 开头，转交给 `workbench-api.mjs`；
4. 工作流引擎：用触发词匹配出 4 条"路由"→ 检查材料缺不缺必填信息 → 判定风险等级 → 把每个路由的工作流步骤写入数据库 → 返回完整执行记录；
5. 前端把返回的 JSON 渲染成"执行结果卡片"；
6. 这条记录永久保存在 `workflow_runs` 表里，打开"执行记录"页随时可查、可复核。

现役核心代码只有 8 个文件、约 600 行（因压缩风格，信息量约等于常规写法 3000+ 行）：

### 0.4 真实代码的阅读技巧

真实文件采用压缩风格，读之前先接受三个事实：

1. **一行就是一段逻辑**。比如 `server.mjs` 第 100 行是一条完整的"创建任务"接口（读体 → 校验 → INSERT → 审计 → 返回），拆开写大约 15 行；
2. **用 IDE 格式化只会读取不写回**。在编辑器里用 `Alt+Shift+F` 临时格式化对照学习是可以的，但不要提交格式化结果——项目刻意保持压缩风格；
3. **先看函数边界，再看细节**。`const fn=()=>{…}`、`if(…)return …` 这类结构就是天然的段落标记。

## 1. 技术选型：为什么这样搭

一个真实项目的第一课永远是"**我该用什么**"。先看结论（`package.json` 的全部直接依赖）：

```json
"dependencies": {
  "jspdf": "^4.2.1",        // 报告导出 PDF
  "lucide-react": "^1.32.0", // 图标
  "react": "^19.2.8",        // 前端框架
  "react-dom": "^19.2.8",
  "xlsx": "^0.18.5"          // 用例导出 Excel/CSV
},
"devDependencies": {
  "@types/react": "^19.2.18", "@types/react-dom": "^19.2.4",
  "@vitejs/plugin-react": "^6.0.5", "typescript": "^7.0.2", "vite": "^8.2.1"
}
```

注意**没有出现的东西**：没有 Express/Koa、没有 ORM、没有路由库、没有 UI 组件库、没有状态管理库、没有 CSS 框架。这不是偷懒，而是这个项目的三条选型原则。

### 1.1 原则一：依赖最小化

每多一个依赖，就多一份升级负担和安全面。这个项目的用户是"个人"，功能规模可控，所以：

- **UI 组件库？** 不需要——自己写 `panel`、`badge`、`table` 这些基础样式（CSS 变量 + 语义类名），完全可控且体积小；
- **路由库？** 不需要——页面切换只是一个 `useState`（见 6.2，含取舍分析）；
- **状态管理库？** 不需要——全局只共享一份 `bootstrap` 数据，用 props 传递足够。

### 1.2 原则二：后端用 Node 原生 `http`

不用框架，`server.mjs` 直接 `import http from 'node:http'`。理由：

- 本项目 API 形态高度统一（REST + JSON），框架带来的"路由分组/中间件"收益有限；
- 学习价值高——你会亲手实现路由分发、请求体解析、错误兜底，这些概念在任何框架里都通用；
- 代价要有数：原生写法要自己处理"读请求体、404 兜底、异常捕获"（第 3 章会完整实现）。

### 1.3 原则三：数据层用 Node 24 内置的 `node:sqlite`

```js
import { DatabaseSync } from 'node:sqlite';
```

- **零安装**：不需要 `npm install sqlite3`（原生模块编译经常是新手噩梦），Node 24 自带；
- **单文件**：整个数据库就是 `data/testpilot.sqlite` 一个文件，备份 = 复制文件；
- **同步 API**：`db.prepare(…).get()` 同步返回，个人工具的并发量下完全够用，代码更直白；
- 注意：JSON 字段做结构化存储，是"轻量 ORM"的替代方案（第 4 章详解）。

### 1.4 前端为什么是 React 19 + TypeScript + Vite

- **React**：组件化适合这种"多个相似列表页 + 大量复用模式"的界面；
- **TypeScript**：项目里大段业务是"数据结构在流转"（任务/用例/知识都是 JSON 对象），类型让重构安全；`npm run build` 会先跑 `tsc --noEmit`，类型错误直接拦住；
- **Vite**：开发态提供极快的热更新（改代码浏览器自动刷新）；构建态把 React/TS 打包成静态文件。两者一个配置搞定（7 行的 `vite.config.ts`）。

### 1.5 部署形态：单进程 + 一键脚本

生产环境不做 CI/CD、不做 Docker——因为受众是个人用户：

- 生产 = `dist/`（前端构建产物）+ `server.mjs`（后端），**同一个进程同时提供两者**；
- `start.bat` / `start.command` 双击即用；`npm run deploy` 负责"检查环境 → 装依赖 → 构建 → 启动 → 打开浏览器"（第 10 章逐段讲解）。

> **小结**：这个项目的选型可以概括为一句话——*在"个人本地工具"的约束下，把每一层的复杂度都压到最低，同时保证架构的完整性和可学习性*。

```bash

```

然后按项目的方式改造 `package.json`，逐字段理解：

```json
{
  "name": "testpilot-personal-workbench",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "scripts": {
    "dev": "node server.mjs",
    "build": "tsc --noEmit && vite build",
    "start": "node server.mjs --production",
    "check": "tsc --noEmit",

## 3. 第 1 步 · 后端 HTTP 服务器

### 🎯 本章目标

写出完整的 `server.mjs` 骨架：**一个进程同时提供 JSON API、静态页面、SPA 回退**，并且开发/生产两种模式都能跑。

### 3.1 从 20 行的最小服务器开始

```js
// 教学版：最小的 HTTP 服务器
import http from 'node:http';

const server = http.createServer((req, res) => {
  res.writeHead(200, { 'Content-Type': 'application/json; charset=utf-8' });
  res.end(JSON.stringify({ ok: true, path: req.url }));
});

server.listen(3344, '127.0.0.1', () => {
  console.log('已启动：http://127.0.0.1:3344');
});
```

请求进来 → 回调拿到 `req`/`res` → 写响应。所有后续功能都是在这 20 行上"长"出来的。

### 3.2 路由分发：API 走左边，页面走右边

真实项目的分发逻辑（展开版）：

```js
const server = http.createServer(async (req, res) => {
  const url = new URL(req.url, `http://${req.headers.host}`);

  // ① API 请求：交给纯逻辑处理，与页面服务完全解耦
  if (url.pathname.startsWith('/api/')) {
    await handleApi(req, res, url);
    return;
  }

  // ② 开发模式：Vite 中间件接管（提供热更新、TSX 编译）
  if (vite) {
    vite.middlewares(req, res, () => send(res, 404, { error: '页面不存在' }));
    return;
  }

  // ③ 生产模式：直接读 dist 里的静态文件
  //    ……（见下方静态服务代码）
});
```

这就是"**API 与页面共用一个进程但互不干扰**"的设计——`/api/*` 是数据世界，其余是界面世界。

### 3.3 静态文件服务与两个安全细节

生产模式下服务器的职责：把 `dist/` 里的文件按 URL 路径发给浏览器。展开版实现：

```js
const types = {
  '.html': 'text/html; charset=utf-8',
  '.css':  'text/css; charset=utf-8',
  '.js':   'text/javascript; charset=utf-8',
  '.svg':  'image/svg+xml',
  '.json': 'application/json; charset=utf-8'
};

const base = join(root, 'dist');
// 细节①：防目录穿越——把 ../ 序列剥掉，保证只能访问 dist 内部
const requested = normalize(url.pathname).replace(/^(\.\.(\/|\\|$))+/, '');
let filePath = join(base, requested === '/' ? 'index.html' : requested);
// 细节②：SPA 回退——文件不存在（如未来加了前端路由）就发 index.html
if (!existsSync(filePath) || (await stat(filePath)).isDirectory()) {
  filePath = join(base, 'index.html');
}
const content = await readFile(filePath);
res.writeHead(200, {
  'Content-Type': types[extname(filePath)] || 'application/octet-stream',
  'Cache-Control': 'no-store'   // 本地工具，禁用缓存保证"改完即所见"
});
res.end(content);
```

**为什么"缺 .svg/.woff 等 MIME"会有问题？** 浏览器对部分资源类型很严格（错误的 MIME 会导致脚本拒绝执行），真实项目只列了实际用到的类型——这是够用就好的典型案例，你若扩展字体等资源记得补 MIME 表。

### 3.4 开发/生产双模式

服务器的模式由启动参数决定：

```js
const production = process.argv.includes('--production');

if (production && !existsSync(join(root, 'dist/index.html'))) {
  throw new Error('缺少构建文件，请使用 start.command 或 start.bat 完成部署。');
}

let vite;
if (!production) {
  const { createServer } = await import('vite');   // 动态导入，生产环境不加载 vite
  vite = await createServer({ root, server: { middlewareMode: true }, appType: 'spa' });
}
```

- **开发态**（`npm run dev`）：服务器进程里"嵌入"一个 Vite 实例，由它即时编译 TSX、推送热更新。浏览器看到的还是 `127.0.0.1:3344`，但你不需要单独跑 `vite` 命令——这就是 `dev` 脚本是 `node server.mjs` 而不是 `vite` 的原因；
- **生产态**（`npm start` / 部署脚本）：Vite 完全不加载，只服务 `dist/` 静态文件，依赖更少、启动更快；
- `await import('vite')` 用动态导入就是为了这个目的——只有开发时才付出加载代价。

### 🔍 对照真实项目

- `server.mjs` 第 122–127 行：MIME 表、生产校验、Vite 中间件、分发服务器、错误监听、监听启动——全部在这 6 行里；
- `server-runtime.mjs`（3 行）是兼容入口，只是 `import './server.mjs'`，供旧脚本调用。

### ⚠️ 要点与坑

- **端口占用**要优雅报错，而不是直接崩栈：

```js
server.on('error', error => {
  console.error(`服务启动失败：${error.code}，请检查端口 ${port} 是否被占用。`);
  process.exitCode = 1;
});
```

- `Cache-Control: no-store` 是本地工具的正确选择：宁可牺牲一点性能也要保证"刷新即最新"；
- `new URL(req.url, 'http://' + req.headers.host)` 统一解析路径与查询参数，比手动切字符串可靠得多。

## 4. 第 2 步 · 数据层设计（SQLite）

### 🎯 本章目标

设计出全部 16 张表，理解每一张存在的理由；掌握 `node:sqlite` 的用法与两个关键设计（JSON 列、命名转换层）。

### 4.1 为什么数据模型先行

后端功能可以概括为一句话：**把界面上的操作翻译成对数据的读写**。所以开发顺序是：

```
表结构 → 通用读写能力 → 业务接口 → 界面
```

表结构一旦定好，后面所有代码都是"围绕数据打转"。这也是为什么真实项目中建表 SQL 放在 `server.mjs` 最顶部（启动即建表）。

### 4.2 node:sqlite 快速上手

```js
import { DatabaseSync } from 'node:sqlite';
import { join } from 'node:path';

const db = new DatabaseSync(join(root, 'data/testpilot.sqlite'));

// 两个必须记住的 PRAGMA：
db.exec('PRAGMA journal_mode=WAL; PRAGMA foreign_keys=ON;');
// WAL：写入不阻塞读取（安全且更快）；foreign_keys=ON：外键约束生效
```

三种最常用的操作：

```js
db.exec(`CREATE TABLE IF NOT EXISTS ...`);            // 建表/多语句执行

const stmt = db.prepare('SELECT * FROM tasks WHERE id=?');
stmt.get(id);          // 查一行，返回对象（无则 undefined）
stmt.all(pageSize);    // 查多行，返回数组

db.prepare('INSERT INTO tasks VALUES(?,?,?)').run(a, b, c);  // 写操作
```

注意 API 是**同步**的——个人工具不需要连接池和异步等待，代码直白是最大的优点。

### 4.3 十六张表全图

按职责分四组记忆（真实定义见 `server.mjs` 第 19–32 行与 `workbench-api.mjs` 第 39–44 行）：

**第一组：组织与系统**

| 表 | 作用 | 设计要点 |
| --- | --- | --- |
| `modules` | 项目→模块→子模块三级结构 | `sort_order` 控制显示顺序，`status` 支持停用 |
| `settings` | 键值配置（格式模板等） | `key + value_json`，万能兜底表 |
| `audit` | 操作审计流水 | `entity_type + entity_id + action`，只增不改 |
| `migrations` | 迁移完成标记 | `key` 主键天然实现幂等 |

**第二组：业务资产**

| 表 | 作用 | 设计要点 |
| --- | --- | --- |
| `cases` | 测试用例 | `code` 唯一；`version` 编辑时 +1；`archived` 软删除 |

| 表 | 作用 | 设计要点 |

**第四组：工作流引擎（第 8 章的主角）**

### 4.4 关键设计一：JSON 列

个人工具的典型做法：结构化要求高的字段建列，**内容形状多变的字段用 JSON 存**。例如任务的输入输出：

```sql
input_json  TEXT NOT NULL DEFAULT '{}',
result_json TEXT NOT NULL DEFAULT '{}'
```

好处是免去了十几张子表；代价是 SQL 层面不能直接查询 JSON 内部（个人工具场景可以接受）。读取时统一容错解析：

```js
const parse = (value, fallback = {}) => {
  try { return JSON.parse(value); } catch { return fallback; }
};
```

### 4.5 关键设计二：命名转换层

数据库按 SQL 惯例用 `snake_case`（`module_id`），前端按 JS 惯例用 `camelCase`（`moduleId`）。如果每个接口手动转换，几十个字段必定写错。解决方案是**一个统一的转换函数**（`server.mjs` 第 85 行）：

```js
function mapRow(resource, row) {
  if (!row) return null;

  // ① snake_case → camelCase（正则替换下划线后的字母为大写）
  const camel = Object.fromEntries(Object.entries(row).map(([k, v]) =>
    [k.replace(/_([a-z])/g, (_, c) => c.toUpperCase()), v]));

  // ② JSON 列自动反序列化：input_json → input
  for (const key of ['inputJson','resultJson','contentJson','dataJson','stepsJson','valueJson']) {
    if (key in camel) { camel[key.replace('Json','')] = parse(camel[key]); delete camel[key]; }
  }

  // ③ 顺带补全展示字段：有 moduleId 就附上 moduleLabel（供前端直接显示三级名称）
  if (camel.moduleId) camel.moduleLabel = moduleLabel(camel.moduleId);

  // ④ providers 表不进数据库的字段用派生值表示"是否已配置 Key"
  if (resource === 'providers') camel.keyConfigured = Boolean(camel.keyMask);

  return camel;
}
```

**凡是从数据库出来的行，都必须过这一层**——前端从此只认一种命名和一种数据结构。这是整个后端最重要的"防腐层"。

### 4.6 seed：让空数据库活起来

第一次启动时如果库是空的，`seed()` 会写入一套演示数据：5 个模块、4 条用例、4 条知识、4 个任务、1 份回归、1 份报告、1 条链路模板、4 个模型厂商配置。

幂等保护只有一行：

```js
if (db.prepare('SELECT COUNT(*) AS n FROM modules').get().n) return;
```

**为什么需要 seed？** 一个全新安装的工作台第一次打开全是空列表，用户无从下手；演示数据让每个功能页"一打开就有东西可看"，同时为开发调试提供了固定基线。

### ⚠️ 要点与坑

- `DatabaseSync` 的 `run` 参数只能用**标量**（字符串/数字/null）——对象必须先 `JSON.stringify`（项目里封装了 `json()`）；
- 删数据用 `archived` 标志（软删除），列表查询统一 `where: 'archived=0'`——个人工具最怕误删；
- `makeId()` 用 `crypto.randomUUID().slice(0, 8)` 生成 `task_3f8a1c2d` 这类前可读、后随机的 ID，兼顾调试可读性与唯一性。

## 5. 第 3 步 · 通用 REST API 层

### 🎯 本章目标

用"配置驱动"的方式，十条路由支撑起八个资源的完整增删改查，并实现状态机、引用保护与审计。

### 5.1 设计目标：消灭重复代码

8 个资源（tasks/cases/knowledge/regressions/reports/workflows/modules/providers）如果每个都手写"分页 + 搜索 + 过滤 + 排序"，会有 8 份几乎相同的代码。真实项目的方案：**用一张配置表描述差异，用一个通用函数处理共性**。

### 5.2 resources 配置表

```js
const resources = {
  tasks:       { table:'tasks',       search:['title','type','status','review_status'], order:'updated_at' },
  cases:       { table:'cases',       search:['code','title','priority','status'],      order:'updated_at', where:'archived=0' },
  knowledge:   { table:'knowledge',   search:['title','category','content','status'],   order:'updated_at' },
  regressions: { table:'regressions', search:['title','status'],                        order:'updated_at' },
  reports:     { table:'reports',     search:['title','project_name','verdict'],        order:'updated_at' },
  workflows:   { table:'workflows',   search:['name','status'],                         order:'updated_at' },
  modules:     { table:'modules',     search:['project_name','module_name','submodule_name','status'], order:'sort_order' },
  providers:   { table:'providers',   search:['name','model'],                          order:'name' }
};
```

每个资源的四要素：表名、可搜索的列、排序字段、固定过滤条件。**加新资源 = 加一行配置 + 加建表 SQL**。

### 5.3 通用列表查询（教学展开版）

```js
function listResource(resource, url) {
  const c = resources[resource];
  if (!c) return null;

  // ① 分页参数：pageSize 只允许白名单值，防止恶意大页
  const page = Math.max(1, Number(url.searchParams.get('page') || 1));
  const pageSize = [20, 50, 100].includes(Number(url.searchParams.get('pageSize')))
    ? Number(url.searchParams.get('pageSize')) : 20;

  // ② 关键词：对配置里的 search 列做 OR LIKE
  const clauses = c.where ? [c.where] : [];   // 固定条件（如 archived=0）
  const params = [];
  const q = (url.searchParams.get('q') || '').trim();
  if (q) {
    clauses.push(`(${c.search.map(k => `${k} LIKE ?`).join(' OR ')})`);
    params.push(...c.search.map(() => `%${q}%`));
  }

  // ③ 通用等值过滤：任何资源都支持这几个键
  ['type','status','module_id','category','priority','risk'].forEach(key => {
    const value = url.searchParams.get(key);
    if (value) { clauses.push(`${key}=?`); params.push(value); }
  });

  // ④ 先查总数（前端分页器需要），再查当前页
  const where = clauses.length ? `WHERE ${clauses.join(' AND ')}` : '';
  const total = db.prepare(`SELECT COUNT(*) AS n FROM ${c.table} ${where}`).get(...params).n;
  const rows = db.prepare(`SELECT * FROM ${c.table} ${where} ORDER BY ${c.order} DESC LIMIT ? OFFSET ?`)
                 .all(...params, pageSize, (page - 1) * pageSize);

  return { items: rows.map(r => mapRow(resource, r)), page, pageSize, total,
           pages: Math.max(1, Math.ceil(total / pageSize)) };
}
```

**注意安全点**：表名、列名全部来自代码内的配置（不是用户输入），用户输入只出现在 `?` 占位符里——这就避免了 SQL 注入。

### 5.5 两个值得精读的业务逻辑

**① 回归进度自动计算**——前端只负责改某一项的状态，进度永远由服务端算：

```js
const items = value.items || [];
const complete = items.filter(i => !['未执行','阻塞'].includes(i.status)).length;
const progress = items.length ? Math.round(complete / items.length * 100) : 0;
```

（"已完成"的判定规则在这里集中定义，保证前后端口径永远一致。）

**② 知识撤销的引用保护**——删除前先查 `relations` 表，有下游引用就拒绝并告知来源：

```js
if (d.action === 'withdraw') {
  const deps = db.prepare(
    "SELECT * FROM relations WHERE target_type='knowledge' AND target_id=? AND active=1"
  ).all(parts[2]);
  if (deps.length) return send(res, 409, { error:'存在有效关联，不能撤销入库', dependencies: deps });
}
```

前端拿到 `409` 后把 `dependencies` 渲染进提示语——这就是"数据完整性由数据层守护，界面只负责传达"的实例。

### 5.6 审计与统一错误处理

每个写操作成功后调用一行审计：

```js
function audit(type, entityId, action, detail = '') {
  db.prepare('INSERT INTO audit(entity_type, entity_id, action, detail, created_at) VALUES(?,?,?,?,?)')
    .run(type, entityId, action, detail, now());
}
```

整个 `handleApi` 用一层 `try/catch` 包住（`server.mjs` 第 95–119 行）：

```js
try { /* 所有路由 */ }
catch (error) {
  console.error(error);
  return send(res, 500, { error: error.message || '服务端错误' });
}
```

业务要求"任何接口都不允许把服务器搞崩"——异常必须转成 JSON 错误响应。

### ⚠️ 要点与坑

- `readBody` 要处理空请求体：`chunks.length ? JSON.parse(...) : {}`，否则 DELETE/PATCH 无体请求会抛错；
- PATCH 的更新模式是"**字段合并**"：`d.title ?? c.title`——只更新传来的字段，没传的保持原值；
- 返回列表时务必带上 `total/pages`，否则前端分页器无法工作。

## 6. 第 4 步 · 前端骨架

### 🎯 本章目标

搭出 App 外壳：侧边导航 + 页面切换 + 全局数据加载 + 提示反馈。完成后，每个功能页都只是"往壳里放组件"。

### 6.1 入口与全局数据（bootstrap）

前端启动时只请求一次 `/api/bootstrap`，拿到全局基础数据（各表计数、模块列表、模型配置）：

```tsx
function App() {
  const [bootstrap, setBootstrap] = useState<Row | null>(null);
  const refresh = async () => setBootstrap(await API.request('/bootstrap'));

  useEffect(() => { refresh().catch(e => setToast(e.message)); }, []);

  if (!bootstrap) return <div className="loading"><Loader2 className="spin"/>正在准备个人工作台…</div>;
  // …渲染外壳
}
```

三个要点：

- **加载守卫**：`bootstrap` 为空时渲染 loading——保证后面所有组件拿到的 `bootstrap` 一定非空；
- **refresh 模式**：任何页面新增了数据，调用 `refresh()` 就刷新全局计数（首页"数据资产"卡片的数字就是这样保持实时的）；
- `useState<Row | null>` 里的 `Row = Record<string, any>`：前端对接口返回数据的宽松类型约定（后端第 4 章的 mapRow 才是真正的"类型契约"）。

### 6.2 页面切换：为什么不用路由库

```tsx
type PageKey = 'dashboard'|'assistant'|'runs'|'cases'|/* …共 13 个 */;

const [page, setPage] = useState<PageKey>('dashboard');

// 侧边导航：点了就 setPage
<nav>{NAV.map(item =>
  <button className={page === item.id ? 'active' : ''} onClick={() => setPage(item.id)}>
    {item.icon}{item.label}
  </button>)}</nav>

// 内容区：条件渲染
{page === 'dashboard' && <Dashboard {...props} />}
{page === 'cases' && <CasesPage {...props} />}
{/* … */}
```

**取舍分析**（面试也常问）：

| | 方案 A：useState 切换（本项目） | 方案 B：react-router |
| --- | --- | --- |
| 依赖 | 0 | 1 个库 |
| 刷新后保持当前页 | ❌ 回到首页 | ✅ |
| URL 可分享/可收藏 | ❌ | ✅ |
| 适合场景 | 本地个人工具，无需分享链接 | 多用户 Web 应用 |

本地工作台打开就是从头用起，"刷新回到首页"完全可以接受——用一行 `useState` 换掉一个依赖，这就是选型原则的又一次实践。

### 6.3 API 封装

所有请求收敛到一个对象里（`main.tsx` 第 35–41 行），前端组件从不直接写 `fetch`：

```ts
const API = {
  async request(path, options) {
    const res = await fetch(`/api${path}`, {
      headers: { 'Content-Type': 'application/json' },
      ...options
    });
    const data = await res.json();
    if (!res.ok) throw new Error(data.error || '请求失败');  // 错误统一抛出
    return data;
  },
  list(resource, params = {}) { /* 过滤空值后拼查询串 */ },
  get(resource, id)   { return this.request(`/${resource}/${id}`); },
  post(resource, data){ return this.request(`/${resource}`, { method:'POST', body: JSON.stringify(data) }); },
  patch(resource, id, data) { /* 同理 */ }
};
```

设计意图：

- **错误即异常**：HTTP 非 2xx 时把后端的 `{error}` 消息包成 `Error` 抛出，组件里统一 `try/catch + notify(e.message)` 处理；
- **URLSearchParams 过滤空值**：`?q=&status=` 这类空参数不拼进查询串，后端也不用判断空字符串。

### 6.4 样式体系：一个文件 + CSS 变量

`src/styles.css` 的设计约定（压缩后只有 14 行，但结构清晰）：

1. **`:root` 定义设计令牌**（主题黄、背景、边框、文字色等 CSS 变量）——换肤只需要改这一处；
2. **语义化类名**：`panel`（面板卡片）、`table-wrap`（表格容器）、`badge`（状态徽标）、`drawer`（侧滑详情）、`two-col`（两栏布局）、`filterbar`、`pagination`、`toast`——组件里复用这些类，不写内联样式；
3. **桌面优先**：`body { min-width: 1180px }`——窄了会出现横向滚动条。个人工具不做响应式移动端，这是刻意的取舍；
4. **文档级滚动**：整个页面用浏览器原生的滚动条（`min-height: 100vh` + 侧栏 `position: fixed`），而不是在某个容器内滚动——截图脚本"全页截图"因此特别简单（见记忆：全页截图需要先设小视口测量高度）。

### 7.1 模式一：列表页（以用例库为例）

几乎每个模块都有列表页，骨架完全一致。教学展开版：

```tsx

需要在脑子里固化四个习惯：

1. **筛选条件即状态**：`q/moduleId/priority` 都是 `useState`，变更时顺手 `setPage(1)`（换筛选回到第一页，否则可能停在空页）；
2. **`useEffect` 依赖数组驱动重新请求**：条件变 → load() 自动重跑，不需要手动管理"什么时候刷新"；
3. **行点击 = 打开抽屉**：传 `{ type, item }` 给全局 drawer 状态；
4. **总数与分页由后端返回**：前端不自己算。

> 用例库还多了一个**模块树**侧栏：`groupModules(modules, cases)` 把"扁平的用例数组"按 项目→模块→子模块 分组渲染。这是"展示层做数据整形"的典型例子——后端只给平数据，树形结构在前端拼。

### 7.2 模式二：详情抽屉（DetailDrawer 分发器）

```tsx
function DetailDrawer({ drawer, close, notify, refresh }) {
  const [item, setItem] = useState(drawer.item);

  useEffect(() => {
    // 打开时拉取最新数据 + 操作审计时间线
    if (drawer.type === 'case') {
      API.get('cases', item.id).then(setItem);
      API.request(`/audit?type=case&id=${item.id}`).then(r => setAudit(r.items));
    }
  }, [item.id, drawer.type]);

  return (
    <div className="overlay" onMouseDown={e => e.target === e.currentTarget && close()}>
      <aside className="drawer">
        <header>{item.title}<button onClick={close}>×</button></header>
        <div className="drawer-body">
          {drawer.type === 'case'      && <CaseDetail item={item} />}
          {drawer.type === 'knowledge' && <KnowledgeDetail item={item} notify={notify} />}
          {drawer.type === 'task'      && <TaskDetail item={item} notify={notify} />}
          {drawer.type === 'report'    && <ReportDetail item={item} notify={notify} />}
          {audit.length > 0 && <AuditTimeline items={audit} />}
        </div>
      </aside>
    </div>

细节都很讲究：

- **"点击遮罩关闭"**：`e.target === e.currentTarget` 判断点击的是否是遮罩本身（而不是抽屉内容冒泡上来的事件）；
- **打开时重新拉取**：列表里的 `item` 可能是旧数据，抽屉展示永远用最新版本；
- **审计时间线**：底部"操作记录"直接来自 `/api/audit`——第 5 章埋的审计表在这里兑现了价值；
- **动作按钮按状态渲染**：知识"待审核"才显示"审核通过并发布"，"已发布"才显示"撤销入库"——界面永远不出现非法操作。

### 7.3 模式三：表单（新增用例为例）

```tsx
function CaseEditor({ modules, notify, done }) {
  const [form, setForm] = useState({ title:'', moduleId:'', priority:'P1', steps:'', expected:'' });
  const set = (k, v) => setForm(s => ({ ...s, [k]: v }));

  async function save() {
    if (!form.title || !form.steps || !form.expected) {
      notify('请补齐标题、步骤和预期结果');   // ① 前端先兜底校验
      return;
    }
    await API.post('cases', {
      ...form,
      content: { steps: form.steps.split('\n').filter(Boolean), expected: form.expected }
    });
    notify('用例已保存到用例库');
    done();   // ② 回调：切回列表 + 重新 load()

  return <section className="panel editor">
    <Field label="用例标题" required><input value={form.title} onChange={e => set('title', e.target.value)} /></Field>
    <Field label="测试步骤（每行一步）" required full>

    </Field>
    <button className="button primary" onClick={save}>保存用例</button>
  </section>;

两个模式值得记住：

- **受控表单 + 单一 set 助手**：一个 `set(k, v)` 处理所有字段，比每个字段写一个 handler 干净得多；
- **`done` 回调设计**：子组件不关心"保存后去哪"，由父组件决定（切页签、刷新列表、更新全局计数）——这是 React 里最常用的组件通信约定。

## 8. 第 6 步 · AI 工作流引擎（全书核心）

### 🎯 本章目标

理解整个项目最有价值的设计：**如何把一个不稳定的"AI 能力"包装成稳定、可追溯、可回归的工程系统**。

### 8.1 设计目标：四条铁律

先看系统对用户的承诺（前端底部"全局安全规则"条）：

1. **不跳步骤**——命中几条路由就按固定顺序全跑；
2. **证据不足时明确标记**——缺什么直说，不用猜测填充；
3. **不编造知识标题或 Bug 编号**——引用只能来自知识库真实检索；
4. **AI 不批准上线**——P0/P1 与 Prompt 测试必须人工复核。

这四条不是文案，而是分别落在代码结构里（路由排序、缺项检查、输出骨架、复核状态机）。

### 8.2 入口定义：ENTRY_DEFS 数据驱动

7 个标准入口全部由一张定义表描述（`workbench-api.mjs` 第 1–9 行）。摘取"Bug 分析"这一条（展开格式）：

```js
{
  id: 'bug_analysis',
  name: 'Bug 分析',
  icon: 'bug',
  // 触发词：材料里出现任意一个，就命中这个入口
  triggers: ['bug','缺陷','复现','实际结果','预期结果','报错','异常'],
  // 必填信息：执行前逐项检查，缺了就标记出来
  required: ['问题标题','复现步骤','实际结果','预期结果','环境'],
  // 知识来源：本次分析允许引用的知识库分类
  knowledge: ['历史 Bug 库','日志规律库','SQL 经验库','业务规则库'],
  // 工作流步骤：命中后严格按这个顺序展开执行轨迹
  workflow: ['校验输入','描述现象','识别影响模块','给出日志方向','给出 SQL 方向',
             '检索历史 Bug','生成回归范围','判断风险','标记人工复核']
}
```

先想清楚一个设计问题：**为什么用"数据定义"而不是"每个入口写一个函数"？**

| | 数据驱动（本项目） | 代码驱动 |
| --- | --- | --- |
| 加新入口 | 加一条对象 | 写一个新函数 + 注册路由 |
| 在线编辑 | 存进 `workbench_assets` 表，用户可在"工作台编排"页改 | 必须改代码重新部署 |
| 前端渲染 | 配置接口直接返回，界面自动出现 | 需要同步维护前端列表 |

代价是定义表必须覆盖所有入口的差异点——本项目通过"统一骨架 + 每入口定制字段"解决（见 8.7）。

7 个入口按 `DEFAULT_ORDER` 排序：`testcase_gen → bug_analysis → log_triage → sql_analysis → regression_list → test_report → prompt_test`，这个顺序决定了多路由执行时谁是"主任务"。

### 8.3 路由算法：从一段材料到执行序列

```js
function routeText(text, selected = []) {
  const lower = text.toLowerCase();

  // ① 触发词全扫描：材料包含任意触发词即命中
  let ids = ENTRY_DEFS
    .filter(e => e.triggers.some(t => lower.includes(t.toLowerCase())))
    .map(e => e.id);

  // ② 用户在界面上手动勾选的入口强制并入（即使没触发词）
  selected.forEach(id => { if (!ids.includes(id)) ids.push(id); });

  // ③ 兜底：什么都没命中时，默认按 Bug 分析处理
  if (!ids.length) ids = ['bug_analysis'];

  // ④ 按固定顺序排序——保证"主任务"（第一个）在任何输入下都稳定
  ids.sort((a, b) => DEFAULT_ORDER.indexOf(a) - DEFAULT_ORDER.indexOf(b));
  return ids;
}
```

拿真实示例走一遍：手册截图里的那段材料（"支付成功后订单仍为待支付…traceId=demo-1024…Lock wait timeout"）会依次命中 `bug_analysis`（复现/实际结果）、`log_triage`（日志/traceId/timeout）、`sql_analysis`（SQL 排查方向）、`regression_list`（回归范围）——所以执行结果就是"1 个主任务 + 3 个辅助任务"，与截图完全对应。

> 为什么不直接用大模型做路由？因为路由是整个系统的"骨架决策"，需要**确定性、零延迟、零成本、可回归**（8.9 的验证案例就依赖它）。大模型只在"内容生成"环节介入。

### 8.4 缺项检查：正则表代替"智能判断"

```js
function fieldPresent(text, field) {
  const rules = {
    '问题标题': /.{5,}/,
    '复现步骤': /复现|步骤|操作|点击|请求/,
    '实际结果': /实际|现象|仍为|报错|失败/,
    '预期结果': /预期|应该|应为/,
    '环境':     /环境|staging|test|prod|生产|测试环境/,
    // … 每个入口的每个必填项都有一条规则
  };
  return rules[field]?.test(text) || false;
}
```

同样的取舍：正则规则简单、透明、可测试。用户看到"缺少必要信息：时间范围、SQL 文本"时，能立刻明白**系统在找什么**——如果换成模型判断，这句提示就成了不可解释的黑盒。

**缺项不是拦截，而是降级**：材料不全时仍然可以执行，只是生成"待补充"状态的记录，等用户补齐后重新执行。

### 8.5 预检 preflight：把"为什么"讲给用户听

点击"识别任务与缺项"时调用 `POST /api/workbench/preflight`，返回结构（教学简化）：

```json
{
  "routes": [
    { "id": "bug_analysis", "name": "Bug 分析", "role": "主任务",
      "missing": [], "completeness": 100 },
    { "id": "log_triage", "name": "日志排查", "role": "辅助任务",
      "missing": ["时间范围"], "completeness": 67 }
  ],
  "mainRoute": "bug_analysis",
  "missing": ["时间范围", "SQL 文本"],
  "canRun": true,
  "policy": "sequential_when_matched"
}
```

`completeness` = （必填项数 − 缺项数）÷ 必填项数，界面上的百分比进度条就来自它。`policy: sequential_when_matched`（命中即顺序执行）是整个引擎的执行语义，也被展示在界面上——**把设计决策变成用户可见的契约**。

### 8.6 执行：从点击到落库的完整管道

`POST /api/workbench/runs` 做九件事（真实实现是 1 行约 1500 字符，见 `workbench-api.mjs` 第 58 行）：

```
① 路由        routeText(text, selectedRoutes)
② 缺项汇总    所有路由的 missing 并集去重
③ 风险分级    材料含"生产/资损/重复扣款/数据丢失/安全/p0" → P0
              含"失败/异常/超时/锁等待" → P1；其余 P2
④ 组装结果    result.sections[路由id] = buildOutput(...)（见 8.7）
              result.routeSummary = [{id, name, role, knowledge}]
⑤ 复核策略    P0/P1 或包含 prompt_test → review.required = true
⑥ 写主记录    INSERT INTO workflow_runs（输入、路由、结果、缺项、风险、复核、证据链全量快照）
⑦ 展开步骤    把每个路由的 workflow 数组逐条写入 workflow_run_steps
              （界面"逐步执行轨迹"就来自这张表）
⑧ 证据链      evidence = ['用户原始输入', '知识库：历史 Bug 库', …]
⑨ 返回快照    前端拿到的就是完整 run 对象，直接渲染
```

风险分级用两行正则完成：

```js
const risk = /生产|资损|重复扣款|数据丢失|安全|p0/i.test(text) ? 'P0'
           : /失败|异常|超时|锁等待|lock wait/i.test(text) ? 'P1' : 'P2';
```

**为什么要给机器判定风险？** 因为风险等级直接决定复核策略——P0/P1 强制 `review.required`，这是"AI 不批准上线"铁律的代码化表达。

### 8.7 结构化输出：只给方向，不给结论

每个入口的输出骨架由 `buildOutput` 生成。以 Bug 分析为例（真实字段）：

```js
if (id === 'bug_analysis') return {
  ...common,   // risk_level、human_review_points、need_more_info
  phenomenon: text.slice(0, 180),                    // 现象原文摘录
  affected_modules: ['根据已选三级模块确认'],
  possible_causes: ['从现象推测存在状态同步或事务边界异常，尚需证据验证'],
  recommended_logs: ['按 traceId 串联入口、消息消费和数据库更新日志'],
  recommended_sql: ['核对业务主表与流水表状态、金额及更新时间'],
  related_history_bugs: ['仅展示实际检索命中的知识，不编造 Bug 编号'],
  regression_scope: ['直接变更模块','上下游状态同步','失败与重复请求场景']

仔细读每个字段的措辞——全部是**方向**（"在哪里查"）而不是**结论**（"就是它"）：

### 8.9 案例验证：给规则引擎写"集成测试"

规则引擎最怕的是"改了一个触发词，别处悄悄失效"。解决方案是把一段固定 walkthrough 做成可重复执行的验证案例（`validation_cases` 表）：

```js
// POST /api/workbench/validations/:id
const actual = routeText(row.input_text);                     // 实际命中的路由
const expected = JSON.parse(row.expected_routes_json);        // 期望命中的路由
const passed = expected.every(x => actual.includes(x));       // 期望项全部命中才算通过
// 结果写入 last_result_json：{ actualRoutes, expectedRoutes, passed, checkedAt, rules }
```

- 内置案例 `val_payment` 的期望路由是 `[bug_analysis, log_triage, sql_analysis, regression_list]`，期望规则包括"不跳结论""根因需证据""至少 6 个必回归项""P0/P1 人工复核"；
- 界面上点"运行验证案例"，会显示最近验证时间与实际路由顺序（`bug_analysis → log_triage → sql_analysis → regression_list`）；
- **改完触发词/顺序后跑一遍案例验证，就是发布前的冒烟测试**。

这是"把不确定的智能系统变成可测试的工程系统"最朴素也最有效的做法。

### 8.10 前端交互流（AssistantPage）

`src/workbench.tsx` 里 `AssistantPage` 的状态机：

```
初始态（无预检）
  ├─ 用户粘贴材料 / 点"载入支付异常示例"
  ├─ 点"识别任务与缺项" → POST /preflight → 渲染右侧"执行前检查"面板
  │     （路由列表 + 完整度 + 缺项提示，回答"为什么匹配"）
  └─ 点"按流程执行"     → POST /runs      → 渲染 RunResult（结果卡片 + 复核按钮）
```

三个值得注意的实现细节：

- 输入框 `onChange` 时同时 `setPreflight(null); setRun(null)`——**材料一变，旧的识别结果立即失效**（防止用户对着过期预检结果做决策）；
- `RunResult` 组件被"AI 助手页"和"执行记录抽屉"共用——同一份结果渲染逻辑，两个入口复用；
- 复核按钮调 `PATCH /runs/:id` 后直接把响应 `setRun(r)` 刷新本地状态，无需重新请求。

### ⚠️ 要点与坑

- 新增/修改 `ENTRY_DEFS` 后需要**重启服务**：入口定义在启动时以 `INSERT OR IGNORE` 写入 `workbench_assets` 表（新 id 会自动补插，已有 id 不会覆盖你在编排页的修改）；

- 演示数据里的 `val_payment` 案例初始状态是"待验证"，运行过一次后状态变为"通过"。

## 9. 第 7 步 · 大模型接入与密钥安全

### 🎯 本章目标

接通真实大模型（OpenAI 兼容协议），并理解"API Key 永不落库"的安全设计。

### 9.1 providers 表与配置界面

4 个厂商在 seed 时写入（OpenAI / 通义千问 / DeepSeek / 自定义兼容接口）。关键字段：

```sql
base_url, model, temperature, timeout, max_tokens,
enabled INTEGER,      -- 是否参与分析

```

`key_mask` 的设计是安全核心：**数据库里永远没有真 Key**，前端显示掩码，真 Key 放在系统级加密存储里（9.4）。

### 9.2 测试连接：先探活再使用

```js
// POST /api/providers/:id/test
const p = db.prepare('SELECT * FROM providers WHERE id=?').get(id);
const key = await readProviderKey(id);              // 从加密存储读真 Key
if (!p || !key) return send(res, 400, { error: '请先保存 API Key' });

const started = Date.now();
const response = await fetch(`${p.base_url}/models`, {   // 兼容厂商都有 /models 探活端点
  headers: { Authorization: `Bearer ${key}` },
  signal: AbortSignal.timeout(p.timeout * 1000)          // 超时保护
});
if (!response.ok) return send(res, 502, { error: `连接失败：HTTP ${response.status}` });
return send(res, 200, { ok: true, latency: Date.now() - started });
```

界面上"测试连接"按钮的提示"连接成功，耗时 xxx ms"就来自这里——**在真正花钱调用前先确认连通性**。

### 9.3 调用分析：OpenAI 兼容协议

`POST /api/ai/analyze` 是对所有厂商的统一封装：

```js
const response = await fetch(`${p.base_url}/chat/completions`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${key}` },
  body: JSON.stringify({
    model: p.model, temperature: p.temperature, max_tokens: p.max_tokens,
    messages: [
      { role: 'system', content: '你是测试分析助手。仅返回合法 JSON，包含 summary、risk、suggestions、missingFields。' },
      { role: 'user',   content: `${taskType}\n${text}` }
    ]
  }),
  signal: AbortSignal.timeout(p.timeout * 1000)
});

const result = await response.json();
const content = result.choices?.[0]?.message?.content || '{}';
// 容错①：模型爱用 ```json 围栏包裹输出 → 剥掉
// 容错②：解析失败不崩溃 → 降级成 { summary: 原始文本 }
return send(res, 200, { provider: p.name, model: p.model,
  result: parse(content.replace(/^```json\s*|\s*```$/g, ''), { summary: content }) });
```

**为什么一个封装能对接四家？** 因为 OpenAI 的 `chat/completions` 已成为事实协议标准——DeepSeek、通义千问（兼容模式）都提供相同端点，自定义厂商只要兼容即可接入。这是"选一个事实标准做适配层"的典型收益。

### 9.4 密钥安全：两个平台两种方案

`scripts/provider-keys.mjs` 的核心设计（53 行）：

**Windows — DPAPI（数据保护 API）**：用当前 Windows 用户的凭据加密，密文只有同一台电脑的同一用户能解：

```js
function dpapi(mode, value) {   // mode: 'Protect' | 'Unprotect'
  const script = `
    Add-Type -AssemblyName System.Security;
    $s = [Console]::In.ReadToEnd();
    $bytes = [Convert]::FromBase64String($s);
    $out = [Security.Cryptography.ProtectedData]::${mode}($bytes, $null,
             [Security.Cryptography.DataProtectionScope]::CurrentUser);
    [Console]::Out.Write([Convert]::ToBase64String($out))`;
  // 通过 powershell -EncodedCommand 执行（脚本 base64 编码，避免引号转义问题）
  const child = spawn('powershell.exe',
    ['-NoProfile','-NonInteractive','-EncodedCommand', Buffer.from(script, 'utf16le').toString('base64')],
    { windowsHide: true });
  // stdin 传入密文 base64，stdout 取回结果
}
```

**macOS — 钥匙串**：

```js
await exec('/usr/bin/security', ['add-generic-password', '-U', '-a', id, '-s', 'TestPilot-LLM', '-w', secret]);
await exec('/usr/bin/security', ['find-generic-password', '-a', id, '-s', 'TestPilot-LLM', '-w']);   // 读取
```

还有两个工程细节值得学：

- **原子写入**：先写 `${file}.${uuid}.tmp` 再 `rename`——避免写到一半崩溃留下损坏文件；文件权限 `0o600`；
- **诚实的能力边界**：DPAPI 密文**不能跨用户/跨电脑解密**，换机后必须重新配置 Key——这个事实在 README 和界面上都如实告知，而不是假装"云端同步"。

### 9.5 降级设计：模型挂了，系统照转

前端分析页的调用逻辑（`main.tsx` 第 117 行附近）：

```ts
try {
  const ai = await API.post('ai/analyze', { providerId, taskType, text });
  result = { ...result, ...ai.result };              // 用模型结果增强本地结果
  model = `${ai.provider} / ${ai.model}`;
} catch (e) {
  notify(`模型暂不可用，已使用本地规则：${e.message}`);   // 明确告知，而非静默
}
const item = await API.post('tasks', { …, result, model });   // model 字段记录本次用了谁
```

- **本地规则永远可用**：没配 Key、断网、超时都不影响主流程；
- **降级必须可见**：提示里写明"已使用本地规则"，任务详情的"分析模型"字段也如实记录（"本地规则" vs "DeepSeek / deepseek-chat"）——用户随时知道每个结论是谁产出的。

### 10.2 deploy.mjs 六段拆解

`scripts/deploy.mjs`（62 行）是整个项目的"用户旅程入口"，按顺序做六件事：

**① 环境检查**——把问题拦在最前面：

if (Number(process.versions.node.split('.')[0]) < 24)

const probe = createServer();

for (const signal of ['SIGINT', 'SIGTERM']) process.on(signal, () => server.kill(signal));

## 11. 第 9 步 · 数据迁移（旧版 → SQLite）

### 🎯 本章目标

理解一个真实项目的"升级路径"：老用户的数据不能丢。

史实背景：这个项目的**第一代**是纯 JS 原型（根目录遗留的 `app.js`，498 行），数据存在浏览器 `localStorage` 里（key：`testpilot-personal-workbench-v1`）。第二代改成 SQLite 后，必须让老用户的数据平滑迁移。

### 11.1 迁移接口的两个关键设计

`POST /api/migrate` 接收旧数据 JSON，核心逻辑：

**① 幂等保护**——`migrations` 表用 key 做主键记录"迁移已完成"：

```js
const old = db.prepare('SELECT * FROM migrations WHERE key=?').get('localstorage-v1');
if (old) return send(res, 200, { migrated: false, reason: 'already-migrated', backupPath: old.backup_path });
```

重复点按钮、重复提交都不会产生重复数据——**这就是幂等的含义：同样的操作执行一万次，结果和执行一次相同**。

**② 备份先行**——导入之前先把原始数据写成只读 JSON：

```js
const backupPath = join(dataDir, 'backups', `localstorage-${Date.now()}.json`);
await writeFile(backupPath, JSON.stringify(d, null, 2), { flag: 'wx' });
```

`flag: 'wx'`（只允许创建新文件，已存在则报错）保证备份文件永远不会被覆盖。

**③ 逐条去重导入**：每条数据先查 id 是否存在，存在就跳过；每条导入都套用"字段默认值"防缺字段：

```js
for (const item of d.tasks || []) {
  const tid = item.id || makeId('legacy_task');
  if (db.prepare('SELECT 1 FROM tasks WHERE id=?').get(tid)) continue;
  db.prepare('INSERT INTO tasks VALUES(…)').run(tid, item.type || 'bug', …);
  imported.tasks++;
}
```

### 11.2 前端如何发现旧数据

App 初始化时偷看 localStorage（`main.tsx` 第 51 行）：

```tsx
useEffect(() => {
  refresh().catch(e => setToast(e.message));
  const raw = localStorage.getItem('testpilot-personal-workbench-v1');
  if (raw) { try { setMigrate(JSON.parse(raw)); } catch { /* 无效数据忽略 */ } }
}, []);
```

有旧数据就弹出迁移弹窗（显示"检测到 N 个任务和 M 条知识"），用户点"备份并迁移"后调用接口，成功后 `localStorage.removeItem(...)` 防止下次再弹。

### 启示

- **兼容旧数据有两种策略**：轻量幂等迁移（本项目，适合唯一的历史包袱）vs 版本化迁移框架（Flyway 等，适合持续演进的产品）。选哪种取决于"包袱数量"；
- **任何迁移都必须"备份先行、幂等兜底"**——这两条是数据工程的铁律。

### 12.3 调试速查

| 症状 | 处理 |
| --- | --- |
| 改了前端没反应 | 确认用的是 `npm run dev`（热更新）；检查终端是否有编译报错 |
| 改了 `server.mjs` 没生效 | 后端改动需要 `Ctrl+C` 后重新 `npm run dev` |
| 想知道库里有啥 | 用 DB Browser for SQLite 打开 `data/testpilot.sqlite`，或命令行 `sqlite3 data/testpilot.sqlite ".tables"` |
| 想看接口原始返回 | 浏览器 DevTools → Network；或 PowerShell：`Invoke-RestMethod 'http://127.0.0.1:3344/api/bootstrap'` |
| 端口被占用 | `netstat -ano | findstr 3344` 找到 PID 后 `taskkill /PID <pid> /F`，或设 `PORT` 环境变量 |
| 类型错误拦住构建 | `npm run check` 单独跑类型检查，报错位置精确到行列 |

### 12.4 后续可以自己扩展的方向

- **组合任务真正启动**：把"全链路模板"从保存模板升级为批量创建父子任务；
- **打包分发**：用 Electron/Tauri 包成桌面应用，或 Docker 化部署到 NAS。

## 结语

回顾这次"从0开发"之旅，你已经走过了完整的全栈闭环：

**环境骨架 → HTTP 服务器 → SQLite 数据层 → 通用 API → 前端外壳 → 页面模式 → 工作流引擎 → 模型接入 → 工程化部署 → 数据迁移**

如果只能带走三样东西，我希望是这三种"工程直觉"：

1. **约束驱动选型**——"个人本地工具"这个约束推导出了整个架构（零依赖、单进程、SQLite、无路由）；
2. **确定性优先**——骨架决策（路由、缺项、风险）用可测试的本地规则，AI 只负责内容生成，且永远可降级；
3. **可追溯即信任**——每一条结论都留下输入、证据、步骤和复核记录，这是 AI 时代测试工具的生命线。
